# 主线程与后台线程

> [!plain] 白话理解
> 可以把上位机程序想象成一个忙碌的车间主任：他一边接电话（处理鼠标点击）、一边写生产记录（刷新界面）、一边盯着设备状态（处理定时事件）。**主线程（UI 线程）就是这位主任，他同一时间只能做一件事**。如果你把"搬运 1000 吨钢材"（重计算/长 IO）这种粗活也交给他亲自干，那么他只能把电话和记录全部搁置——窗口就"卡死"了。正确的做法是：粗活交给"搬运工"（后台线程/线程池）去干，主任只在活干完时收个结果、更新一下记录。不这样做，任何需要超过几十毫秒的任务都会让界面冻结，拖动窗口、点击按钮全部无响应，这在现场操作中是不可接受的。
>
> 一句话：**UI 线程管界面，后台线程管干活，干完活回到 UI 线程汇报**。

> [!def] 官方定义
> - **主线程（UI 线程）**：WPF 应用启动时创建的进程主线程，负责创建窗口与控件、处理输入事件、执行布局渲染。它是**线程亲和**的——`System.Windows.Application` 启动后，绝大多数与界面相关的操作都要求在该线程上执行。
> - **后台线程**：由 `System.Threading.Thread`、`System.Threading.Tasks.Task`（经线程池）等创建的并行执行单元。后台线程没有创建控件，因此不能直接访问 UI 元素，必须借助 `System.Windows.Threading.Dispatcher` 把更新请求"投递"回 UI 线程。
> - WPF 对线程模型的要求不同于 WinForms（WinForms 不强制，WPF 强制校验），违反时抛出 `System.InvalidOperationException`："调用线程无法访问此对象，因为另一个线程拥有该对象。"
> - 📖 官方文档：[WPF 线程模型概述](https://learn.microsoft.com/zh-cn/dotnet/desktop/wpf/advanced/threading-model)

> [!origin] 由来背景
> 早期 Win32 程序用消息泵（Message Loop）驱动界面，任何耗时的窗口过程都会阻塞消息分发，造成界面无响应。WinForms 时代通过 `Control.Invoke` 实现了初级的跨线程调度，但并没有强制约束，开发者经常踩"跨线程访问控件"的坑。WPF 从 2006 年发布起，就把**单 UI 线程 + Dispatcher 调度 + 线程亲和校验**设计成了强约束的线程模型，并在 .NET 4.0（2010 年）引入 Task Parallel Library（TPL）后，用 `Task.Run` + `async/await` 取代了早年手写 `Thread` 的繁琐模式，让"后台干活、前台刷新"成为标准写法。

> [!essentials] 核心要点
> - **一个 UI 线程管所有控件**：WPF 窗口及其控件树只能由创建它的 UI 线程操作，这是线程亲和性的核心约束
> - **耗时任务必须离开 UI 线程**：超过 100ms 的任务（文件读写、串口等待、图像处理）都该放后台
> - **后台线程更新界面必须绕道**：`Dispatcher.Invoke`（同步等待）或 `Dispatcher.BeginInvoke`（异步排队），或用 `async/await` + `IProgress<T>` 自动回主线程
> - **后台线程不等于"越多越好"**：线程是系统资源，大量长驻线程会增大上下文切换开销，首选线程池（`Task.Run`）
> - **区分线程与进程**：后台线程共享进程内存，可读写普通字段；跨进程才需要 `Mutex` 等更重的机制（见 `mutex-跨进程互斥`）

> [!example] 完整示例
> **主线程与后台线程演示：耗时任务放后台执行，界面保持流畅：**
>
> **MainWindow.xaml：**
> ```xml
> <Window x:Class="HmiDemo.MainWindow"
>         xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
>         xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
>         Title="主线程与后台线程" Height="380" Width="420"
>         WindowStartupLocation="CenterScreen" Background="#0D1117">
>     <StackPanel Margin="15" Background="#161B22" Padding="15">
>         <TextBlock Text="上位机线程模型演示" FontSize="16" FontWeight="Bold"
>                    Foreground="#58A6FF" Margin="0,0,0,10"/>
>         <TextBlock x:Name="ThreadInfoText" TextWrapping="Wrap"
>                    Foreground="#8B949E" Margin="0,0,0,10"/>
>         <!-- 在主线程直接执行耗时任务：窗口会卡死 -->
>         <Button Content="主线程执行耗时任务（界面卡死）" Click="OnSyncClick"
>                 Margin="0,5" Padding="8" Background="#DA3633" Foreground="White"/>
>         <!-- 放后台线程执行：界面保持流畅 -->
>         <Button Content="后台线程执行耗时任务（界面流畅）" Click="OnAsyncClick"
>                 Margin="0,5" Padding="8" Background="#238636" Foreground="White"/>
>         <TextBlock x:Name="ResultText" Foreground="#8B949E"
>                    Margin="0,10,0,0" TextWrapping="Wrap"/>
>     </StackPanel>
> </Window>
> ```
>
> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System.Threading;
> using System.Threading.Tasks;
> using System.Windows;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         public MainWindow()
>         {
>             InitializeComponent();
>             // 展示主线程的基本信息
>             var thread = Thread.CurrentThread;
>             ThreadInfoText.Text = $"主线程 ID = {thread.ManagedThreadId}，" +
>                                   $"IsBackground = {thread.IsBackground}";
>         }
>
>         // 错误示范：在主线程直接做 3 秒耗时操作，窗口会卡死无法拖动
>         private void OnSyncClick(object sender, RoutedEventArgs e)
>         {
>             ResultText.Text = "开始在主线程执行耗时任务…（窗口此时无法响应）";
>             Thread.Sleep(3000); // 模拟重型计算
>             ResultText.Text = "主线程任务完成";
>         }
>
>         // 正确做法：把耗时任务丢给后台线程，界面保持流畅
>         private void OnAsyncClick(object sender, RoutedEventArgs e)
>         {
>             ResultText.Text = "已提交到后台线程执行…";
>             int threadId = 0;
>             Task.Run(() =>
>             {
>                 Thread.Sleep(3000); // 模拟耗时任务
>                 threadId = Thread.CurrentThread.ManagedThreadId;
>                 // 后台线程不能直接改控件，必须回到主线程调度
>                 Dispatcher.Invoke(() => ResultText.Text =
>                     $"后台线程(Id={threadId})任务完成，界面未卡顿");
>             });
>         }
>     }
> }
> ```
> 

> [!scene] 适用场景
> ✅ **需要保界面的耗时操作**：PLC 通信等待、大批量数据解析、图像模板匹配——这些放后台，界面照常可操作
> ✅ **周期性数据采集**：采集线程在后台循环读数据，只把最新值推给界面刷新（见 `定时数据采集模式`）
> ✅ **导入/导出/打印**：文件处理放后台并显示进度，避免点击导出后整个程序"假死"
> ❌ **纯计算量极小的操作**：更新一个 TextBlock 文本这种微秒级操作没必要开线程，徒增调度开销
> ❌ **访问非线程安全的共享状态**：多个后台线程同时改同一个 `List<T>` 或普通 Dictionary，必须先加锁或换用 `并发集合`，否则数据损坏

> [!pitfall] 常见踩坑
> 坑 1：**耗时任务直接写在 Click 事件里** → 现象：点击按钮后窗口白屏无响应，标题栏显示"未响应" → 原因：UI 线程被 `Thread.Sleep`/同步 IO 阻塞，消息泵停止工作 → 解决：把任务包进 `Task.Run` 或 `await Task.Run(...)`，完成后再回 UI 线程更新结果
>
> 坑 2：**后台线程直接改控件** → 现象：运行时抛出 `InvalidOperationException`（调用线程无法访问此对象）→ 原因：WPF 控件有线程亲和性，非创建线程访问即报错 → 解决：一律用 `Dispatcher.Invoke`/`BeginInvoke` 或 `async/await`（await 会自动回到 UI 上下文，见 `async-与-await-详解`）
>
> 坑 3：**把"后台线程"理解成"随便 new Thread"** → 现象：任务量小但线程很多，程序莫名变慢、CPU 飙高 → 原因：每个 `Thread` 默认占约 1MB 栈内存，且上下文切换有开销 → 解决：短任务用 `Task.Run` 走线程池，只有需长时间独占的后台服务（如串口监听）才考虑专用线程（见 `线程池-vs-专用线程`）

> [!best] 最佳实践
> - **先问"能不能不动 UI 线程"**：凡是超过 50ms 的操作一律考虑后台，这是上位机流畅性的底线
> - **`async/await` 优先于手写 `Thread`**：`await Task.Run(...)` 写法简洁、异常传播自然，还自动处理了回 UI 线程的问题
> - **后台回传进度用 `IProgress<T>`**：它内部用 `SynchronizationContext` 自动回到 UI 线程，比手动 `Dispatcher` 更干净（见 `从-ui-线程安全更新控件`）
> - **取消用 `CancellationToken`**：采集/计算任务都该支持取消，防止关闭窗口后后台线程还在空转（见 `取消异步操作`）
> - **用 `Thread.CurrentThread.ManagedThreadId` 打日志**：定位"到底在哪个线程跑"时，这个 ID 是最直接的证据

> [!practice] 上手练习
> **Lv.1 运行改参数**：运行示例，先点红色按钮感受 3 秒卡死，再点绿色按钮对比流畅效果；把 `Thread.Sleep(3000)` 改成 8000，观察两种方式差异更明显
> **Lv.2 加属性**：在 `ResultText` 下方加一个进度 TextBlock，在 `Task.Run` 里模拟 10 步进度（每步 `Sleep(300)`），用 `Dispatcher.Invoke` 每步更新一次进度文本
> **Lv.3 改造异步**：把 `OnAsyncClick` 改成 `async void` + `await Task.Run(...)`，去掉手动 `Dispatcher.Invoke`，验证 `await` 之后代码自动回到 UI 线程执行
> **Lv.4 挑战**：做一个"开始采集/停止采集"模拟器：点开始后后台线程每 500ms 生成一个随机温度值（用 `Random`），实时刷新界面 TextBlock；点停止后任务退出。尝试引入 `CancellationToken` 优雅停止（可先参考 `取消异步操作`）
