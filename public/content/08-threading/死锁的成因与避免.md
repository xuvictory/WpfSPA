# 死锁的成因与避免

> [!plain] 白话理解
> 死锁就像**两辆对向行驶的车在一座只能过一辆的窄桥上相遇**：车 A 占了桥头 A 端、想开到 B 端，车 B 占了桥头 B 端、想开到 A 端，两辆车互不相让，谁也动不了。程序里也一样：线程 1 拿了锁 A、想要锁 B，线程 2 拿了锁 B、想要锁 A——两个线程各自攥着一把对方需要的钥匙，谁都不肯放手，就永远卡死了。最典型的场景是**"UI 线程 `.Wait()` 等后台，后台 `Dispatcher.Invoke` 等 UI"**：两边互相等，界面假死、后台停摆。避免死锁的常用招数是：**所有线程按同一顺序拿锁**（大家都先过 A 端桥再过 B 端桥），或者干脆**少拿锁、用异步代替同步等待**。
>
> 一句话：**死锁 = 两个线程互相攥着对方要的锁，谁也等不到**——统一拿锁顺序 + 不用同步等待可根治。

> [!def] 官方定义
> - **死锁（Deadlock）**：两个或多个线程在执行过程中因**竞争资源而造成互相等待**的状态，若无外力干预，这些线程都无法继续执行。操作系统把死锁产生的四个必要条件（Coffman 条件）归纳为：**互斥、持有并等待、不可剥夺、循环等待**。
> - **互斥**：资源同一时刻只能被一个线程占用（锁的特性）。
> - **持有并等待**：线程持有至少一个资源，又在等待另一个资源。
> - **不可剥夺**：已持有的资源不能被其他线程强行抢走（`lock` 不可强夺）。
> - **循环等待**：线程 A 等线程 B 的资源、B 等 A 的资源，形成环形等待。
> - **WPF 场景的典型死锁**：UI 线程调用 `.Wait()`/`.Result` 等待后台 Task，而该 Task 完成前需要回到 UI 线程（`Dispatcher`/同步上下文）——两者互相等待。
> - 📖 官方文档：[死锁（.NET 并发术语）](https://learn.microsoft.com/zh-cn/dotnet/standard/threading/deadlocks)、[基于任务的异步模式中的死锁陷阱](https://learn.microsoft.com/zh-cn/dotnet/csharp/asynchronous-programming/async-scenarios)

> [!origin] 由来背景
> 死锁是并发编程从操作系统诞生起就存在的经典难题。1971 年 Edward G. Coffman 等人归纳出死锁的四个必要条件，此后"预防死锁"的核心思路就是**破坏四个条件之一**：最常见的是"破坏循环等待"（统一加锁顺序）和"破坏持有并等待"（一次性申请全部资源）。.NET 的 `lock` 本身无法检测死锁，开发者的纪律决定了风险高低。C# 5.0（2012）的 async/await 从语言层面提供了根治方案：**用 `await` 代替 `.Wait()`/`.Result`，UI 线程不再"持有并等待"**，从源头消灭了 WPF 中最常见的一类死锁。上位机开发中，UI 与采集线程的交互频繁，理解死锁机制是写出可靠程序的必修课。

> [!essentials] 核心要点
> - **四个必要条件缺一不可**：破坏任何一个都能避免死锁——实践中主要破坏"循环等待"（统一顺序）与"持有并等待"（不长时间持锁等待）
> - **WPF 头号死锁：`.Wait()`/`.Result` + await 回 UI**：UI 线程同步等待后台任务，后台任务需要回 UI 上下文完成——互相等死
> - **多把锁必须统一顺序**：所有线程按"锁 A→锁 B"的同一顺序获取，循环等待就不存在
> - **`lock` 内不能 `await`**：编译器会报错，恰好避免"持锁跨异步"；需要异步互斥用 `SemaphoreSlim(1,1)`（见 `semaphore-信号量`）
> - **死锁无异常、难发现**：程序不报错只是"卡住"，调试时用 Visual Studio 的"并行堆栈/调试所有线程"窗口可定位
> - **避免死锁的优先级**：不用锁 > 少用锁 > 短持锁 > 统一顺序 > 超时检测

> **死锁演示与避免：两个锁交叉申请导致互相等待：**

> <Window x:Class="HmiDemo.MainWindow"

>                    Foreground="#58A6FF" Margin="0,0,0,10"/>
>         <!-- 错误示范：交叉加锁导致死锁 -->
>         <Button Content="制造死锁（线程交叉加锁）" Click="OnDeadlockClick"
>                 Margin="0,5" Padding="8" Background="#DA3633" Foreground="White"/>
>         <!-- 正确示范：按固定顺序加锁，避免死锁 -->
>         <Button Content="按固定顺序加锁（避免死锁）" Click="OnSafeClick"
>                 Margin="0,5" Padding="8" Background="#238636" Foreground="White"/>
>         <TextBlock x:Name="LogText" Foreground="#8B949E" TextWrapping="Wrap"
>                    MinHeight="160" Margin="0,10,0,0"/>
>     </StackPanel>
> </Window>
> ```
>
> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Threading;
> using System.Threading.Tasks;
> using System.Windows;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         private readonly object _lockA = new object(); // 模拟锁 A：数据库连接
>         private readonly object _lockB = new object(); // 模拟锁 B：设备缓冲区
>
>         public MainWindow() => InitializeComponent();
>
>         // 死锁版：线程 1 拿 A 要 B，线程 2 拿 B 要 A，互相等待永不释放
>         private void OnDeadlockClick(object sender, RoutedEventArgs e)
>         {
>             LogText.Text = "";
>             Task.Run(() =>
>             {
>                 lock (_lockA)
>                 {
>                     AppendLog("线程1：已锁定 A，等待 B…");
>                     Thread.Sleep(200);
>                     lock (_lockB) { AppendLog("线程1：获得 B"); }
>                 }
>             });
>             Task.Run(() =>
>             {
>                 lock (_lockB)
>                 {
>                     AppendLog("线程2：已锁定 B，等待 A…");
>                     Thread.Sleep(200);
>                     lock (_lockA) { AppendLog("线程2：获得 A"); }
>                 }
>             });
>             AppendLog("两个线程互相等待，程序陷入死锁 ⚠");
>         }
>
>         // 安全版：两个线程都按 A→B 的固定顺序加锁，永远不会循环等待
>         private void OnSafeClick(object sender, RoutedEventArgs e)
>         {
>             LogText.Text = "";
>             Task.Run(() =>
>             {
>                 lock (_lockA)
>                 {
>                     Thread.Sleep(200);
>                     lock (_lockB) { AppendLog("线程1：A→B 顺序执行完成"); }
>                 }
>             });
>             Task.Run(() =>
>             {
>                 lock (_lockA) // 同样先 A 后 B，与线程1 保持一致
>                 {
>                     Thread.Sleep(200);
>                     lock (_lockB) { AppendLog("线程2：A→B 顺序执行完成"); }
>                 }
>             });
>             AppendLog("统一加锁顺序（A→B），死锁被避免 ✓");
>         }
>
>         private void AppendLog(string line) =>
>             Dispatcher.Invoke(() => LogText.Text += line + Environment.NewLine);
>     }
> }
> ```
> 

> [!scene] 适用场景
> ✅ **UI 线程等待后台任务**：`await` 是正解；若遇到老代码 `.Result`/`.Wait()`，立即改写成 `async/await` 全链路
> ✅ **多资源操作**：同时操作"数据库 + 设备缓冲区"等多共享资源时，审视加锁顺序
> ✅ **组件/库的嵌套调用**：A 库加锁调用 B 库、B 库又回调 A——检查是否构成循环等待
> ✅ **第三方库回调**：回调发生在锁内时要特别小心（回调里又去抢同一把锁）
> ❌ **单锁简单场景**：只有一个 `lock` 不存在循环等待，正常用即可
> ❌ **追求极端性能处滥用锁**：锁多了死锁概率高，能用并发集合/无锁方案就别加锁（见 `并发集合`）

> [!pitfall] 常见踩坑
> 坑 1：**UI 线程 `.Result` 等后台 + 后台要回 UI** → 现象：窗口打开就假死，标题栏"未响应" → 原因：UI 持锁（同步上下文）等待后台，后台完成需要回 UI 上下文 → 解决：**async all the way**——从事件处理器开始用 `await`，绝不 `.Wait()`/`.Result`（见 `async-与-await-详解`）
>
> 坑 2：**多把锁加锁顺序不一致** → 现象：偶发程序卡死，尤其并发量大时 → 原因：线程 1 A→B、线程 2 B→A 形成循环等待 → 解决：全项目约定统一顺序（如"先小锁后大锁、先低层后高层"），代码评审重点检查
>
> 坑 3：**锁内调用第三方/回调方法** → 现象：调用方与回调方互相等 → 原因：持锁状态下回调里又申请锁 → 解决：锁内只做"纯数据操作"，任何回调/事件/外部调用移出锁外
>
> 坑 4：**`lock` 里 `await`（编译器已禁）但误用 `SemaphoreSlim` 拿锁跨异步** → 现象：异步链里持锁过久，其他异步任务排队假死 → 原因：`WaitAsync` 拿到信号量后 `await` 期间一直持有 → 解决：能避免就避免"跨 await 持锁"；真需要时严格限定临界区范围并加超时 `WaitAsync(TimeSpan, token)`

> [!best] 最佳实践
> - **第一原则：UI 线程永不同步等待**：`await` 代替 `.Wait()`/`.Result`，这是 WPF 死锁头号来源的根治
> - **能不用锁就不用**：`Interlocked`、并发集合、不可变数据（见 `并发集合`、`lock-与-monitor`）
> - **统一加锁顺序**：多锁场景制定规范（如"按资源 id 排序"），并在代码评审中人工检查
> - **缩短持锁时间**：临界区只放"读-改-写"最小代码，IO、回调、await 全在锁外
> - **用超时兜底**：`Monitor.TryEnter(lockObj, TimeSpan.FromSeconds(1))` 拿不到就重试/报错，把死锁变超时
> - **调试用并行堆栈**：程序卡死时，VS 菜单"调试→窗口→并行任务/线程"，看谁在等谁
> - **测试用并发压力**：写"多个线程反复操作共享资源"的测试，死锁在开发期暴露而不是现场

> [!practice] 上手练习
> **Lv.1 运行改参数**：运行示例点红色按钮观察死锁日志（两线程都卡在等待），点绿色按钮对比正确结果；把 `Thread.Sleep(200)` 改成 500 观察更明显的停顿
> **Lv.2 加属性**：把红色按钮改为"5 秒后自动恢复"：在后台线程里先 `lock A`，再用 `Monitor.TryEnter(_lockB, TimeSpan.FromSeconds(5))` 等锁，拿不到就放弃并输出"超时，不再等待"
> **Lv.3 改造**：实现"UI 死锁复现"：一个按钮里 `Task.Run(() => Task.Delay(1000)).Wait()`（UI 线程等待），观察窗口卡死；再用 `await Task.Run(...)` 改造，验证窗口恢复流畅
> **Lv.4 挑战**：写一个"银行转账"模拟：两个账户 A、B 与两个线程互相转账（A→B、B→A），用 lock 保护账户；先写出死锁版本复现，再用"按账户 id 排序加锁"修复，验证并发 100 次无死锁且余额守恒
