# 项目结构与目录规划

> [!plain] 白话理解
> 车间要分区：物料区、装配区、质检区各归各，工具不能乱放——**布局决定效率**。项目结构就是代码的"车间布局"：`Models` 放数据实体、`ViewModels` 放界面逻辑、`Views` 放界面、`Services` 放服务、`Helpers` 放公共工具。
> 不规划会怎样？几百个类堆在一个目录里，新同事入职一个月找不到"报警逻辑在哪"；项目一壮大就重构，代价巨大。按职责分目录，任何代码"按图索骥"3 秒定位——这本身就是团队协作的隐形规则。

> [!def] 官方定义
> 目录结构（Project Structure）是 MVVM 项目的**组织约定**，将代码按职责与分层归入命名空间与文件夹。典型结构：
> ```
> WpfApp/
> ├─ App.xaml / MainWindow.xaml        # 组合根与主窗体
> ├─ Models/                           # 数据实体（DeviceModel、AlarmModel）
> ├─ ViewModels/                       # 页面/窗口 VM（MainViewModel、DeviceViewModel）
> ├─ Views/                            # XAML 界面（DeviceView、AlarmView）
> ├─ Services/                         # 基础设施服务（ConfigService、LogService、SerialService）
> └─ Helpers/                          # 命令、转换器、基类（RelayCommand、ViewModelBase）
> ```
> 大型项目可再按**功能模块**划分（Prism Module：每模块内再分 VM/View/Service）。命名空间与文件夹保持一致，如 `WpfApp.ViewModels`。
> 官方文档：https://learn.microsoft.com/zh-cn/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures

> [!origin] 由来背景
> WPF 早期项目常见"文件夹里堆一切"：`MainWindow.xaml.cs` 上千行，业务逻辑、数据访问、弹窗混在一起。MVVM 普及后，社区逐步沉淀出**按层分文件夹**的惯例：`Models`（数据）、`ViewModels`（逻辑）、`Views`（界面）、`Services`（服务）、`Helpers`（公共件）。
> Prism 等框架进一步引入**模块化**（Module）：把功能按领域切分（设备模块、报警模块、配方模块），每模块内部再分层。上位机项目功能庞杂（通信、看板、报表、权限），良好的目录规划从"可选项"变成了**项目能撑到第 10 个功能页的关键**。

> [!essentials] 核心要点
> - **四层基础**：`Models`（实体）、`ViewModels`（界面状态/命令）、`Views`（XAML）、`Services`（基础设施）
> - **公共件入 Helpers/Infrastructure**：`RelayCommand`、`ViewModelBase`、`BooleanToVisibilityConverter`、`IDialogService` 等
> - **依赖方向单向**：View → ViewModel → Service → Model，禁止反向引用（Model 不引用 VM、VM 不引用 View）
> - **命名规范**：`DeviceView` ↔ `DeviceViewModel` ↔ `DeviceModel`，一一对应，目录即命名空间
> - **分层 vs 模块化**：中小项目按层分；大型项目按模块分（模块内再分层），或二者结合
> - **组合根独立**：容器装配代码集中（`App.xaml.cs` 或 `Bootstrapper.cs`），见「di-在-mvvm-中的应用」

> [!example] 完整示例
> **目录规划演示：模拟一个分层清晰的 MVVM 项目结构——Model（数据实体）→ Service（服务）→ ViewModel（界面逻辑）→ View（界面）。这里用 DeviceViewModel 展示三层协作：**
>
> **MainWindow.xaml：**
> ```xml
> <Window x:Class="HmiDemo.MainWindow"
>         xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
>         xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
>         Title="项目结构与目录规划" Height="340" Width="420"
>         WindowStartupLocation="CenterScreen" Background="#0D1117">
>     <StackPanel Margin="20">
>         <TextBlock Text="分层架构演示（Models / Services / ViewModels / Views）" Foreground="#58A6FF"
>                    FontSize="14" FontWeight="Bold" TextWrapping="Wrap"/>
>         <TextBlock Text="设备名称" Foreground="#8B949E" Margin="0,15,0,4"/>
>         <TextBlock Text="{Binding DeviceName}" Foreground="White" FontSize="20" FontWeight="Bold"/>
>         <TextBlock Text="运行状态" Foreground="#8B949E" Margin="0,12,0,4"/>
>         <TextBlock Text="{Binding Status}" Foreground="#238636" FontSize="18"/>
>         <TextBlock Text="当前产量（件）" Foreground="#8B949E" Margin="0,12,0,4"/>
>         <TextBlock Text="{Binding Output}" Foreground="White" FontSize="28" FontWeight="Bold"/>
>         <TextBlock Text="{Binding LayerNote}" Foreground="#8B949E" Margin="0,10,0,0"
>                    TextWrapping="Wrap"/>
>     </StackPanel>
> </Window>
> ```
>
> **MainWindow.xaml.cs —— 按层组织的三组类：**
> ```csharp
> using System;
> using System.ComponentModel;
> using System.Windows;
>
> namespace HmiDemo
> {
>     // ---------- Models 层：纯数据实体，不含任何逻辑 ----------
>     public class DeviceModel
>     {
>         public string Name { get; set; }
>         public bool IsRunning { get; set; }
>         public int Output { get; set; }
>     }
>
>     // ---------- Services 层：数据获取与业务服务 ----------
>     public class DeviceService
>     {
>         // 生产环境：从 PLC / 数据库读取，此处用模拟数据
>         public DeviceModel GetDevice()
>         {
>             return new DeviceModel
>             {
>                 Name = "冲压机 #1",
>                 IsRunning = true,
>                 Output = 1280
>             };
>         }
>     }
>
>     // ---------- ViewModels 层：界面状态与命令（调用 Service） ----------
>     public class MainViewModel : INotifyPropertyChanged
>     {
>         private readonly DeviceService _deviceService;
>         private DeviceModel _device;
>
>         public MainViewModel(DeviceService deviceService)
>         {
>             _deviceService = deviceService;
>             Load();
>         }
>
>         private void Load()
>         {
>             _device = _deviceService.GetDevice(); // VM 不碰数据源，只调服务
>             OnPropertyChanged(nameof(DeviceName));
>             OnPropertyChanged(nameof(Status));
>             OnPropertyChanged(nameof(Output));
>         }
>
>         public string DeviceName => _device.Name;
>         public string Status => _device.IsRunning ? "运行中" : "已停止";
>         public string Output => _device.Output.ToString();
>         public string LayerNote => "数据流：Models → Services → ViewModels → Views";
>
>         public event PropertyChangedEventHandler PropertyChanged;
>         private void OnPropertyChanged(string name) =>
>             PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(name));
>     }
>
>     // ---------- Views 层（入口）：把组装好的 VM 交给界面 ----------
>     public partial class MainWindow : Window
>     {
>         public MainWindow()
>         {
>             InitializeComponent();
>             DataContext = new MainViewModel(new DeviceService());
>         }
>     }
> }
> ```

> [!scene] 适用场景
> ✅ **中型以上项目**（20+ 类）：按层分目录，代码可定位性、可维护性显著提升
> ✅ **多人协作**：目录即约定，每人负责一层/一模块，冲突少、交接快
> ✅ **需要单元测试**：VM/Service 分层后，各层可独立注入 Mock 测试
> ✅ **大型上位机**（看板+报警+配方+报表+权限）：按功能模块划分，模块间解耦
> ❌ 3-5 个类的教学 demo：分层反而增加跳转成本，直接单文件更清晰
> ❌ 一次性工具程序：不需要目录规范

> [!pitfall] 常见踩坑
> 坑 1：**有目录没分层纪律** → 现象：`ViewModel` 里直接 `new Window()`、`Model` 里写数据库逻辑；原因：只分文件夹、没守住依赖方向；解决：明确"View → VM → Service → Model"单向依赖，代码评审把"VM 里出现 View 类型"列为红线
>
> 坑 2：**按页面功能分、不按层分** → 现象：找"报警业务逻辑"要去 `AlarmPage` 目录里翻，页面与逻辑耦合；原因：混合分法；解决：采用"**层 + 模块**"二维划分——先按层建目录，功能模块在层内用小目录聚合
>
> 坑 3：**ViewModel 塞满一切** → 现象：`MainViewModel` 上千行，属性、命令、数据访问、弹窗全在里面；原因：单一职责被忽略；解决：数据访问抽到 Service、公共命令/转换器抽到 Helpers、页面逻辑拆成多个小 VM，VM 只做"绑定适配"

> [!best] 最佳实践
> - **默认模板**：`Models/`、`ViewModels/`、`Views/`、`Services/`、`Helpers/` 五件套起步，名字即职责
> - **View↔VM 一一对应**：`DeviceView` 配 `DeviceViewModel`，命名对称，自动映射（DataTemplate/Prism）才顺
> - **服务接口与实现就近**：`Services/IDeviceService.cs` + `Services/DeviceService.cs`（或 `Services/Interfaces/` 分离）
> - **公共件收敛**：`RelayCommand`、`ViewModelBase`、转换器、对话框接口放 `Helpers/Infrastructure`，避免散落
> - **目录 = 命名空间**：文件夹结构与 namespace 保持一致，减少 `using` 混乱
> - **组合根独立成文件**：`Bootstrapper.cs`（或 `App.xaml.cs`）集中容器装配，见「di-在-mvvm-中的应用」

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例，对照代码梳理 `DeviceModel`（Model 层）、`DeviceService`（Service 层）、`MainViewModel`（VM 层）、`MainWindow`（View 层）各属哪层
> **Lv.2 小试牛刀**：新增 `AlarmService` 与 `AlarmModel`（`Id/Level/Message/Time`），在 VM 中注入并显示最新一条报警——体验"新增功能 = 新增一个 Service + 一个 Model + 绑定一行"
> **Lv.3 融会贯通**：把示例改造成规范目录：在 `MainWindow.xaml.cs` 里新增 `namespace HmiDemo.ViewModels`（VM）、`HmiDemo.Services`（Service）、`HmiDemo.Models`（Model）三个命名空间并把类分开放，体会"文件夹即命名空间"
> **Lv.4 拆层挑战**：把示例改造成"**按模块分组**"结构：`Features/Device/`（内分 Model/Service/ViewModel/View）、`Features/Alarm/`，对比"按层分"与"按模块分"两种组织方式的取舍，并用 Prism `RegisterTypes` 完成各模块注册
