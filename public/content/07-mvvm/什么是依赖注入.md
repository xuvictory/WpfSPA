# 什么是依赖注入？

> [!plain] 白话理解
> 车间里装一台新传感器，工装师傅不会自己开五金店去造零件，而是**需要什么、让采购按清单送过来**。依赖注入就是这个思路：`MainViewModel` 需要"取产量"的能力，它不在自己里面 `new` 一个具体服务，而是**在构造函数里声明"我要一个能取产量的东西"**，由外部把实现送进来。
> 不这样做会怎样？如果把 `new MesProductionService()` 写死在 ViewModel 里，想换数据源（真实 MES / 测试 Mock）就必须改 ViewModel 代码；而注入之后，**换实现只改"组装处"一行**，ViewModel 本身完全不用动。这就是解耦。

> [!def] 官方定义
> 依赖注入（Dependency Injection，DI）是一种软件设计模式：**对象在其构造函数、属性或方法中接收它所依赖的其他对象（服务），而不是由自身创建或查找这些依赖**。它属于控制反转（Inversion of Control，IoC）的一种实现方式，由 Martin Fowler 在 2004 年发表的《Inversion of Control Containers and the Dependency Injection pattern》中系统命名并区分出构造器注入、属性（Setter）注入、接口注入三种形式。
> .NET 官方实现为 `Microsoft.Extensions.DependencyInjection` 包，核心类型：`IServiceCollection`（注册服务）与 `IServiceProvider`（解析服务）；WPF 中 ViewModel 最常用的是构造器注入。
> 官方文档：https://learn.microsoft.com/zh-cn/dotnet/core/extensions/dependency-injection

> [!origin] 由来背景
> 依赖注入的哲学根源是 SOLID 原则中的**依赖倒置原则（Dependency Inversion Principle，Robert C. Martin 提出）**：高层模块不应依赖低层模块，二者都应依赖抽象；抽象不应依赖细节，细节应依赖抽象。
> 2004 年，Martin Fowler 在分析当时的 IoC 容器乱象时写下《Inversion of Control Containers and the Dependency Injection pattern》，首次把"对象从外部接收依赖"这一思想命名为"依赖注入"，并指出它与 IoC 容器是两回事：**DI 是设计思想，容器只是实现它的工具**。
> 在 WPF 上位机领域，早期代码普遍在 ViewModel 里直接 `new` 服务对象，导致三个痛点：硬件实现难以替换（联调真实 PLC 与模拟器要改业务代码）、单元测试无从下手（无法注入 Mock）、服务间的装配逻辑散落各处。DI 正是为解决这些痛点而成为 MVVM 工程化的基石。

> [!essentials] 核心要点
> - **三个角色**：服务（接口，如 `IProductionService`）、客户端（消费服务的对象，如 `MainViewModel`）、注入器（负责组装与传递，可以是手写代码或容器）
> - **构造函数注入是 WPF 首选**：依赖在对象创建时一次性确定、只读不可变，最能表达"这个对象离不开这些依赖"
> - **DI 与 IoC 的关系**：IoC 是更宏观的思想（依赖的控制权反转），DI 是它的具体实现方式之一（另一种是服务定位器 ServiceLocator）
> - **面向接口而非实现**：注入的永远是抽象（接口），才能实现实现类的自由替换与 Mock 测试
> - **DI 与 MVVM 的结合**：ViewModel 构造函数接收 `ILogger`、`IAlarmService` 等服务，界面层只负责解析装配好的 ViewModel

> [!example] 完整示例
> **依赖注入演示：数据服务通过构造函数注入到 ViewModel，而不是在 ViewModel 里 new 出来。这样更换服务实现（真实 PLC / Mock）只需改一处：**
>
> **MainWindow.xaml：**
> ```xml
> <Window x:Class="HmiDemo.MainWindow"
>         xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
>         xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
>         Title="什么是依赖注入" Height="340" Width="400"
>         WindowStartupLocation="CenterScreen" Background="#0D1117">
>     <StackPanel Margin="20">
>         <TextBlock Text="产量统计（依赖注入）" Foreground="#58A6FF" FontSize="16" FontWeight="Bold"/>
>         <TextBlock Text="数据来源" Foreground="#8B949E" Margin="0,15,0,4"/>
>         <TextBlock Text="{Binding SourceName}" Foreground="#58A6FF" FontSize="14"/>
>         <TextBlock Text="今日产量（件）" Foreground="#8B949E" Margin="0,12,0,4"/>
>         <TextBlock Text="{Binding TodayOutput}" Foreground="White" FontSize="28" FontWeight="Bold"/>
>         <TextBlock Text="{Binding Remark}" Foreground="#238636" Margin="0,4,0,15"/>
>         <Button Content="刷新产量" Command="{Binding RefreshCommand}" Padding="8"
>                 Background="#21262D" Foreground="White" HorizontalAlignment="Left"/>
>     </StackPanel>
> </Window>
> ```
>
> **MainWindow.xaml.cs —— 构造函数注入：**
> ```csharp
> using System;
> using System.ComponentModel;
> using System.Windows;
> using System.Windows.Input;
>
> namespace HmiDemo
> {
>     // 数据服务接口：定义"取产量"能力，不关心具体实现
>     public interface IProductionService
>     {
>         int GetTodayOutput();
>         string SourceName { get; }
>     }
>
>     // 真实实现：连接 MES 系统（此处用随机数模拟）
>     public class MesProductionService : IProductionService
>     {
>         private readonly Random _rand = new Random();
>         public string SourceName => "MES 系统";
>         public int GetTodayOutput() => 800 + _rand.Next(400);
>     }
>
>     // 测试实现：固定返回值，便于单元测试（这就是注入的好处）
>     public class MockProductionService : IProductionService
>     {
>         public string SourceName => "测试 Mock";
>         public int GetTodayOutput() => 100;
>     }
>
>     public class MainViewModel : INotifyPropertyChanged
>     {
>         private readonly IProductionService _service; // 只依赖接口
>         private int _todayOutput;
>
>         // 依赖通过构造函数注入：谁想用，谁就传进来
>         public MainViewModel(IProductionService service)
>         {
>             _service = service;
>             RefreshCommand = new RelayCommand(Refresh);
>             Refresh();
>         }
>
>         public string SourceName => _service.SourceName;
>         public string TodayOutput => _todayOutput.ToString();
>         public string Remark => "注入的服务可在 MainWindow 里一行切换";
>         public ICommand RefreshCommand { get; }
>
>         private void Refresh()
>         {
>             _todayOutput = _service.GetTodayOutput();
>             OnPropertyChanged(nameof(TodayOutput));
>         }
>
>         public event PropertyChangedEventHandler PropertyChanged;
>         private void OnPropertyChanged(string name) =>
>             PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(name));
>     }
>
>     public class RelayCommand : ICommand
>     {
>         private readonly Action _execute;
>         public RelayCommand(Action execute) => _execute = execute;
>         public bool CanExecute(object parameter) => true;
>         public void Execute(object parameter) => _execute();
>         public event EventHandler CanExecuteChanged;
>     }
>
>     public partial class MainWindow : Window
>     {
>         public MainWindow()
>         {
>             InitializeComponent();
>             // 想换数据源，只改这一行：new MockProductionService() 即可
>             DataContext = new MainViewModel(new MesProductionService());
>         }
>     }
> }
> ```

> [!scene] 适用场景
> ✅ 需要**替换硬件实现**的上位机：同一套界面，联调用真实 PLC 通信、演示/调试用模拟器，只换注入的实例
> ✅ 业务逻辑要写**单元测试**：给 ViewModel 注入固定返回值的 Mock 服务，不连真实设备即可验证逻辑
> ✅ 服务协作多的项目：日志、配置、通信、报警多个服务互相配合，统一由组装处装配
> ✅ 团队开发的大项目：模块只认接口，各人实现自己的服务，互不阻塞
> ❌ 仅三五个类的小工具：手工 `new` 更直白，引入注入反增样板代码
> ❌ 依赖关系单一（ViewModel 只依赖一个服务）的页面：直接构造即可，不必上容器

> [!pitfall] 常见踩坑
> 坑 1：**循环依赖导致解析失败或栈溢出** → 现象：容器解析时报"循环依赖"异常，或程序栈溢出崩溃；原因：A 依赖 B，B 又依赖 A；解决：把两者共用的底层逻辑下沉到第三个服务（如从 B 中抽出 A 需要的部分），打破环
>
> 坑 2：**到处 `new`，注入形同虚设** → 现象：改了容器注册，页面行为不变；原因：ViewModel 内部仍直接 `new ConcreteService()`，根本没走注入；解决：先抽象接口，所有依赖一律从构造函数进
>
> 坑 3：**接口粒度过粗（上帝接口）** → 现象：一个 `IDeviceService` 塞满读温、读压、写参、启停，改动一处牵连所有消费方；原因：违反接口隔离原则（ISP）；解决：按职责拆成 `ITemperatureReader`、`IParameterWriter` 等多个小接口，各自注入

> [!best] 最佳实践
> - **只依赖接口**：ViewModel 字段类型写 `IProductionService` 而不是 `MesProductionService`，替换实现时零改动
> - **构造函数注入优先**：依赖在对象创建时确定且只读（`readonly` 字段），不要用属性注入制造"可空依赖"
> - **组合根（Composition Root）只放启动处**：在 `App.xaml.cs` 或 `MainWindow` 构造里组装对象图，业务类不碰容器、不碰 `new` 的服务
> - **区分命名**：接口 `I` 前缀 + 能力化命名（`IProductionService`），实现类用具体对象命名（`MesProductionService`）
> - **测试替身配合**：写 `MockProductionService` 类提供固定数据，单元测试里注入它，验证 ViewModel 逻辑而非硬件

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例，点击"刷新产量"观察随机数变化；把 `MainWindow` 里 `new MesProductionService()` 改成 `new MockProductionService()`，确认"数据来源"变为"测试 Mock"且产量恒为 100
> **Lv.2 小试牛刀**：给 `IProductionService` 增加 `int GetQualifiedRate()`（合格率）方法，两个实现各自返回不同值（MES 返回 90~99，Mock 固定 95），并在界面加一个 `TextBlock` 绑定显示
> **Lv.3 融会贯通**：新增 `ILogger` 接口与 `ConsoleLogger` 实现，让 `MainViewModel` 构造函数同时接收 `IProductionService` 和 `ILogger`，每次"刷新产量"都记录一条日志
> **Lv.4 拆层挑战**：不用任何第三方容器，手写一个极简 `ServiceLocator`（内部一个 `Dictionary<Type, object>`），把服务的创建集中到 `App` 启动处统一注册——体会"组合根"与容器之间的关系
