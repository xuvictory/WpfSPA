# 设备管理与采集调度

> [!plain] 白话理解
> 一条产线上有 3 台 PLC（上料、装配、包装），上位机不可能同时跟它们"打电话"——串口/单 TCP 连接同一时刻只能和一台设备通信。于是采用**轮询调度**：调度器像"保安巡岗"一样，每秒走到 1 号岗亭问数据，下一秒走到 2 号，再下一秒 3 号，周而复始，每台设备轮流被问候到。
> 示例里 `_index = (_index + 1) % _devices.Count` 就是这圈巡岗的路线，`%` 保证走完最后一台回到第一台。轮询中还顺带"体检"：随机模拟通信超时，超时的设备标成离线，界面上实时反映哪台设备掉线了。这就是工业上位机最基本的"设备管理 + 采集调度"闭环——设备多了之后，还要给每台设备配不同的轮询周期、优先级，但骨架都是这个循环。

> [!def] 官方定义
> **轮询调度**（Round-Robin Scheduling）是一种时间片分配策略：将任务按固定顺序循环分配执行，保证各任务获得均等的执行机会，常用于多设备/多站点的通信管理。工业数据采集中，主站按"设备列表 + 轮询索引"周期性遍历从站，每次采集一个或多个从站，周期与超时策略决定数据新鲜度。
> .NET 中调度实现通常依赖 `System.Windows.Threading.DispatcherTimer`（UI 线程定时器，回调无需切换线程）或 `System.Threading.Timer`（后台线程，需配合 Dispatcher 更新 UI）。官方文档见 https://learn.microsoft.com/zh-cn/dotnet/desktop/wpf/advanced/timers-overview

> [!origin] 由来背景
> 轮询调度源于计算机操作系统的进程调度理论：1960-70 年代分时系统为了让多个用户共享一台主机，提出按时间片轮流分配 CPU 的 Round-Robin 算法，保证"谁都不会饿死"。这套思路后来被工业总线继承——RS-485 是半双工共享总线，同一时刻只允许一台设备说话，主站必须轮流点名，轮询顺序、周期、超时就成了通信调度器（如 MODBUS 主站）的核心设计。
> 上位机项目里"设备管理"随之成型：设备不再是一个串口，而是一个带名字、IP、轮询周期的实体对象；调度器负责在多个实体间公平分配采集时间，并维护每台设备的在线状态。本篇示例把这个最小模型跑通，后续「通信管理与-oee-计算」「scada-系统架构」中的大规模轮询、分级调度都是它的扩展。

> [!essentials] 核心要点
> - **设备实体化**：每台设备是 `Device` 对象（Name/Online/通信参数），而非零散字符串，便于增删与状态维护
> - **轮询循环**：`_index = (_index + 1) % _devices.Count` 实现 Round-Robin 公平调度，一轮走遍所有设备
> - **超时模拟**：用随机数模拟偶发通信超时，验证离线状态下的 UI 反馈与后续重试逻辑
> - **状态即时反馈**：当前轮询设备、采集值/超时提示、列表在线状态三处同步刷新，操作工一眼可知现场情况
> - **启停控制**：开始/停止按钮通过 `_timer.IsEnabled` 控制调度开关，避免重复启动叠加 Tick

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Collections.Generic;
> using System.Windows;
> using System.Windows.Media;
> using System.Windows.Threading;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         // 设备实体：实际项目中还包含 IP / 串口号 / 轮询周期等通信参数
>         private class Device
>         {
>             public string Name { get; set; }
>             public bool Online { get; set; }
>         }
>
>         private readonly List<Device> _devices = new List<Device>
>         {
>             new Device { Name = "PLC-1 上料线", Online = true },
>             new Device { Name = "PLC-2 装配线", Online = true },
>             new Device { Name = "PLC-3 包装线", Online = true }
>         };
>         private readonly DispatcherTimer _timer = new DispatcherTimer();
>         private readonly Random _rand = new Random();
>         private int _index, _pollCount;
>
>         public MainWindow()
>         {
>             InitializeComponent();
>             _timer.Interval = TimeSpan.FromSeconds(1);
>             _timer.Tick += OnPoll;
>             RefreshDeviceList();
>         }
>
>         private void OnToggle(object sender, RoutedEventArgs e)
>         {
>             if (_timer.IsEnabled) { _timer.Stop(); ToggleBtn.Content = "开始调度"; }
>             else { _timer.Start(); ToggleBtn.Content = "停止调度"; }
>         }
>
>         // 轮询调度核心：每次切换下一台设备采集，把 CPU/时间片均匀分给各设备
>         private void OnPoll(object sender, EventArgs e)
>         {
>             _index = (_index + 1) % _devices.Count;
>             Device dev = _devices[_index];
>             dev.Online = _rand.Next(10) < 8; // 模拟：偶尔通信超时脱机
>             double value = 100 + _rand.NextDouble() * 500;
>
>             CurDeviceText.Text = dev.Name;
>             CurValueText.Text = dev.Online ? $"采集值 {value:F1}" : "通信超时！";
>             CurValueText.Foreground = dev.Online ? Brushes.LimeGreen : Brushes.OrangeRed;
>
>             RefreshDeviceList();
>             _pollCount++;
>             PollCountText.Text = $"已轮询 {_pollCount} 次";
>         }
>
>         private void RefreshDeviceList()
>         {
>             DeviceList.Items.Clear();
>             foreach (var d in _devices)
>                 DeviceList.Items.Add($"{d.Name}  {(d.Online ? "● 在线" : "○ 离线")}");
>         }
>     }
> }
> ```

> [!scene] 适用场景
> ✅ 多条产线/多台设备轮询：一条串口或 TCP 连接带多台从站，用 Round-Robin 依次采集，公平且简单
> ✅ 设备在线监测：实时维护每台设备的在线/离线状态，离线自动标记并提示
> ✅ 不同优先级场景的扩展：给设备加权重或独立轮询周期（如核心设备 200ms、普通设备 1s），仍是同一条循环
> ✅ 大规模设备接入（SCADA/中控）：数千点位的轮询分片、分组调度，见「scada-系统架构」
> ❌ 单台设备单连接：不需要调度器，直接周期读即可，调度反而多余
> ❌ 高实时性设备（运动控制、视觉触发）：轮询延迟不可控，应改用中断/事件驱动（见 14.6 运动控制章节）

> [!pitfall] 常见踩坑
> 坑 1：**轮询周期与设备数量失配** → 设备多、周期短，数据还没回来下一轮又开始了，队列堆积、数据混乱 → 轮询周期 ≥ 设备数 × 单次采集耗时，实测余量，必要时分组轮询
>
> 坑 2：**某台设备长时间无响应阻塞整条循环** → 一台 PLC 掉线，后面所有设备跟着一起停更 → 每次采集必须带超时（如 500ms），超时即跳过并标记离线，不能让单点故障拖垮全局
>
> 坑 3：**离线设备反复"重试轰炸"** → 设备掉线后每轮都发请求，浪费带宽又刷屏日志 → 离线设备降级为"慢速重连"（如每 30 秒探一次），在线恢复再回到正常轮询
>
> 坑 4：**设备列表在轮询中被修改**（新增/删除设备时并发问题）→ 列表遍历出错或越界 → 增删设备走统一入口并加锁，或采用快照遍历

> [!best] 最佳实践
> - 设备对象带齐通信参数（IP/端口/站号/周期/超时），设备管理就是"配置驱动的增删改查"
> - 轮询与 UI 分离：调度器负责"问"，界面负责"看"，数据通过事件/回调分发，界面只消费结果
> - 用 `DispatcherTimer` 做 UI 侧轮询演示，真实项目多设备并发用 `Task`/`SemaphoreSlim` 控制并发上限（RS-485 半双工只允许一路在途请求）
> - 为每台设备维护独立的"连续失败计数"，超过阈值判定离线并触发告警（与「报警功能与历史数据」联动）
> - 轮询统计（总次数、成功/失败率）暴露到界面，现场评估调度是否健康

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例，观察轮询设备名每秒切换、偶尔出现"通信超时"红色提示、设备列表状态实时变化
> **Lv.2 小试牛刀**：给 `Device` 增加 `PollInterval` 字段，让 PLC-2 每 2 秒才轮询一次（其余每秒），实现差异化周期
> **Lv.3 融会贯通**：把"连续 3 次超时判离线、离线后每 30 秒才重试"的规则补进 `OnPoll`，并在日志区输出每次状态变化
> **Lv.4 挑战**：把轮询调度重构为独立类 `PollScheduler`（线程安全），接入「modbus-通信层封装」的真实读写，用 `Task.Delay` + `CancellationToken` 实现后台轮询，UI 只通过事件接收结果
