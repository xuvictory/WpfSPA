# 系统架构设计

> [!plain] 白话理解
> 一个产线监控平台要干的活其实就三件：从设备把数据拿回来（数据层）、把原始数据加工成有意义的信息（业务层）、把信息画到屏幕上给人看（UI 层）。系统架构设计就是给这三件事"分办公室"——谁负责干活、谁负责传话、谁负责展示，责任边界划得清清楚楚。
> 示例点一下按钮，你就能"看见"数据从底层往上走：数据层读出原始值 458（PLC 里的原始寄存器值），业务层把它换算成 45.8℃ 并判断"超没超 28"，UI 层最终把结果画出来。每一层只做自己的事：数据层不知道温度是给谁看的，UI 层不知道 458 是怎么读出来的。这样以后换通讯协议、改界面风格，都只动一层，不牵连全盘——这就是分层架构的价值。

> [!def] 官方定义
> **分层架构**（Layered Architecture）是软件体系结构中最经典的风格：将系统按职责划分为**表示层**（Presentation，UI/View）、**业务逻辑层**（Business/Service）与**数据访问层**（Data Access，通信/持久化），层间遵循**单向依赖**（上层依赖下层，下层不反向依赖上层），同层内部通过接口交互，从而获得可维护性、可测试性与可替换性。
> 微软对 .NET 分层/清洁架构的工程建议见 https://learn.microsoft.com/zh-cn/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures ；分层理念在 WPF 侧的落地即 MVVM（见第 7 章）。

> [!origin] 由来背景
> 分层架构的思想可追溯到 1970 年代 IBM 的"分层系统结构"研究与 Dijkstra 对"关注点分离"（Separation of Concerns）的倡导：复杂系统按抽象层次组织，每层只关心本层职责。1990 年代企业应用爆发后，Martin Fowler 的《企业应用架构模式》（2002）将"三层架构"（表现层/领域层/数据源层）固化为主流实践，随后各语言生态皆以此组织大型项目。
> 上位机软件早期常是"一个窗体全搞定"：串口代码、换算逻辑、界面刷新全挤在事件里，项目一大就难以维护。分层架构把"采集-处理-展示"切成三个可独立演进的层次，这也是本系列所有项目（温湿度、Modbus 看板、WMS、SCADA）的统一骨架。本篇用可视化的三层图让你一次看懂数据流走向。

> [!essentials] 核心要点
> - **职责三分**：数据层只负责"读寄存器/读写数据库"，业务层只做"换算、判定、计算"，UI 层只负责"展示与交互"
> - **单向依赖**：UI → 业务 → 数据，箭头只向下；数据层绝不引用 UI 类型，保证上层可替换
> - **数据流路径**：原始值（寄存器）→ 量程换算（业务）→ 展示（UI），示例用三步日志直观呈现
> - **换算集中**：`raw * 0.1` 这类系数只在业务层出现，UI 永远消费"工程值"而非"原始值"
> - **可测试性**：业务层独立成类后可脱离界面做单元测试（如换算与报警判定），这是分层的最大红利

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Windows;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         public MainWindow() => InitializeComponent();
>
>         // 模拟一次完整的数据流：数据层采集 → 业务层处理 → UI 层展示
>         private void OnFlow(object sender, RoutedEventArgs e)
>         {
>             // 1) 数据层：从 PLC 读取原始寄存器值

>             DataLog.Text = $"读寄存器 40001 → 原始值 {raw}";
>
>             // 2) 业务层：量程换算 + 报警判定（分层架构中独立成类，便于单元测试）
>             double temp = raw * 0.1; // 0.1℃/bit 换算
>             string alarm = temp > 28 ? "→ 触发报警" : "";
>             BizLog.Text = $"量程换算 → {temp:F1} ℃{alarm}";
>
>             // 3) UI 层：刷新界面显示
>             UiLog.Text = $"界面刷新：温度 {temp:F1} ℃";
>         }
>     }
> }
> ```

> [!scene] 适用场景
> ✅ 中大型上位机平台：多设备、多页面、多数据源，分层让结构清晰、可并行开发
> ✅ 团队协作开发：UI、业务、通信可分工并行，接口先定义好互不阻塞
> ✅ 长期维护与二次开发：设备升级换协议、界面改版时只动对应层，风险可控
> ✅ 需要单元测试的工程：换算、报警、OEE 计算等纯业务逻辑可脱离界面测试
> ❌ 几十行的小工具：为简单程序强行分层反而增加样板代码，得不偿失
> ❌ 性能极端敏感的实时控制回路：分层带来调用开销，直接驱动更合适

> [!pitfall] 常见踩坑
> 坑 1：**分层变成"伪分层"**（UI 事件里直接写读寄存器代码）→ 表面分了文件夹，实际耦合依旧，换协议仍要全盘改 → 从代码层面约束：UI 层只依赖业务接口，数据访问只能在数据层
>
> 坑 2：**依赖方向反了**（数据层引用 UI/业务类型）→ 层层倒挂，测试与替换都困难 → 坚持单向依赖，必要时用依赖注入（DI）把上层需要的服务传给下层
>
> 坑 3：**换算逻辑散落各层**（有的在 UI、有的在业务）→ 同一系数多份实现，改一处漏一处 → 量程换算、单位转换一律收进业务层，UI 只显示业务层给出的工程值
>
> 坑 4：**过度设计**（一个"Hello"也抽象接口）→ 层级和接口比业务还多，开发效率大降 → 分层粒度与项目规模匹配，先两层/三层，确有必要再抽象

> [!best] 最佳实践
> - 先画"架构图"再写代码：把三层职责、数据流方向画清楚，团队达成共识后再动手
> - 层间用接口（`IDeviceService`、`IAlarmService`）交互，便于 mock 与替换
> - 数据层封装为服务类（`ModbusService`、`HistoryRepository`），一个数据源一个类
> - 业务层的换算与判定写成纯方法（无 UI 依赖），单元测试直接覆盖
> - 每层定义"不许做什么"（如 UI 不碰串口、数据层不弹窗），比"该做什么"更防腐化
> - 演进方向：层数随复杂度增长——从三层起步，必要时增加"服务层"或"基础设施层"

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例，点"模拟数据流"观察三层日志依次点亮，理解"数据层→业务层→UI 层"的走向
> **Lv.2 小试牛刀**：修改业务层的换算系数（`0.1` 改为 `0.5`）与报警阈值（`28` 改为 `30`），观察 UI 结果与报警提示变化，体会"只改业务层"的效果
> **Lv.3 融会贯通**：在示例中新增一条"模拟写入"数据流（UI 层→业务层→数据层），方向相反，观察写入路径如何传递
> **Lv.4 挑战**：把示例重构为真正的三层工程：新建 `DataLayer`（读寄存器类）、`ServiceLayer`（换算+报警服务）、`UI`（绑定展示）三个类，业务服务支持单元测试（用已知输入断言输出），验证分层带来的可测试性
