# 报警功能与历史数据

> [!plain] 白话理解
> 报警功能就像车间的"蜂鸣警报器 + 值班日志"：温度一旦超过 28℃ 这个上限，警报器响起（徽章变红、数字变橙红），同时在日志本上记一笔"几点几分温度多少度超限"。温度回落了，再记一笔"已恢复"。值班员看到后按一下"确认报警"按钮，表示"我知道了"——这算第三笔记录。
> 这里有个关键细节叫"上升沿触发"：只有当温度从"正常"变成"超限"的那一瞬间才报警一次，而不是温度持续超限就每秒刷一条——否则一分钟日志就刷满屏了。整个逻辑围绕一个 `_alarming` 状态标志：超限且未报警→触发；回落且正报警→恢复。报警历史只追加、不删除，供事后追溯。

> [!def] 官方定义
> **报警管理**（Alarm Management）在工业领域有成熟标准：**ISA-18.2**（美国仪表学会，2009 年发布）与 **IEC 62682** 定义了报警的全生命周期——报警检测（Detection）、报警通知（Annunciation）、操作员响应/确认（Acknowledge）与恢复（Return to Normal），并强调通过**报警阈值合理化**防止"报警泛滥"（Alarm Flood）。
> 工程实现上，报警判定常用**边沿触发**（Edge-triggered）：以布尔状态标志记录当前是否处于报警态，仅在"正常→报警"上升沿与"报警→正常"下降沿产生事件，避免持续越限时重复上报。UI 反馈以颜色（红/橙）与状态文本区分，历史数据以时间戳 + 事件类型 + 数值的形式追加存储。

> [!origin] 由来背景
> 工业报警管理成为一门"学科"，源自一起著名的教训：1979 年美国三哩岛核电站事故调查发现，事故初期控制室警报器同时鸣响多达上百条，操作员被"报警淹没"（Alarm Flood），无法分辨关键信息，延误了处置。此后行业开始研究报警的合理数量与生命周期管理，最终形成 ISA-18.2 / IEC 62682 标准。
> 上位机里的报警功能正是这套理念的工程落地：阈值合理化（不设无意义的报警）、边沿触发（只报状态变化）、确认机制（操作员必须回应）、历史追溯（事后可查）。本篇示例用温度超限演示了这套最小闭环，后续 14.7 的「报警规则引擎」会把它扩展成多条件、分级、抑制的企业级规则系统。

> [!essentials] 核心要点
> - **边沿触发**：用 `_alarming` 布尔标志实现"正常→报警"上升沿触发一次，温度持续越限不重复刷屏
> - **联动反馈**：温度颜色（橙红）+ 报警徽章（红底白字）双通道提示，信息传达冗余但直观
> - **恢复判定**：温度回落后自动写"恢复"记录，报警状态归零，形成完整闭环
> - **确认机制**：操作员手动"确认报警"，历史中留下确认记录，实现 ISA-18.2 的操作员响应环节
> - **历史只追加**：报警/恢复/确认三类记录按时间戳插入列表头部，只增不删，供事后追溯

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Windows;
> using System.Windows.Media;
> using System.Windows.Threading;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         private const double AlarmLimit = 28.0; // 报警上限
>         private readonly DispatcherTimer _timer = new DispatcherTimer();
>         private readonly Random _rand = new Random();
>         private bool _alarming;
>
>         public MainWindow()
>         {
>             InitializeComponent();
>             _timer.Interval = TimeSpan.FromSeconds(1);
>             _timer.Tick += OnTick;
>         }
>
>         private void OnToggle(object sender, RoutedEventArgs e)
>         {
>             if (_timer.IsEnabled) { _timer.Stop(); ToggleBtn.Content = "开始采集"; }
>             else { _timer.Start(); ToggleBtn.Content = "停止采集"; }
>         }
>
>         private void OnTick(object sender, EventArgs e)
>         {
>             double temp = 20 + _rand.NextDouble() * 15; // 20~35℃ 波动，可能越限
>             TempText.Text = $"{temp:F1} ℃";
>             TempText.Foreground = temp > AlarmLimit
>                 ? Brushes.OrangeRed
>                 : new SolidColorBrush(Color.FromRgb(0x58, 0xA6, 0xFF));
>
>             // 上升沿触发报警：温度越限且当前未报警 → 写入历史
>             if (temp > AlarmLimit && !_alarming)
>             {
>                 _alarming = true;
>                 SetAlarmBadge(true);
>                 AlarmList.Items.Insert(0,
>                     $"[{DateTime.Now:HH:mm:ss}] 温度 {temp:F1}℃ 超上限 {AlarmLimit}℃");
>             }
>             else if (temp <= AlarmLimit && _alarming)
>             {
>                 _alarming = false; // 温度回落后自动恢复
>                 SetAlarmBadge(false);
>                 AlarmList.Items.Insert(0, $"[{DateTime.Now:HH:mm:ss}] 温度恢复 {temp:F1}℃");
>             }
>         }
>
>         // 手动确认报警：仅清除当前报警状态，历史记录保留供事后追溯
>         private void OnAck(object sender, RoutedEventArgs e)
>         {
>             if (!_alarming) return;
>             _alarming = false;
>             SetAlarmBadge(false);
>             AlarmList.Items.Insert(0, $"[{DateTime.Now:HH:mm:ss}] 操作员确认报警");
>         }
>
>         private void SetAlarmBadge(bool on)
>         {
>             // 报警时红色底白字，正常时面板色灰字
>             AlarmBadge.Background = on
>                 ? new SolidColorBrush(Color.FromRgb(0xDA, 0x36, 0x33))
>                 : new SolidColorBrush(Color.FromRgb(0x21, 0x26, 0x2D));
>             AlarmStateText.Text = on ? "报警" : "正常";
>             AlarmStateText.Foreground = on
>                 ? Brushes.White
>                 : new SolidColorBrush(Color.FromRgb(0x8B, 0x94, 0x9E));
>         }
>     }
> }
> ```

> [!scene] 适用场景
> ✅ 温湿度/压力等模拟量超限报警：阈值越限的检测、颜色反馈与记录，是现场最常见的报警形态
> ✅ 需要"报警→确认→恢复"闭环的生产环境：操作员确认机制满足企业安全管理（ISA-18.2）要求
> ✅ 报警历史追溯：交接班、事故调查时查看"几点几分发生了什么、谁确认过"
> ✅ 多级报警提示：与「报警规则引擎」配合升级为多通道、分级报警
> ❌ 极简的一次性工具：只有显示没有报警需求的调试工具，加报警逻辑反而增加复杂度
> ❌ 报警项极多的复杂系统（上千条报警）：单靠阈值 + 列表撑不住，需要优先级、抑制、去抖等规则管理

> [!pitfall] 常见踩坑
> 坑 1：**没有边沿触发，持续越限每秒刷一条** → 温度超限 5 分钟日志就刷出 300 条，真正的关键记录被淹没 → 用 `_alarming` 标志只在上升沿/下降沿记一条，或加"最小重复间隔"去抖
>
> 坑 2：**确认按钮与自动恢复逻辑冲突** → 操作员刚确认，下一秒温度仍超限又自动触发一条新报警，操作员觉得"确认了也没用" → 明确语义：确认只清"待确认"状态，数据是否越限由采集独立判定，两者职责分开
>
> 坑 3：**历史列表无限增长** → 运行一个月内存被报警记录占满 → 列表设上限（如最近 1000 条），长期保存交给数据库（见「历史趋势与报表」的持久化思路）
>
> 坑 4：**阈值写死且不合理**（28℃ 但工艺允许 30℃）→ 天天误报警，操作员最终无视所有报警 → 阈值做成可配置并走"阈值合理化"评审，宁可少而准，不可多而滥

> [!best] 最佳实践
> - 报警状态用"正常/报警/已确认"三态建模，比裸布尔更接近真实场景（可升级为枚举状态机，见「设备状态机设计」）
> - 历史记录统一格式 `时间戳 + 事件类型 + 数值/说明`，便于排序、筛选与后期入库
> - 报警反馈至少双通道：颜色 + 文字/图标，兼顾色弱与盲区视角
> - 阈值、报警文案等配置集中定义，不散落各方法；生产环境由配置文件下发
> - 演示/教学程序标注"模拟数据"，正式报警功能必须经现场验证阈值合理性后再上线

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例，观察温度超过 28℃ 时徽章变红、历史插入报警记录，回落后自动恢复，点"确认报警"生成确认记录
> **Lv.2 小试牛刀**：新增湿度报警通道：湿度超 60%RH 时独立触发，徽章/文字提示增加"湿度"标识
> **Lv.3 融会贯通**：把报警阈值 28.0 改为界面可配置（TextBox 绑定），改阈值后立即生效，并给报警记录加上阈值字段（`超上限 {alarmLimit}℃`）
> **Lv.4 挑战**：引入 `AlarmState` 枚举（Normal/Alarm/Acknowledged）状态机重构判定逻辑，并把报警历史持久化到 SQLite（`System.Data.SQLite` 或 EF Core），重启程序后历史仍可查询
