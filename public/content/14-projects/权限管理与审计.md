# 权限管理与审计

> [!plain] 白话理解
> 车间系统不能人人全权限：操作员只要"看数据"，工程师能"改报警阈值"，只有管理员才能"下发控制指令、管理用户"。权限管理就是给每个人发一张"通行证"——登录时选择角色，系统按权限矩阵决定每个按钮能不能点：操作员登录，"修改报警阈值"等按钮全部置灰不可点；管理员登录，全部可点。
> 审计则是"监控录像"：谁、在什么时间、做了什么操作，全部记进日志。示例里切换角色本身记一条"操作员 → 登录"，点任何按钮也记一条"管理员 → 下发控制指令"——因为所有操作都走同一个 `OnOp` 入口统一记录。这样出问题时能回答"谁干的、什么时候、干了什么"，这就是合规审计的意义。

> [!def] 官方定义
> **访问控制**（Access Control）是信息安全的核心机制，经典模型有 **RBAC**（Role-Based Access Control，基于角色的访问控制，1992 年由 Ferraiolo & Kuhn 提出）：用户（User）分配角色（Role），角色授予权限（Permission），权限决定对资源的操作。**权限矩阵**（Access Matrix）用"角色 × 操作"二维表描述授权关系。
> **审计日志**（Audit Trail）按时间顺序记录系统内的关键操作（登录、配置修改、控制指令），要求**不可否认**（Non-repudiation）：记录含操作者、时间、动作、结果，供事后追溯与合规检查。工业系统相关标准：IEC 62443（工业网络安全）与 FDA 21 CFR Part 11（电子记录与签名）。

> [!origin] 由来背景
> 访问控制的思想可追溯到 1970 年代美国军方/政府的多级安全模型（Bell-LaPadula，1973），1980-90 年代 RBAC 规范化（NIST 1992 年提出标准模型），成为企业系统的标准做法。工业界则因两件事推进权限管理：一是 21 世纪初"震网病毒"（Stuxnet，2010 年）等安全事件暴露了工控系统"无权限、无审计"的隐患；二是 IEC 62443 等标准明确要求"最小权限 + 操作可审计"。
> SCADA 系统因此必须回答三个问题：谁能看？（查看权限）、谁能改？（配置权限）、谁能控制？（操作权限）。操作员/工程师/管理员三级角色是工业现场的常见划分。本篇示例用"权限矩阵 + 统一操作入口 + 审计日志"三件套实现了最小合规闭环——升级为真实系统时，角色权限存数据库、登录用账户密码、审计日志写历史库即可。

> [!essentials] 核心要点
> - **角色权限矩阵**：操作员仅查看 / 工程师可改阈值 / 管理员全权限，一行代码一条授权规则
> - **按钮级控制**：`IsEnabled` 按角色开关，无权限按钮统一深色置灰，可用/禁用一眼可辨
> - **统一操作入口**：所有功能按钮共用 `OnOp` 处理器，审计记录集中产生，不漏记任何操作
> - **审计日志**：`时间 + 用户 + 动作` 格式入库/上屏，登录与操作都留痕
> - **最小权限原则**：默认禁用、按需放开，而不是默认全开再收紧（安全基线不同）

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Windows;
> using System.Windows.Controls;
> using System.Windows.Media;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         public MainWindow()
>         {
>             InitializeComponent();
>             RoleBox.SelectedIndex = 0;
>         }
>
>         // 切换角色：按权限矩阵启用/禁用按钮，并记录审计
>         private void OnRoleChanged(object sender, SelectionChangedEventArgs e)
>         {
>             string role = (RoleBox.SelectedItem as ComboBoxItem)?.Content.ToString();
>             CurrentUserText.Text = $"当前用户：{role}";
>             ApplyPermission(role);
>             Audit(role, "登录");
>         }
>
>         // 权限矩阵：管理员全开 / 工程师除用户管理外全开 / 操作员仅查看
>         private void ApplyPermission(string role)
>         {
>             BtnView.IsEnabled = true;
>             BtnAlarm.IsEnabled = role != "操作员";
>             BtnControl.IsEnabled = role == "管理员";
>             BtnAdmin.IsEnabled = role == "管理员";
>
>             // 无权限按钮统一加深置灰，直观区分可用/禁用
>             foreach (var btn in new[] { BtnView, BtnAlarm, BtnControl, BtnAdmin })
>                 btn.Background = new SolidColorBrush(Color.FromRgb(
>                     btn.IsEnabled ? (byte)0x21 : (byte)0x18,
>                     btn.IsEnabled ? (byte)0x26 : (byte)0x1B,
>                     btn.IsEnabled ? (byte)0x2D : (byte)0x20));
>         }
>
>         // 操作统一入口：任何功能操作都先记录审计日志
>         private void OnOp(object sender, RoutedEventArgs e)
>         {
>             string op = ((Button)sender).Content.ToString();
>             string role = (RoleBox.SelectedItem as ComboBoxItem)?.Content.ToString();
>             Audit(role, op);
>         }
>
>         private void Audit(string user, string action)
>         {
>             AuditList.Items.Insert(0, $"[{DateTime.Now:HH:mm:ss}] {user} → {action}");
>         }
>     }
> }
> ```

> [!scene] 适用场景
> ✅ 中控室多角色系统：操作员/工程师/管理员分工明确，防止越权操作
> ✅ 合规要求严格的行业：医药（21 CFR Part 11）、电力、化工要求操作可追溯、权限受控
> ✅ 关键设备控制：控制指令（启动/停机/参数下发）必须管理员/授权工程师才能执行
> ✅ 审计追溯：事故/误操作复盘时查"谁改过参数、谁下过指令"
> ❌ 单人使用的内部工具：没有多角色区分，权限与审计是负担
> ❌ 纯展示无操作的系统：只读大屏（见「大屏可视化看板」）不需要权限矩阵，登录反而碍事

> [!pitfall] 常见踩坑
> 坑 1：**只有界面禁用、没有后端校验** → 绕过 UI（改代码/调接口）依然能执行越权操作 → 权限校验放在服务/命令层（`CanExecute` 或服务端鉴权），按钮禁用只是体验层
>
> 坑 2：**审计只记成功操作** → 越权尝试不落日志，出了事无从追查 → 登录、切换角色、操作（含被拒操作）全部记录，记录含操作者/时间/动作/结果
>
> 坑 3：**角色写死在逻辑各处**（`if (role == "管理员")` 散落 N 处）→ 加角色、改权限要全局搜索改代码 → 权限矩阵集中定义（字典/配置），统一入口查询，加角色只加一行矩阵
>
> 坑 4：**审计日志不持久化** → 程序重启日志全丢，审计形同虚设 → 日志写入数据库/文件（见「需求与数据库设计」），界面只展示最近 N 条

> [!best] 最佳实践
> - 权限模型用 RBAC 三件套：用户 → 角色 → 权限，权限矩阵（角色 × 操作）集中管理
> - 权限控制"服务端强制、界面配合"：命令用 `ICommand.CanExecute` 控制可用性，逻辑层再校验一次
> - 审计日志统一格式 `时间戳 + 用户 + 角色 + 动作 + 结果`，写历史库供「历史趋势与报表」查
> - 默认最小权限：新角色默认无权限，按需逐项放开；管理员也分级（超管/普通管理员）
> - 按钮置灰用统一样式（`IsEnabled=false` + 深色），避免"可用但无反应"的困惑
> - 演示环境标注"模拟登录"，正式系统用账户密码 + 会话超时（见「安全与权限」相关章节）

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例，切换三种角色观察按钮可用性变化（操作员仅"查看"可点）、审计日志逐条增加
> **Lv.2 小试牛刀**：新增第四种角色"维护员"（可查看 + 可下发控制，不可改阈值、不可用户管理），扩展权限矩阵
> **Lv.3 融会贯通**：把"角色 → 权限"从 `if/else` 改为权限字典（`Dictionary<string, bool[]>` 或 `Dictionary<string, List<string>>`），切换角色只查字典
> **Lv.4 挑战**：审计日志持久化到 SQLite（`AuditLog` 表：时间/用户/动作），并增加"登录密码验证"（模拟账号密码登录而非直接选角色）；再用 `ICommand` + `CanExecute` 把按钮可用性与权限绑定，实现"命令级权限控制"
