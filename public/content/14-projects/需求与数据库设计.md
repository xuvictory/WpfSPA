# 需求与数据库设计

> [!plain] 白话理解
> WMS（仓库管理系统）的核心就是三本"账本"：货品目录账（货品表，记每个货品的编号、名称、条码）、库位地图账（库位表，记仓库里每个格子叫什么、在哪排）、出入库流水账（记录表，记"几点几分、哪个货品、从哪个库位、进/出、多少件"）。
> 关键设计是：流水账里**不直接写字**（如"苹果"），只写货品表的编号（`GOODS_ID=3`）。要看名字时"翻目录"联表查询（JOIN）。这样改个货品名只改目录一处，流水账不用动——这就是外键 + JOIN 的意义：不重复存储、不产生脏数据。示例里点"查询出入库记录"，DataGrid 显示的就是流水账 JOIN 货品表、库位表后拼出来的完整视图。

> [!def] 官方定义
> **数据库设计**（Database Design）指从业务需求出发，确定实体、属性、关系并最终形成表结构的过程，核心产物是**ER 模型**（Entity-Relationship Model）与建表 DDL。关键概念：
> - **主键（Primary Key）**：唯一标识一行记录，如 `T_Goods.Id`；
> - **外键（Foreign Key）**：引用另一张表主键的列，如 `T_Record.GOODS_ID → T_Goods.Id`，体现表间关联；
> - **JOIN**：SQL 联表查询，`INNER JOIN` 按外键把多表行拼接成完整视图；
> - **范式**（以 3NF 为目标）：消除重复数据与传递依赖，避免更新异常。
> 关系模型理论奠基论文为 E.F.Codd 1970 年《A Relational Model of Data for Large Shared Data Banks》。

> [!origin] 由来背景
> 关系型数据库的理论源自 1970 年：IBM 的 E.F.Codd 发表《A Relational Model of Data for Large Shared Data Banks》，首次用数学化的"关系"（表）描述数据，奠定关系模型；1976 年 Peter Chen 提出 **ER 模型**（实体-联系图）用于概念设计；随后范式理论（1NF→2NF→3NF→BCNF）让"如何避免冗余与异常"有了系统方法。商用产品随之崛起（Oracle 1979、SQL Server 1989、MySQL 1995）。
> 上位机软件早期习惯把数据写进本地文件（INI/CSV），但仓库管理这类系统需要"多表关联、事务、并发、查询统计"，关系数据库才是正确工具。WMS 作为 MES/ERP 的组成部分，其核心就是围绕"货品-库位-流水"的关系建模。本篇示例用内存数据表 + DataGrid 演示了这套设计，把表换成 SQLite/SQL Server 即成为真实系统（见「轻量级数据库-sqlite」）。

> [!essentials] 核心要点
> - **实体拆分**：货品/库位/出入库记录拆成三张独立表，各表职责单一，符合 3NF
> - **主键唯一**：每表设主键（`Id`），货品与库位以编码为主键值，保证唯一性与引用稳定性
> - **外键关联**：记录表用 `GOODS_ID`/`BIN_ID` 外键引用货品/库位，**不重复存储名称**，杜绝"改了名字旧记录还显示旧名"的脏数据
> - **JOIN 组装视图**：查询时 `INNER JOIN` 把编号翻译成名称，DataGrid 展示的是拼接后的完整记录
> - **字段语义明确**：数量用数值类型、记录类型用枚举（入库/出库/移位）、时间用 DateTime，为统计与报表铺路

> [!scene] 适用场景
> ✅ 需要持久化与查询的系统：出入库台账、库存盘点、报表统计，数据要长期保存并可追溯
> ✅ 多表关联的业务：货品-库位-流水、订单-明细-客户，关系模型天然表达
> ✅ 多用户/多终端：仓库扫码枪、上位机、管理端共享同一数据库，靠事务与锁保证一致
> ✅ WMS/MES/ERP 集成：库存数据要向上游系统开放，关系库是行业标准
> ❌ 纯实时监控不存历史：如实时曲线、瞬时状态展示，不需要数据库（见「实时曲线与仪表盘」）
> ❌ 超高频写入的时序数据（每秒上万条设备数据）：关系库写入瓶颈明显，用时序库（见「时序数据库简介」）

> [!pitfall] 常见踩坑
> 坑 1：**流水表里直接存货品名称**（违反范式）→ 货品改名后历史记录全部对不上，出现"表里有两个名字" → 记录表只存 `GOODS_ID` 外键，名称一律 JOIN 货品表获取
>
> 坑 2：**外键不建、数据随意删** → 删掉货品行后流水变成"孤儿记录"，统计对不上 → 建立外键约束（级联策略明确），删除前先检查引用
>
> 坑 3：**ID 语义混乱**（自增主键与业务编码混用）→ 界面显示的数字 ID 与条码、货品编号对不上 → 主键统一自增 `Id`，业务编码（条码、库位码）单独建唯一索引字段
>
> 坑 4：**演示用内存表、上线改真库却结构不同** → 示例能跑，接 SQLite 后查询报错 → 先用内存 `DataTable` 设计好表结构并写清建表 DDL，换库时表结构保持一致

> [!best] 最佳实践
> - 先画 ER 图再建表：把实体、属性、关系（1:N）画清楚，评审通过后再写 DDL
> - 主键用自增 `Id`，业务编码（货品条码、库位码）单独字段 + 唯一索引，二者职责分离
> - 记录表只存外键与数量，一切名称、单位通过 JOIN 获取，从根上杜绝数据冗余
> - 数量/金额字段用 `decimal`（`double` 有浮点误差），时间统一 `DateTime`，编码统一小写/大写规范
> - 数据访问层用 `DataTable` 或 ORM（EF Core/Dapper）封装，SQL 字符串不散落在 UI 事件里
> - 真实部署选型：单机用 SQLite（见「轻量级数据库-sqlite」）、多终端用 SQL Server/MySQL（见「关系型数据库sql-servermysql」）

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例，点"查询出入库记录"看 JOIN 后完整视图，观察三张表的字段如何拼成一行
> **Lv.2 小试牛刀**：给 `T_Bin` 增加"容量"字段（如 500 件）、给 `T_Record` 增加"操作人"字段，并在 DataGrid 中展示
> **Lv.3 融会贯通**：把三张内存表落成真实 SQLite 库（`Microsoft.Data.Sqlite`）：建表、插数据、用 `INNER JOIN` 查询并绑定 DataGrid，验证与内存版结果一致
> **Lv.4 挑战**：扩展 ER 模型：新增"供应商"表并与货品关联（多对多需中间表），实现"某供应商所有货品的出入库明细"联表查询；再为出库增加"扣减库存"的数据库事务（`BeginTransaction`）
