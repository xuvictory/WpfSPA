# 报警规则引擎

> [!plain] 白话理解
> 现场有几十上百个点位，每个点位的报警条件各不相同（温度超 80、压力超 6、液位低于 10）。如果每个判断都写死在界面代码里，加一条规则就要改代码、重新编译。**报警规则引擎**把这些条件变成可配置的"规则"，引擎每秒取点位值、逐条匹配规则，谁越限谁报警——规则可以随时增删，代码一行不用动。
> 示例把规则做成 `AlarmRule` 对象（名字 + 判定函数 `v => v > 80`），三条件轮流模拟数据，引擎自动匹配、越限亮红徽章并记入历史，回落自动恢复。这比「报警功能与历史数据」更进一步：那里是"一个阈值写死"，这里是"N 条规则统一驱动"——规则的增加不再靠改代码，而是往列表里加一条，这就是"引擎"与"硬编码"的本质区别。

> [!def] 官方定义
> **规则引擎**（Rule Engine）是将业务规则从程序代码中解耦、以数据（规则集）形式驱动逻辑执行的软件组件，经典实现模式有**生产规则系统**（如 Drools）与简单阈值规则。工业报警引擎是规则引擎在 SCADA 的应用：规则 = 条件（Condition）+ 动作（Action），引擎周期评估条件并执行动作（触发报警/恢复/通知）。
> 示例用 `Func<double, bool>` 作为规则条件载体，`_rules` 列表即规则集；引擎主循环 `OnEvaluate` 依次匹配，配合**边沿检测**（`_alarming` 标志）只在"正常→报警"与"报警→正常"时产生事件。报警管理标准 ISA-18.2/IEC 62682 见第 14 章「报警功能与历史数据」中说明。

> [!origin] 由来背景
> 规则引擎的思想源于 1970-80 年代专家系统：Rete 算法（Charles Forgy，1979）让"规则高效匹配"成为可能，商业产品（CLIPS、JBoss Rules）随之出现。工业报警领域则因 1979 年三哩岛事故的"报警淹没"教训（见「报警功能与历史数据」），开始把报警"条件"从代码中抽出来管理：阈值、优先级、死区、延迟、抑制都做成配置，由统一引擎评估——这就是"报警规则引擎"的由来。
> 它的工程价值在于"变更成本"：传统报警改一个阈值要发版，规则引擎改一条配置即可，且规则可统计、可审计、可批量导入导出。示例用 `Func<double,bool>` 实现最小规则模型，规则存为数据（列表）而不是代码分支，正是这一思想的雏形；生产系统还会加死区、延迟确认、优先级分级（ISA-18.2 推荐模型）。

> [!essentials] 核心要点
> - **规则数据化**：`AlarmRule`（名称 + `Func<double,bool>` 判定）存于规则列表，增删规则不改引擎代码
> - **引擎主循环**：定时 `OnEvaluate` 取点位值，依次把值送入所有规则匹配（`IsTriggered(value)`）
> - **边沿检测**：`_alarming` 标志实现上升沿（触发）/下降沿（恢复），越限不重复刷屏
> - **点位轮询**：`_ruleIndex` 循环轮转模拟多点位数据，规则与数据一一对应可扩展
> - **报警历史**：触发/恢复事件带时间戳插入历史列表，事后可追溯（升级版见「历史趋势与报表」）

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Collections.Generic;
> using System.Windows;
> using System.Windows.Media;
> using System.Windows.Threading;
>
> namespace HmiDemo
> {
>     // 报警规则：名称 + 判定条件（实际项目规则可在组态界面增删改）
>     public class AlarmRule
>     {
>         public string Name { get; set; }
>         public Func<double, bool> IsTriggered { get; set; }
>         public override string ToString() => Name;
>     }
>
>     public partial class MainWindow : Window
>     {
>         private readonly DispatcherTimer _timer = new DispatcherTimer();
>         private readonly Random _rand = new Random();
>         private readonly List<AlarmRule> _rules = new List<AlarmRule>
>         {
>             new AlarmRule { Name = "反应釜温度 > 80 ℃", IsTriggered = v => v > 80 },
>             new AlarmRule { Name = "管道压力 > 6 MPa",  IsTriggered = v => v > 6 },
>             new AlarmRule { Name = "液位 < 10 %",        IsTriggered = v => v < 10 }
>         };
>         private int _ruleIndex;
>         private bool _alarming;
>
>         public MainWindow()
>         {
>             InitializeComponent();
>             foreach (var r in _rules) RuleList.Items.Add(r);
>             _timer.Interval = TimeSpan.FromSeconds(1);
>             _timer.Tick += OnEvaluate;
>         }
>
>         private void OnToggle(object sender, RoutedEventArgs e)
>         {
>             if (_timer.IsEnabled) { _timer.Stop(); ToggleBtn.Content = "启动规则引擎"; }
>             else { _timer.Start(); ToggleBtn.Content = "停止规则引擎"; }
>         }
>
>         // 引擎主循环：取一个点位值，依次送入所有规则匹配
>         private void OnEvaluate(object sender, EventArgs e)
>         {
>             _ruleIndex = (_ruleIndex + 1) % _rules.Count;
>             // 模拟点位值在规则阈值附近波动
>             double value = _ruleIndex switch
>             {
>                 0 => 75 + _rand.NextDouble() * 10, // 温度 75~85
>                 1 => 5.5 + _rand.NextDouble() * 2, // 压力 5.5~7.5
>                 _ => 8 + _rand.NextDouble() * 8     // 液位 8~16
>             };
>             TagValueText.Text = $"{value:F1}";
>
>             var rule = _rules[_ruleIndex];
>             bool triggered = rule.IsTriggered(value);
>             // 上升沿触发：越限且当前未报警 → 记一条；回落 → 记恢复
>             if (triggered && !_alarming)
>             {
>                 _alarming = true;
>                 SetAlarm(true);
>                 AlarmHistory.Items.Insert(0,
>                     $"[{DateTime.Now:HH:mm:ss}] {rule.Name} → 触发（当前 {value:F1}）");
>             }
>             else if (!triggered && _alarming)
>             {
>                 _alarming = false;
>                 SetAlarm(false);
>                 AlarmHistory.Items.Insert(0,
>                     $"[{DateTime.Now:HH:mm:ss}] {rule.Name} → 恢复");
>             }
>         }
>
>         private void SetAlarm(bool on)
>         {
>             AlarmBadge.Background = on
>                 ? new SolidColorBrush(Color.FromRgb(0xDA, 0x36, 0x33))
>                 : new SolidColorBrush(Color.FromRgb(0x21, 0x26, 0x2D));
>             AlarmStateText.Text = on ? "报警" : "正常";
>             AlarmStateText.Foreground = on
>                 ? Brushes.White
>                 : new SolidColorBrush(Color.FromRgb(0x8B, 0x94, 0x9E));
>         }
>     }
> }
> ```

> [!scene] 适用场景
> ✅ 多条件报警管理：几十上百条阈值/条件规则统一评估，规则集中维护
> ✅ 报警规则需频繁调整的现场：改阈值、加规则走配置，不改代码不重启
> ✅ 与 SCADA 点位联动：规则绑定实时库点位（见「scada-系统架构」），点位值变化自动触发评估
> ✅ 分级报警与抑制：引擎可扩展优先级、死区、延迟确认，满足 ISA-18.2 报警管理要求
> ❌ 单点阈值固定的小项目：直接用「报警功能与历史数据」的硬编码即可，引擎是过度设计
> ❌ 规则数量少且长期不变：配置化反而增加抽象成本，权衡"变更频率 × 规则数量"

> [!pitfall] 常见踩坑
> 坑 1：**没有边沿检测，越限每秒刷屏** → 温度超限一分钟历史几百条，真正的关键记录被淹没 → 用 `_alarming` 标志只在上升沿/下降沿记一条（与「报警功能与历史数据」同坑，务必复用该思路）
>
> 坑 2：**规则与点位绑定错位**（规则 A 的数据喂给规则 B）→ 温度规则显示"压力超限"，现场误导 → 规则对象自带点位标识（`AlarmRule.PointTag`），引擎按点位路由数据，不靠索引硬编码
>
> 坑 3：**规则边界值语义不清**（`>` 还是 `>=`，死区多大）→ 临界抖动导致报警频繁触发/恢复 → 明确定义比较方向与死区（如触发 80、恢复 78），边界用测试用例固定
>
> 坑 4：**报警历史不落库** → 程序重启历史全丢，事故追溯无据可查 → 触发/恢复事件写入数据库（见「需求与数据库设计」），界面只展示最近 N 条

> [!best] 最佳实践
> - 规则配置化（XML/JSON/数据库），引擎只做"评估 + 动作"，规则不写死在代码里
> - 规则模型包含：点位、条件、优先级、死区、延迟、抑制组（ISA-18.2 建议字段），示例的 `AlarmRule` 是最小雏形
> - 边沿检测 + 时间戳：触发/恢复/确认三类事件齐全，历史可完整还原现场时序
> - 规则评估与 UI 分离：引擎是纯逻辑（可单测），界面订阅事件刷新徽章与历史
> - 引擎评估频率与数据源匹配：点位更新才评估（事件驱动）优于固定轮询（省 CPU、响应快）
> - 报警历史持久化到历史库，与「历史趋势与报表」联动生成报警统计

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例，观察三个规则轮流评估、温度/压力越限亮红并写历史、回落恢复绿字"正常"
> **Lv.2 小试牛刀**：新增第 4 条规则"转速 > 3000 r/min"，并在轮转数据中加入转速点位，验证新规则自动生效
> **Lv.3 融会贯通**：给规则增加"优先级"（High/Medium/Low），历史记录显示优先级，报警徽章按最高优先级着色
> **Lv.4 挑战**：把规则集抽成配置（JSON 加载，含点位/条件/优先级/死区），引擎与 UI 解耦（事件发布触发/恢复）；再将报警事件写入 SQLite，重启后历史仍可查，并用「报警功能与历史数据」的确认机制完善闭环
