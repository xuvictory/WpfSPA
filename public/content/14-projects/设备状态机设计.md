# 设备状态机设计

> [!plain] 白话理解
> 一台设备不是随便想干嘛就干嘛的：设备没启动就不能"暂停"，设备在运行中就不能直接"启动"（会重复启动报错），只有故障了才能"复位"。状态机就是给设备行为立规矩——把"当前是什么状态、能跳到哪些状态"画成一张规则表，所有操作先查表，允许才执行，不允许就拦下来提示"非法操作"。
> 示例里点"暂停"时，如果设备还停在"停机"状态，日志会立刻提示"非法操作：暂停（Stopped → Paused 不允许）"。这张规则表用 C# 的元组模式 switch 写在一处（`(目标, 当前) switch`），一目了然。状态机的好处是：设备行为有且只有一张表来管，不会出现"某个按钮在某些状态下行为诡异"的 bug。

> [!def] 官方定义
> **有限状态机**（Finite State Machine, FSM）是计算理论中的经典模型：由有限个**状态**（State）、**事件/输入**（Event）、**状态迁移**（Transition）与**迁移条件**组成，同一时刻只处于一个状态，事件触发满足条件时迁移到新状态。FSM 可用状态迁移表（State Transition Table）或状态图（State Diagram，UML）描述。
> 工程上常用枚举定义状态、用模式匹配集中定义合法迁移（如 C# 的元组 `switch` 表达式），通过唯一入口 `TryTransition` 完成"校验 → 迁移 → 通知"。UML 状态机图规范见 https://www.omg.org/spec/UML/ ；C# 模式匹配见 https://learn.microsoft.com/zh-cn/dotnet/csharp/language-reference/operators/patterns

> [!origin] 由来背景
> 有限状态机理论诞生于 20 世纪中叶：1943 年 McCulloch 与 Pitts 用"神经元逻辑"论文为自动机理论奠基，1950 年代 Mealy/Moore 提出规范化的状态机模型，此后 FSM 成为数字电路设计、编译器词法分析、通信协议状态解析的理论基石。
> 工业领域更是状态机的"主战场"：IEC 61131-3 标准中的**SFC（顺序功能图）**就是 PLC 程序的状态机表达——设备从初始化、运行、暂停到故障复位，每一步迁移都受条件约束。上位机要正确反映设备状态（大屏显示"运行/暂停/故障"、控制按钮是否可用、OEE 按状态计时），就必须用同样的模型与 PLC 保持一致。本篇用枚举 + 迁移表把这个模型搬到 C#，它同时是「通信管理与-oee-计算」按状态计时的基础。

> [!essentials] 核心要点
> - **状态枚举化**：用 `DeviceState` 枚举（Stopped/Running/Paused/Faulted）代替字符串/布尔标志，杜绝拼写与判断散落
> - **迁移表集中**：合法迁移用元组模式 switch（`(target, _state) switch`）一张表说清"从哪到哪允许"
> - **唯一入口**：所有状态变化走 `TryTransition`，先校验后迁移，非法操作统一拦截并提示
> - **任意状态迁移**：`(DeviceState.Faulted, _)` 表示"任意状态都可报故障"，用 `_` 通配表达
> - **UI 联动**：状态变化时同步刷新文字与颜色（运行绿/故障红），设备状态对操作工一屏可见

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System.Windows;
> using System.Windows.Media;
>
> namespace HmiDemo
> {
>     // 状态机核心：状态枚举 + 合法迁移表，把"能不能迁"收敛到一处管理
>     public enum DeviceState { Stopped, Running, Paused, Faulted }
>
>     public partial class MainWindow : Window
>     {
>         private DeviceState _state = DeviceState.Stopped;
>
>         public MainWindow() => InitializeComponent();
>
>         // 尝试迁移：合法则执行并刷新 UI，非法则拦截并提示
>         private bool TryTransition(DeviceState target, string action)
>         {
>             // 元组模式 switch：(目标状态, 当前状态) → 是否允许
>             bool allowed = (target, _state) switch
>             {
>                 (DeviceState.Running, DeviceState.Stopped) => true, // 启动
>                 (DeviceState.Paused, DeviceState.Running) => true,  // 暂停
>                 (DeviceState.Running, DeviceState.Paused) => true,  // 继续
>                 (DeviceState.Faulted, _) => true,                   // 任意状态可报故障
>                 (DeviceState.Stopped, DeviceState.Faulted) => true, // 故障复位
>                 _ => false
>             };
>             if (!allowed)
>             {
>                 LogText.Text = $"非法操作：{action}（{_state} → {target} 不允许）";
>                 LogText.Foreground = Brushes.OrangeRed;
>                 return false;
>             }
>             _state = target;
>             StateText.Text = target.ToString();
>             StateText.Foreground = target switch
>             {
>                 DeviceState.Running => Brushes.LimeGreen,
>                 DeviceState.Faulted => Brushes.OrangeRed,
>                 _ => new SolidColorBrush(Color.FromRgb(0x8B, 0x94, 0x9E))
>             };
>             LogText.Text = $"操作成功：{action} → 当前状态 {target}";
>             LogText.Foreground = new SolidColorBrush(Color.FromRgb(0x8B, 0x94, 0x9E));
>             return true;
>         }
>
>         private void OnStart(object s, RoutedEventArgs e) => TryTransition(DeviceState.Running, "启动");
>         private void OnPause(object s, RoutedEventArgs e) => TryTransition(DeviceState.Paused, "暂停");
>         private void OnResume(object s, RoutedEventArgs e) => TryTransition(DeviceState.Running, "继续");
>         private void OnFault(object s, RoutedEventArgs e) => TryTransition(DeviceState.Faulted, "故障");
>         private void OnReset(object s, RoutedEventArgs e) => TryTransition(DeviceState.Stopped, "复位");
>     }
> }
> ```

> [!scene] 适用场景
> ✅ 设备状态建模：把"停机/运行/暂停/故障"等设备状态与合法迁移固化成规则，杜绝状态随意跳变
> ✅ 控制按钮可用性：按钮是否可点由当前状态推导（如只有运行中才能暂停），状态机 + 界面联动
> ✅ OEE 计时依据：不同状态对应不同计时区间，状态机是「通信管理与-oee-计算」的前提
> ✅ 流程/工单流转：审批、派工、订单状态流转同样是有限状态机，一套模型处处可用
> ❌ 简单的开关量（仅"开/关"两态）：布尔变量即可表达，上状态机是过度设计
> ❌ 状态间关系复杂、存在并发子状态：FSM 表达力不足，应升级为 HSM（层次状态机）或专门状态机库（Stateless）

> [!pitfall] 常见踩坑
> 坑 1：**迁移表漏了某条合法迁移** → 现场允许的操作被程序误拦截，操作工无法执行 → 对照工艺文档逐条核对迁移表，用测试覆盖"所有状态 × 所有事件"组合
>
> 坑 2：**状态用字符串/散落 if 判断**（`if (state == "running")`）→ 拼写错误编译期查不出，判断分散各处难维护 → 用枚举，状态迁移只经 `TryTransition` 唯一入口
>
> 坑 3：**状态改了 UI 没跟着变** → 界面停留在旧状态，操作工误判设备当前状态 → 迁移成功后在入口处统一刷新 UI（颜色/文字/按钮可用性），不在每个按钮事件里各刷各的
>
> 坑 4：**多线程同时改状态** → 轮询线程与 UI 线程竞争状态字段，出现"中间态" → 状态变更收敛到单线程（Dispatcher）或加锁，保证状态读取的原子性

> [!best] 最佳实践
> - 状态、事件、迁移三者显式建模：枚举定义状态与事件，迁移表定义"从→到"合法性，逻辑一目了然
> - 用元组模式 switch 表达迁移表，比一长串 if/else 更易读、更易测；复杂时抽成字典 `Dictionary<(from, ev), to>`
> - 迁移成功/失败都留日志（含 from → to），现场排查"设备为什么没响应"时直接看日志
> - 定义"进入状态的动作"（OnEnter）：进入 Running 时清零计时、进入 Faulted 时触发报警，把副作用挂在状态迁移上
> - 状态机与 UI 解耦：状态机是纯逻辑类（可单元测试），界面只订阅状态变化事件刷新显示
> - 状态枚举的显示文案、颜色用映射表集中定义，新状态只加一行映射

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例，依次点"启动→暂停→继续→故障→复位"，再故意点"暂停"（停机时）观察非法操作拦截提示
> **Lv.2 小试牛刀**：新增"维护"状态（Maintenance），定义合法迁移（仅 Stopped 可进入维护、维护中可回 Stopped），并加对应按钮
> **Lv.3 融会贯通**：为状态机增加"进入动作"：进入 Running 时开始记录运行时长，进入 Stopped 时输出"本次运行 XX 秒"到日志
> **Lv.4 挑战**：把状态机抽象为泛型类 `StateMachine<TState>`（迁移表可配置、状态变更事件可订阅），并改写「报警功能与历史数据」中的报警状态，用状态机统一管理"正常/报警/已确认"三态
