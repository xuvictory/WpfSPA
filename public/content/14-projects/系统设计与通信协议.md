# 系统设计与通信协议

> [!plain] 白话理解
> 温湿度采集下位机和上位机之间通信，就像两个车间的人隔着对讲机对话——如果没人约定"谁先说、说什么、说多长、怎么确认没听错"，双方就会鸡同鸭讲，收到的数据根本没法用。
> 通信协议就是这份"对话暗号"：帧头（`AA 55`）告诉对方"我开始说话了"，功能码告诉对方"我要读温度还是写配置"，数据长度告诉对方"后面要读几个字节"，最后一位校验和用来确认"这一路传下来有没有变味"。上位机拿到一帧，先看帧头、再算校验、最后才信数据。没有这层设计，现场一有电磁干扰，屏幕上就会出现 255 度这种离谱读数。

> [!def] 官方定义
> 通信协议（Communication Protocol）是通信双方就"数据如何封装、如何同步、如何纠错"达成的一组约定规则。本篇采用**自定义帧协议**：在一段字节流中按固定结构划分出帧头（Frame Header）、功能码（Function Code）、数据长度（Data Length）、数据域（Payload）与校验域（Checksum），接收方据此完成帧同步（识别一帧的起止）与差错校验。
> 校验采用**异或校验**（XOR Checksum）：对帧内除校验字节外的所有字节逐位异或，结果作为校验字节，接收方重算比对，不一致即判定为坏帧丢弃。串行通信的帧结构基础见 https://learn.microsoft.com/zh-cn/dotnet/api/system.io.ports.serialport

> [!origin] 由来背景
> 帧结构设计源自串行通信的"起止式"同步机制：RS-232 用起始位、停止位让接收方知道"每个字节从哪开始到哪结束"，但当传输的是连续多字节数据时，仅靠起止位无法回答"这个字节属于哪条消息"。于是工业领域在字节之上叠加了帧层：Modbus 用"从站地址+功能码+数据+CRC16"组织 RTU 帧，上位机与自定义下位机设备通信时，也遵循同样的思路——用帧头同步、用长度界定边界、用校验防错。
> 上位机项目里，PLC、仪表、自研采集板各有各的私有协议，但"帧头+功能码+长度+校验"的骨架高度一致。本篇的自定义帧协议就是这套工业惯例的简化版，掌握了它，后续读 Modbus 帧、SCADA 点表都顺理成章。

> [!essentials] 核心要点
> - **帧头同步**：固定 `0xAA 0x55` 双字节帧头，接收方据此判断一帧起点，避免在字节流中间误切
> - **功能码约定**：`0x01=读温度请求`、`0x81=温度响应`，一收一发成对出现，请求与响应靠功能码区分
> - **长度字段**：数据长度放在固定偏移位，接收方先读长度再按需读取，防止粘帧/拆帧
> - **校验防错**：全字节异或校验收尾，接收方重算比对，坏帧直接丢弃而非给出错误读数
> - **字节序统一**：2 字节温度值按大端（高字节在前）传输，配合 0.1℃ 精度换算（`raw / 10f`）

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Windows;
> using System.Windows.Media;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         // 功能码约定：01=读温度请求 81=温度响应
>         private const byte CmdReadTemp = 0x01;
>         private const byte CmdRespTemp = 0x81;
>
>         public MainWindow() => InitializeComponent();
>
>         // 打包一帧：帧头 AA 55 + 功能码 + 长度 + 数据 + 全字节异或校验
>         private byte[] PackFrame(byte func, byte[] data)
>         {
>             var frame = new byte[4 + data.Length + 1];
>             frame[0] = 0xAA; frame[1] = 0x55;          // 帧头
>             frame[2] = func;                            // 功能码
>             frame[3] = (byte)data.Length;              // 数据长度
>             Array.Copy(data, 0, frame, 4, data.Length);
>             byte checksum = 0;
>             for (int i = 0; i < 4 + data.Length; i++) checksum ^= frame[i];
>             frame[^1] = checksum;                       // 末尾校验字节
>             return frame;
>         }
>
>         // 解析响应帧：校验帧头与校验和，提取温度值（0.1℃ 精度，大端 2 字节）
>         private bool TryParseFrame(byte[] frame, out float temperature)
>         {
>             temperature = 0;
>             if (frame.Length < 6 || frame[0] != 0xAA || frame[1] != 0x55) return false;
>             byte checksum = 0;
>             for (int i = 0; i < frame.Length - 1; i++) checksum ^= frame[i];
>             if (checksum != frame[^1]) return false;    // 校验和不一致视为坏帧
>             short raw = (short)((frame[4] << 8) | frame[5]);
>             temperature = raw / 10f;
>             return true;
>         }
>
>         private void OnSendRequest(object sender, RoutedEventArgs e)
>         {
>             // 1) 打包请求帧（读 1 号通道温度）
>             byte[] request = PackFrame(CmdReadTemp, new byte[] { 0x01 });
>             SendFrameText.Text = BitConverter.ToString(request).Replace("-", " ");
>
>             // 2) 模拟下位机返回 25.6℃ 的响应帧
>             short value = (short)(25.6f * 10);
>             byte[] resp = PackFrame(CmdRespTemp, new byte[] { (byte)(value >> 8), (byte)value });
>
>             // 3) 解析并展示结果
>             if (TryParseFrame(resp, out float temp))
>             {
>                 ParseText.Text = $"帧头 0xAA55 通过 → 功能码 0x{resp[2]:X2} → 温度 = {temp:F1} ℃";
>                 StatusText.Text = "通信正常";
>                 StatusText.Foreground = Brushes.LimeGreen;
>             }
>             else
>             {
>                 ParseText.Text = "响应帧校验失败！";
>                 StatusText.Text = "校验异常";
>                 StatusText.Foreground = Brushes.OrangeRed;
>             }
>         }
>     }
> }
> ```
>

> [!scene] 适用场景
> ✅ 对接自研采集板/定制仪表：设备厂商只给协议文档（寄存器表、帧格式），需要按文档实现组帧解析
> ✅ 传输抗干扰要求高的现场：车间电机启停、变频器运行会产生电磁干扰，必须有校验位防止误数据
> ✅ 多帧连续上报：下位机 1 秒一条数据，用帧头+长度从字节流里稳定切出每条完整消息
> ✅ 协议扩展与演进：在帧里预留功能码和长度字段，后续加"写阈值""校时"命令不必改帧骨架
> ❌ 已有标准协议的场景：能直接用 Modbus/OPC UA 就不必自造轮子，标准协议生态更成熟
> ❌ 单机内部进程通信：同一台机器内用命名管道、内存共享更简单，不需要帧同步与校验

> [!pitfall] 常见踩坑
> 坑 1：**帧头只有一个字节**（如只用 `0xAA`）→ 数据域里恰好出现 0xAA 时接收方误判为帧起点，同步错乱 → 用双字节帧头（`AA 55`）且数据域中冲突时按"连续两个帧头字节才算"处理
>
> 坑 2：**忘记重算校验就解析** → 现场一条干扰帧被当成正常数据，温度瞬间跳到 255℃ 引发误报警 → 解析前必须重算校验，坏帧返回 false 直接丢弃，宁可丢一帧也不信错数据
>
> 坑 3：**字节序不统一**（上位机小端、下位机大端）→ 温度 25.6 变成 0.0256 或负值 → 协议文档里明确字节序，收发两端统一用 `(byte)(value >> 8)` 高字节在前，测试用已知值验证

> [!best] 最佳实践
> - 帧头、长度、校验的偏移位置固定写死成常量，禁止魔法数字散落代码；解析用 `TryParse` 模式返回是否成功
> - 协议文档先行：动手编码前先画一张帧结构表（偏移/字段/长度/说明），两端按同一张表开发
> - 校验和从简单异或起步，数据可靠性要求高时升级为 CRC16（Modbus 同款），误判率更低
> - 预留"帧类型"或"协议版本"字节，设备固件升级、协议扩展时无需推倒重来
> - 调试期把收发帧以十六进制打印到界面（如 `AA 55 01 01 01`），现场排障一眼能看出问题

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例，点击"发送读温度请求"观察请求帧十六进制串与解析结果，再手动改 `25.6f` 为负值或小数验证换算
> **Lv.2 小试牛刀**：新增一个功能码 `0x02=写报警阈值`，用 `PackFrame` 打包一帧"写阈值 28.5℃"并正确打印
> **Lv.3 融会贯通**：故意把响应帧最后一个校验字节改错，验证 `TryParseFrame` 返回 false 且界面显示"校验异常"，体会坏帧拦截流程
> **Lv.4 挑战**：把校验升级为 CRC16-Modbus（多项式 `0xA001`），改写 `PackFrame`/`TryParseFrame`，并用已知样本（如 `01 03 00 00 00 02` → CRC `C4 0B`）自测正确性
