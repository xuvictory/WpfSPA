# 什么是路由事件

> [!plain] 白话理解
> 路由事件就是让事件沿着 UI 控件树**"跑"**——像快递包裹从发货人一路经过各中转站送到收货人手里。WinForms 的普通事件只有一件事：`Button.Click += handler`，点按钮就触发，传递路径为零。WPF 的路由事件则让事件在控件树上**传递**：你点击 `Button` 里包裹的 `StackPanel` 里的 `TextBlock` 里的文字，这个 `MouseDown` 事件会从 `TextBlock` 开始，一层层向上传送（冒泡），途径 `StackPanel`、`Button`、`Grid`、`Window`——每一层都有机会"拦截"和"处理"它。反过来，隧道事件从上往下走（Preview 前缀事件），让外层控件先知道"有事情要发生了"。

> [!def] 官方定义
> 路由事件是 WPF 事件系统的核心，它通过 `RoutedEvent` 标识符注册，并沿着可视树（Visual Tree）或逻辑树（Logical Tree）传递。路由策略有三种：`Bubbling`（冒泡，从源元素向上传递到根）、`Tunneling`（隧道，从根向下传递到源元素）、`Direct`（直接，仅源元素处理）。路由事件的事件参数是 `RoutedEventArgs`（或其子类），包含 `Source`（触发源）、`OriginalSource`（原始视觉树源）和 `Handled`（标记已处理，阻止继续传递）等关键属性。

> [!origin] 由来背景
> WinForms 的平面事件模型有个大痛：假设你想给工具条上所有按钮统一注册同一个 Click 处理器，你必须遍历每个 Button 各自 `+=`。更麻烦的是，如果有一个 `Grid` 包含 100 个控件，你想知道"用户点击了这个区域的任何一个控件"，WinForms 无法一次搞定——你得给 100 个控件分别挂事件。WPF 的路由事件就是为了解决这类"批量事件监听"问题而设计的：在父容器上注册一个事件处理器，所有子元素的该类型事件都会冒泡上来。

> [!essentials] 核心要点
> - **三种路由策略**：Bubbling（向上冒泡）、Tunneling（向下隧道）、Direct（原地处理）
> - **隧道先行于冒泡**：Preview 前缀的隧道事件先触发，然后才是对应的冒泡事件
> - **Handled 可截断传递**：设置 `e.Handled = true` 后事件不再向上/向下传递
> - **父容器可统一监听子元素事件**：在 StackPanel 上注册 `Button.Click`，子按钮点击都能收到
> - **可视树 vs 逻辑树**：路由沿可视树传递，但 `LogicalTreeHelper` 也会参与路由判定

> **MainWindow.xaml.cs**
 ```csharp
using System.Windows;
using System.Windows.Controls;
using System.Windows.Input;
using System.Windows.Media;

namespace HmiDemo;

public partial class MainWindow : Window
{
    public MainWindow()
    {
        InitializeComponent();
    }

    /// <summary>
    /// 统一处理所有设备按钮的冒泡事件
    /// 所有 Button.Click 都会冒泡到 Grid，被 Grid 上的 Button.Click="..." 捕获
    /// </summary>
    private void OnAnyDeviceButtonClick(object sender, RoutedEventArgs e)
    {
        // e.Source: 实际触发事件的元素（哪个 Button 被点了）
        // e.OriginalSource: 视觉树最底层的元素（可能是 Button 内的 TextBlock）
        if (e.Source is Button btn)
        {
            // 通过按钮的 Tag 区分是哪个设备的哪个操作
            string? action = btn.Tag?.ToString() ?? "未知操作";
            txtLog.Text = $">>> 路由事件: [{action}] — "
                + $"Source={e.Source.GetType().Name}, "
                + $"OriginalSource={e.OriginalSource.GetType().Name}";

            // 演示：有选择地"吞噬"事件
            if (action == "M-101报警")
            {
                e.Handled = true;  // 标记已处理，冒泡就此停止
                txtLog.Text += "\n⚠ 报警事件在 Button 层被 Handled，不再向上传递";
            }
        }
    }

    /// <summary>
    /// MouseDown 冒泡演示：点击设备卡片面板任意位置
    /// 事件从被点击的元素开始冒泡，最终到达 StackPanel
    /// </summary>
    private void OnPanelMouseDown(object sender, MouseButtonEventArgs e)
    {
        txtLog.Text = $">>> MouseDown 冒泡到 panelDevices — "
            + $"Source={e.Source.GetType().Name}";
    }
}
 ```
>
> 运行后点击任意按钮，所有 `Button.Click` 事件都会冒泡到 `Grid`，被 `OnAnyDeviceButtonClick` 统一处理——这就是路由事件的"批量监听"能力。你不需要给每个 Button 分别注册事件处理器。

> [!scene] 适用场景
> ✅ 父容器统一监听所有子元素的同类事件（如上例）
> ✅ 多层嵌套控件中在任意层级"拦截"处理（如 `e.Handled = true` 阻止传递）
> ✅ 隧道事件（Preview 系列）做事件预处理/校验——外层面板先知道，有机会取消
> ✅ 自定义控件内部事件暴露给外部使用者
> ❌ 不关心控件树关系的一次性事件——用普通 CLR 事件更简单

> [!pitfall] 常见踩坑
> 坑 1：**`Source` 和 `OriginalSource` 分不清** → `Source` 是逻辑树上触发事件的元素；`OriginalSource` 是视觉树上最底层的元素。点击 Button 上的 TextBlock，`Source=Button`，`OriginalSource=TextBlock`。做类型判断时优先用 `Source`。
>
> 坑 2：**用 `e.Handled = true` 截断后，上层的隧道事件也会受影响** → 如果隧道事件（PreviewMouseDown）中被标记 `Handled=true`，对应的冒泡事件（MouseDown）根本不会触发。因为隧道和冒泡**共享同一个 RoutedEventArgs 实例**。
>
> 坑 3：**在隧道事件中不小心"吃掉"了系统功能** → 比如在 `PreviewKeyDown` 中设 `e.Handled=true` 拦截所有按键，某些系统快捷键（如 Tab 键焦点切换）也会被屏蔽。

> [!best] 最佳实践
> - 上位机中，给"操作日志"面板用父容器统一监听——所有子按钮的操作一条事件处理器记录
> - 隧道事件（Preview）适合做"操作前的校验"——如弹出确认对话框阻止操作
> - 冒泡事件适合做"操作后的响应"——如更新状态栏
> - 不要在路由事件处理器中写大量的同步 IO 操作——事件在 UI 线程同步执行，会卡界面
