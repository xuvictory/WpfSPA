# 采集策略（轮询、事件驱动、订阅）

> [!plain] 白话理解
> 把设备数据比作**食堂窗口的饭菜**，三种采集策略就是三种"取饭"方式：
> - **轮询（Polling）**：像**定时去窗口问"好了吗"**——每隔固定时间主动去读一次设备。不管饭菜有没有变化都去问，简单粗暴，但能保证"到点就有数据"。适合设备不支持主动上报、或者你想完全掌控节奏的场景（如每 200ms 读一次温度）。
> - **事件驱动（Event Driven）**：像**饭菜好了窗口会按铃**——设备状态发生变化时才通知你（如超温报警触发）。平时不用盯，有变化才响应，省资源、响应快，但前提是设备/驱动支持这种"变化通知"。
> - **订阅（Subscribe）**：像**办了订阅制送餐**——数据源按自己的节奏主动把数据推给你，你只要"订阅"后被动接收即可。典型如 MQTT 消息、PLC 的变化推送。上游发什么你收什么，不用管它什么时候发。
>
> 一句话：**轮询是你去找数据，事件是数据找你，订阅是你挂着收数据**。选哪种，取决于设备能力和你对"实时性 vs 开销"的权衡。

> [!def] 官方定义
> - **轮询**：客户端按固定周期向数据源发起读取请求（如定时读寄存器），数据源是被动应答。.NET 中常用 `System.Threading.Timer` / `System.Windows.Threading.DispatcherTimer` 驱动周期读取。
> - **事件驱动**：由设备或底层驱动在"数据变化/状态跳变"时主动触发通知，客户端注册事件处理器接收。.NET 的 `event` 关键字、`System.ComponentModel.INotifyPropertyChanged`（数据变化通知）是其语言基础。
> - **订阅（发布/订阅模式）**：客户端向消息中间件或数据源订阅主题，数据源按发布节奏推送。.NET 侧典型实现：`System.Reactive`（Rx，IObservable/IObserver）、MQTT 客户端库（如 `MQTTnet`）、事件总线。
> - 📖 官方文档：[System.Threading.Timer](https://learn.microsoft.com/zh-cn/dotnet/api/system.threading.timer)、[INotifyPropertyChanged 接口](https://learn.microsoft.com/zh-cn/dotnet/api/system.componentmodel.inotifypropertychanged)、[Reactive Extensions（Rx.NET）](https://learn.microsoft.com/zh-cn/dotnet/reactive/)

> [!origin] 由来背景
> 最早的上位机软件几乎清一色轮询：串口是半双工的，主站不问、从站不说，天然就是"你问我答"的轮询模型，Modbus RTU 协议就是典型。轮询实现简单、节奏可控，至今仍是绝大多数 PLC/仪表的标准玩法。
>
> 但轮询有两个先天缺陷：**空转浪费**（数据没变也白读一遍）和**延迟**（变化要等到下一个周期才被发现）。于是设备厂商在协议层加入"主动上报"能力（如 Modbus 的 TCP 推送扩展、SNMP Trap），事件驱动应运而生。到了物联网时代，MQTT（2010 年 IBM 提出）这类**发布/订阅**协议成为主流——设备作为发布者持续推送，上位机作为订阅者被动接收，彻底把"什么时候发"交给数据源，也让千万级设备的接入成为可能。三种策略如今并存，各管一段场景。

> [!essentials] 核心要点
> - **轮询的节奏参数是关键**：周期（`Interval`）决定实时性与网络/CPU 开销的平衡；轮询周期要大于设备响应时间，否则请求会排队积压
> - **事件驱动靠"订阅 + 注销"配对**：用 `+=` 订阅、`-=` 注销，窗口关闭不注销会导致事件泄漏、对象无法被回收
> - **事件驱动的数据里要带"变化原因"**：是超温了、掉线了还是恢复了，事件参数里要有状态区分，处理器才能正确响应
> - **订阅关注"背压"问题**：推送频率高于消费速度时数据会积压，要设计丢弃策略或限流，否则内存越涨越高
> - **三者可以混用**：一条数据链路里，设备状态用事件驱动、过程值用轮询、与 MES 交互用 MQTT 订阅——很常见
> - **轮询空转检测**：读到的值没变化时可以不更新 UI，节省界面刷新开销

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Windows;
> using System.Windows.Threading;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         // 策略三用的“发布/订阅”事件：订阅者无需关心数据从哪里来
>         public event EventHandler<double> DataPushed;
>
>         private readonly DispatcherTimer _pollTimer;  // 轮询定时器
>         private readonly DispatcherTimer _pushTimer;  // 订阅推送定时器
>         private readonly Random _rnd = new Random();
>
>         public MainWindow()
>         {
>             InitializeComponent();
>
>             // 轮询：定时器到点就主动读一次设备
>             _pollTimer = new DispatcherTimer { Interval = TimeSpan.FromMilliseconds(500) };
>             _pollTimer.Tick += (s, e) => Log("轮询", $"主动读取：温度 {_rnd.Next(20, 60)} ℃");
>
>             // 订阅：定时推送数据源
>             _pushTimer = new DispatcherTimer { Interval = TimeSpan.FromSeconds(1) };
>             _pushTimer.Tick += (s, e) => DataPushed?.Invoke(this, _rnd.Next(20, 60));
>
>             // 订阅者：DataPushed 一旦触发，这个回调就执行
>             DataPushed += (s, value) => Log("订阅", $"被动接收推送：温度 {value} ℃");
>         }
>
>         private void OnStartPoll(object sender, RoutedEventArgs e)
>         {
>             _pollTimer.Start();
>             PollBtn.IsEnabled = false;
>             StopPollBtn.IsEnabled = true;
>         }
>
>         private void OnStopPoll(object sender, RoutedEventArgs e)
>         {
>             _pollTimer.Stop();
>             PollBtn.IsEnabled = true;
>             StopPollBtn.IsEnabled = false;
>         }
>
>         // 事件驱动：设备超温时主动通知，而不是等主程序来查
>         private void OnFireAlarm(object sender, RoutedEventArgs e)
>             => Log("事件", $"设备超温报警触发，当前温度 {_rnd.Next(70, 90)} ℃");
>
>         private void OnToggleSubscribe(object sender, RoutedEventArgs e)
>         {
>             if (_pushTimer.IsEnabled)
>             {
>                 _pushTimer.Stop();
>                 SubBtn.Content = "订阅数据流(每1s推送)";
>             }
>             else
>             {
>                 _pushTimer.Start();
>                 SubBtn.Content = "取消订阅";
>             }
>         }
>
>         private void Log(string strategy, string msg)
>             => LogList.Items.Insert(0, $"[{strategy}] {DateTime.Now:HH:mm:ss}  {msg}");
>     }
> }
> ```

> [!scene] 适用场景
> ✅ **轮询**：串口/Modbus RTU 等"一问一答"式设备；需要固定节拍记录趋势数据的场景；设备数据变化频繁、时刻要最新值的场景
> ✅ **事件驱动**：设备报警、掉线/恢复、到位信号这类"不常发生但发生了必须立刻响应"的状态变化；PLC 内部已做变化检测、主动上抛的场景
> ✅ **订阅**：MQTT/OPC UA 推送、设备自带上报功能、海量设备（上万点）接入——靠订阅才能避免轮询的网络风暴
> ❌ **轮询**：数据每秒变化几十次的突发量，轮询周期跟不上且白白刷屏
> ❌ **事件驱动/订阅**：设备根本不支持主动上报（老式仪表只有问-答协议），只能回到轮询

> [!pitfall] 常见踩坑
> 坑 1：**轮询周期比设备响应时间还短** → 现象：设备忙不过来，请求超时、报错率飙升 → 原因：主站发请求比从站处理快，从站来不及应答 → 解决：轮询周期设为设备响应时间的 2 倍以上，或采用"上一次请求完成再发下一次"的串行轮询
>
> 坑 2：**事件订阅后忘记注销（`-=`）** → 现象：窗口关了事件还在触发，内存持续增长甚至崩溃 → 原因：事件持有对象引用，未注销则对象无法被 GC 回收 → 解决：在 `Closed` 事件里把所有 `+=` 的处理器对称地 `-=`；用弱事件模式（`WeakEventManager`）兜底
>
> 坑 3：**订阅推送太快，处理不过来** → 现象：数据越积越多，内存暴涨，界面越来越卡 → 原因：消费端没有背压控制 → 解决：消费端做限流/合并（如 1s 内只处理最新一条）、或采用环形缓冲丢旧保新

> [!best] 最佳实践
> - **能订阅就别轮询**：设备支持 MQTT/OPC UA 主动推送时优先订阅，省资源且实时性更好；轮询留给"只能问-答"的老设备
> - **轮询用"串行队列"而非裸循环**：维护一个待读点位队列，读一个出一个，天然避免周期撞车
> - **事件处理器保持轻量**：事件里只记录状态变化，重活（写库、弹窗）丢给队列/后台任务，避免阻塞事件源
> - **日志里标记策略来源**：每条日志带 `[轮询]/[事件]/[订阅]` 前缀（如示例），现场排查"这条数据哪来的"一目了然
> - **统一封装为接口**：把三种策略收敛到一个 `IAcquisitionStrategy` 接口下，切换策略只换实现、不换调用方

> [!practice] 上手练习
> **Lv.1 运行改参数**：运行示例分别点三个按钮，观察三种策略的日志格式差异；把轮询周期改成 100ms，观察日志刷屏速度
> **Lv.2 加属性**：给轮询加一个"空转检测"——温度与上次相同时不写入日志（提示"无变化跳过"），体会轮询的浪费
> **Lv.3 改造**：给事件驱动加一个"恢复事件"：点击"触发超温报警事件"后再点"温度恢复"按钮，日志显示恢复正常——理解事件要带状态区分
> **Lv.4 挑战**：定义 `IAcquisitionStrategy` 接口，把三种策略分别封装成三个实现类（轮询用 `Timer`、事件用 `event`、订阅用 `IObservable<T>`），主界面通过接口调用——体验策略可插拔
