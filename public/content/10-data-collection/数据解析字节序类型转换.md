# 数据解析（字节序、类型转换）

> [!plain] 白话理解
> 把"多字节数字"比作一个**电话号码**：大端序就像正常写法"138-0000-0000"（高位在前），小端序就像"0000-0000-138"（低位在前）。同一串号码，按不同习惯读，含义完全不同。
>
> 工业现场就是"各说各话"的世界：Modbus、西门子 S7 协议规定数据**大端**传输（高位字节在前），而你的电脑（x86）内存是**小端**存储。所以设备发来的 `0x04 0x00`，按大端读是 `1024`，按小端读却是 `4`——解析错了，温度变成几百分之一或放大几百倍，现场数据全是乱的。
>
> 一句话：**解析报文 = 按协议文档说的"读写习惯"（字节序）+ 类型规则，把原始字节翻译成能用的数值**，单字节数据（设备号、状态）无所谓，多字节数据（整数、浮点）必须对齐字节序。

> [!def] 官方定义
> - **字节序（Endianness）**：多字节数据在内存/网络中字节的排列顺序。**大端序（Big-Endian）**：高位字节存低地址；**小端序（Little-Endian）**：低位字节存低地址。.NET 中 `System.BitConverter.IsLittleEndian` 指示本机字节序。
> - **类型转换**：把字节序列解析为数值类型。核心 API 归属：`System.BitConverter`（`ToUInt16`/`ToSingle` 等）、`System.Buffers.Binary.BinaryPrimitives`（.NET Core 3.0+，可显式指定 `ReadUInt16BigEndian`/`ReadUInt16LittleEndian`，推荐使用）、`System.Text.Encoding`（字节↔字符串）。
> - **网络字节序**：TCP/IP、Modbus、S7 等协议统一采用大端序传输数据。
> - 📖 官方文档：[BitConverter.IsLittleEndian](https://learn.microsoft.com/zh-cn/dotnet/api/system.bitconverter.islittleendian)、[BinaryPrimitives 类](https://learn.microsoft.com/zh-cn/dotnet/api/system.buffers.binary.binaryprimitives)

> [!origin] 由来背景
> 字节序的分歧源于 1970-80 年代 CPU 架构之争：**x86 系列（Intel 8086 起）采用小端**，因为小端方便"低位字节直接做加法进位"的硬件设计；**Motorola 68000、IBM 大型机采用大端**。后来 TCP/IP 标准化为"网络字节序=大端"，让不同厂商设备能在网络上正确通信；工控协议（Modbus、Profibus、S7）同样沿用大端。于是出现了一头是"大端协议"、一头是"小端电脑"的错位——这成了上位机程序员解析报文时最常踩的坑。这也是为什么解析库（如 `BinaryPrimitives`）专门提供显式字节序的读取方法，把"容易错的事"变成"写错都难"。

> [!essentials] 核心要点
> - **单字节字段无视字节序**：设备号、状态字节等 1 字节数据直接取值，没有顺序问题
> - **多字节整数按协议字节序读**：`ushort`/`short`/`int` 的解析必须与设备协议一致（Modbus/S7 用大端）
> - **浮点也有字节序**：`float`（4 字节）、`double`（8 字节）同样存在大小端问题，且内部是 IEEE 754 标准，不要手动位运算拼接
> - **优先用 `BinaryPrimitives` 显式指定字节序**：`ReadUInt16BigEndian(span)` 比"先读再手动翻转"更不易出错
> - **长度与索引边界先行校验**：解析前确认 `offset + 类型长度 <= 报文长度`，否则越界异常
> - **字符串注意编码**：协议里字符串是 ASCII/UTF-8/GB2312 取决于文档，`Encoding` 选错中文就变乱码

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Windows;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         // 模拟收到的报文：设备ID(1B) + 状态(1B) + 温度(2B ushort) + 转速(4B float)
>         private byte[] _frame;
>
>         public MainWindow() => InitializeComponent();
>
>         private void OnGenClick(object sender, RoutedEventArgs e)
>         {
>             var rnd = new Random();
>             _frame = new byte[] { 0x01, 0x00,
>                                   (byte)rnd.Next(0, 100), (byte)rnd.Next(0, 100),
>                                   (byte)rnd.Next(0, 255), (byte)rnd.Next(0, 255),
>                                   (byte)rnd.Next(0, 255), (byte)rnd.Next(0, 255) };
>             RawText.Text = "原始字节：" + BitConverter.ToString(_frame);
>             ResultList.Items.Clear();
>         }
>
>         private void OnParseClick(object sender, RoutedEventArgs e)
>         {
>             if (_frame == null)
>             {
>                 ResultList.Items.Insert(0, "请先点击“生成模拟报文”");
>                 return;
>             }
>             bool bigEndian = EndianBox.SelectedIndex == 0;   // 本机是小端，选大端时要翻转
>             ResultList.Items.Insert(0, $"字节序：{(bigEndian ? "大端" : "小端")}");
>
>             // 设备 ID 与状态：单字节数据无需考虑字节序
>             ResultList.Items.Add($"设备 ID ：0x{_frame[0]:X2}");
>             ResultList.Items.Add($"运行状态：{(_frame[1] == 0 ? "停机" : "运行")}");
>
>             // 温度：ushort，2 字节，字节序影响结果
>             ushort temp = ReadUInt16(_frame, 2, bigEndian);
>             ResultList.Items.Add($"温度    ：{temp} (0.1℃)");
>
>             // 转速：float，4 字节，字节序影响结果
>             float speed = ReadSingle(_frame, 4, bigEndian);
>             ResultList.Items.Add($"转速    ：{speed:F2} RPM");
>         }
>
>         // 读 2 字节无符号整数(手动处理字节序)
>         private ushort ReadUInt16(byte[] buf, int offset, bool bigEndian)
>         {
>             return bigEndian
>                 ? (ushort)((buf[offset] << 8) | buf[offset + 1])
>                 : (ushort)((buf[offset + 1] << 8) | buf[offset]);
>         }
>
>         // 读 4 字节单精度浮点(统一转成小端交给 BitConverter)
>         private float ReadSingle(byte[] buf, int offset, bool bigEndian)
>         {
>             byte[] bytes = { buf[offset], buf[offset + 1], buf[offset + 2], buf[offset + 3] };
>             if (bigEndian) Array.Reverse(bytes);
>             return BitConverter.ToSingle(bytes, 0);
>         }
>     }
> }
> ```

> [!scene] 适用场景
> ✅ **Modbus RTU/TCP 报文解析**：协议规定大端，寄存器数据按 `ReadUInt16BigEndian` 读取
> ✅ **西门子 S7 通信**：与设备 ID、状态、模拟量打交道的点表解析，全部大端
> ✅ **自定义厂商协议**：仪表、电表、变频器私有协议的帧结构解析（偏移+类型+字节序按文档来）
> ❌ **OPC UA / 组态软件直连**：这些中间层 SDK 已把字节序处理掉，直接拿到的是数值，无需手工解析
> ❌ **纯内存中的同一进程数据**：自己写自己读，字节序自然一致，没有转换必要

> [!pitfall] 常见踩坑
> 坑 1：**按本机字节序（小端）去读协议大端数据** → 现象：温度显示 100 实际是 25600、或反过来巨大/极小 → 原因：`BitConverter.ToUInt16` 默认按本机小端解析 → 解决：用 `BinaryPrimitives.ReadUInt16BigEndian` 显式按协议字节序读，别依赖"本机碰巧一致"
>
> 坑 2：**手动位运算拼接 `float`** → 现象：解析结果 NaN、无穷大或精度全乱 → 原因：浮点内部是 IEEE 754 布局，不能当整数拼接 → 解决：把 4 字节按协议字节序排好，交给 `BitConverter.ToSingle`（如示例 `ReadSingle`）
>
> 坑 3：**字符串编码选错** → 现象：设备返回的中文全是乱码 → 原因：设备用 GB2312/GBK，代码按 UTF-8 解析 → 解决：对照协议文档确认编码，用 `Encoding.GetEncoding("GB2312")` 显式指定
>
> 坑 4：**解析前不检查报文长度** → 现象：`IndexOutOfRangeException` 崩溃 → 原因：短报文也硬解析 → 解决：解析入口先 `if (frame.Length < expected) return;` 并记日志

> [!best] 最佳实践
> - **统一封装解析方法族**：`ReadUInt16(frame, offset, endian)` 这类方法集中放一个 `FrameParser` 静态类，全项目复用，避免到处 `Array.Reverse`
> - **解析日志记录原始帧**：每条解析记一行"原始字节 + 解析结果"，现场对不上数据时这是唯一的排查线索
> - **配置驱动点表**：点位定义（偏移、类型、字节序、比例）放配置文件，新增设备不改代码（详见 `数据转换与工程值计算`）
> - **解析与业务解耦**：解析只产出"点位值 + 时间戳"，校验、清洗、换算交给下游（`数据校验crc校验和等`、`数据过滤与清洗`）

> [!practice] 上手练习
> **Lv.1 运行改参数**：运行示例先点"生成模拟报文"，在"大端/小端"间切换再点"解析报文"，对比温度、转速两个数值——亲手验证字节序对多字节数据的影响
> **Lv.2 加属性**：给报文增加一个"有符号短整型"字段（如偏差值 `short`，2 字节），实现 `ReadInt16` 并解析，体会有符号与无符号的差异
> **Lv.3 改造**：把 `ReadUInt16`/`ReadSingle` 换成 `BinaryPrimitives.ReadUInt16BigEndian`/`ReadUInt16LittleEndian` 等 API，代码更短更不易错
> **Lv.4 挑战**：设计一张"点位配置表"（名称、偏移、类型、字节序、单位），写一个配置驱动的通用解析器 `ParseFrame(byte[] frame, PointConfig[] configs)`，用一个 10 字段的假协议帧验证——这正是真实采集系统的雏形
