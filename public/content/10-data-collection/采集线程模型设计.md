# 采集线程模型设计

> [!plain] 白话理解
> 把上位机比作**餐厅的厨房与前厅**：UI 线程是"前厅服务员"（负责跟顾客/操作员交互），采集线程是"后厨厨师"（负责出菜/采数据）。如果让服务员自己去后厨烧菜（UI 线程做采集 IO），那么顾客叫一声（点按钮、拖窗口）都得等菜烧完才能响应——界面就"冻住"了。
>
> 正确的做法是：**后厨归后厨、前厅归前厅**——采集放到专门的后台线程（`Thread`/`Task`），烧好的"菜"（数据）通过**传菜口**（`Dispatcher.Invoke`）递给前厅服务员，由服务员端给顾客（更新控件）。因为 WPF 规定"控件只能由创建它的 UI 线程碰"，所以后台线程永远不能直接改控件，必须经过 `Dispatcher` 封送。
>
> 一句话：**UI 线程只干界面活，采集活交给后台线程，两者靠 Dispatcher 这个"传菜口"交换数据**。

> [!def] 官方定义
> - **采集线程模型**：上位机软件中关于"数据采集逻辑运行在哪个线程、如何与 UI 线程交换数据"的设计约定。WPF 采用**单线程套间（STA）模型**：每个窗口运行在创建它的 UI 线程上，UI 元素只能被该线程访问（跨线程访问会抛 `InvalidOperationException`）。
> - 关键类型归属：后台采集可用 `System.Threading.Thread`（原生命令式线程）、`System.Threading.Tasks.Task`（线程池任务）、`System.Threading.Timer`（定时回调，线程池线程）；跨线程回 UI 必须用 `System.Windows.Threading.Dispatcher.Invoke`（同步）或 `BeginInvoke`（异步）。
> - 线程间数据共享需同步原语：`lock`、`System.Collections.Concurrent.ConcurrentQueue<T>`（无锁并发队列）等。
> - 📖 官方文档：[WPF 线程模型](https://learn.microsoft.com/zh-cn/dotnet/desktop/wpf/threading-model)、[Dispatcher.Invoke 方法](https://learn.microsoft.com/zh-cn/dotnet/api/system.windows.threading.dispatcher.invoke)、[Thread 类](https://learn.microsoft.com/zh-cn/dotnet/api/system.threading.thread)

> [!origin] 由来背景
> 早期 Windows 程序（Win32 API 时代）界面上直接做耗时操作，窗口会变成"白板"（无响应），微软引入了"消息泵 + 重绘"机制缓解，但根子上的问题没解决。1990 年代后期，多线程被引入 Windows 编程，但"哪个线程碰哪个控件"没有统一约束，跨线程操作控件常导致随机崩溃，极难排查。
>
> WPF（2006 年随 .NET 3.0 发布）从设计上定了规矩：**Dispatcher 线程模型**——UI 元素绑定创建它的线程，跨线程访问必须通过 `Dispatcher` 封送。这看似"不自由"，实则把"数据从采集线程到界面"的路径变成了一条明确的单向通道，避免了整个控件体系为多线程并发付出巨大复杂度。与此同时，.NET 线程池（`ThreadPool`）和后来的 `Task` 让后台线程的创建与回收成本大幅降低，于是"后台线程采集 + Dispatcher 封送刷新"成为 WPF 上位机的事实标准。

> [!essentials] 核心要点
> - **UI 线程只做界面**：任何采集 IO（读串口、读寄存器、等待响应）都不该占用 UI 线程，否则界面卡死
> - **跨线程访问必须经 Dispatcher**：后台线程更新控件用 `Dispatcher.Invoke`（同步等待）或 `BeginInvoke`（不等待）；不熟悉时优先 `BeginInvoke` 避免阻塞采集线程
> - **采集循环要可优雅停止**：用 `volatile bool _running` 作为退出标志，别用 `Thread.Abort`（已被弃用且危险）
> - **共享数据要线程安全**：采集线程写、UI 线程读的共享容器用 `ConcurrentQueue<T>`/`lock`，不要裸用 `List<T>`
> - **线程数量要克制**：每台设备一个常驻采集线程是反模式，设备多时用 `ThreadPool`/`Task` 或"单采集线程 + 轮询点表"模型
> - **UI 更新频率要限流**：后台线程 10ms 采一次，没必要刷 UI 100 次/秒；节流到 100-500ms 刷新一次即可

> [!example] 完整示例
> **采集线程模型演示：后台线程循环采集，Dispatcher 封送更新 UI，UI 不被阻塞：**
>
> **MainWindow.xaml：**
> ```xml

>                     Padding="10,6" Background="#DA3633" Foreground="White" Margin="8,0,0,0"/>
>             <!-- 用于验证 UI 线程未被采集线程阻塞 -->
>             <Button x:Name="UiTestBtn" Content="UI 响应测试" Click="OnUiTestClick" Padding="10,6"
>                     Background="#21262D" Foreground="White" Margin="8,0,0,0"/>

>                    Text="当前值：--" FontFamily="Consolas"/>
>
>         <ListBox x:Name="ThreadLog" Grid.Row="3" Margin="5" Background="#0D1117"
>                  Foreground="#8B949E" BorderBrush="#21262D" BorderThickness="1" FontFamily="Consolas"/>

>
> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Threading;
> using System.Windows;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         private volatile bool _running;  // 采集运行标志(volatile 保证跨线程可见)
>         private Thread _acqThread;       // 后台采集线程
>         private int _uiHits;             // UI 响应计数
>
>         public MainWindow() => InitializeComponent();
>
>         private void OnStartClick(object sender, RoutedEventArgs e)
>         {
>             _running = true;
>             StartBtn.IsEnabled = false;
>             StopBtn.IsEnabled = true;
>             // 采集放到后台线程，避免阻塞 UI 线程
>             _acqThread = new Thread(AcquireLoop) { IsBackground = true, Name = "采集线程" };
>             _acqThread.Start();
>         }
>
>         // 采集循环：运行在后台线程，绝不允许直接碰 UI 控件
>         private void AcquireLoop()
>         {
>             var rnd = new Random();
>             string threadName = Thread.CurrentThread.Name;
>             while (_running)
>             {
>                 double value = rnd.Next(100, 500) / 10.0;   // 模拟读取寄存器
>                 // 跨线程更新 UI：必须通过 Dispatcher 封送到 UI 线程执行
>                 Dispatcher.Invoke(() =>
>                 {
>                     ValueText.Text = $"当前值：{value:F1}";
>                     ThreadLog.Items.Insert(0,
>                         $"[{threadName}] {DateTime.Now:HH:mm:ss} 读到 {value:F1}");
>                 });
>                 Thread.Sleep(200);                           // 模拟采集间隔
>             }
>         }
>
>         private void OnStopClick(object sender, RoutedEventArgs e)
>         {
>             _running = false;
>             StartBtn.IsEnabled = true;
>             StopBtn.IsEnabled = false;
>         }
>
>         private void OnUiTestClick(object sender, RoutedEventArgs e)
>             => UiHitText.Text = $"UI 响应次数：{++_uiHits}（UI 线程未被采集线程阻塞）";
>     }
> }
> ```

> [!scene] 适用场景
> ✅ **串口/网络设备轮询采集**：读 Modbus 寄存器、串口仪表时，响应慢（几十到几百 ms），必须放后台线程避免卡界面
> ✅ **高频率数据采集**：每秒几十次以上的采样，放 UI 线程会让界面明显掉帧
> ✅ **UI 需要"边采边操作"的场景**：采集同时操作员要点按钮、看曲线、切画面，UI 线程必须保持空闲
> ❌ **低频、轻量的界面轮询**：每秒 1-2 次的简单状态刷新，直接用 `DispatcherTimer` 反而更简单（见 `dispatchertimer`）
> ❌ **纯后台任务不需要 UI 的场景**：数据只进库不展示，那根本不需要 Dispatcher，交给 `Task.Run` 即可

> [!pitfall] 常见踩坑
> 坑 1：**后台线程直接改控件** → 现象：运行时报 `InvalidOperationException`（调用线程无法访问此对象，因为它由其他线程拥有）→ 原因：违反 WPF 线程模型 → 解决：所有 UI 更新包进 `Dispatcher.Invoke/BeginInvoke`
>
> 坑 2：**用 `Thread.Abort()` 停采集线程** → 现象：偶发崩溃、数据写一半、控件状态异常 → 原因：`Abort` 强制打断线程任意位置，已被 .NET 标记为过时危险 API → 解决：用 `volatile bool` 标志位让循环自然退出（如示例 `_running`），必要时配合 `ManualResetEvent` 让 `Sleep` 可被立即唤醒
>
> 坑 3：**每个设备开一个常驻线程** → 现象：50 台设备 50 个线程，内存暴涨、上下文切换频繁 → 原因：线程是重量级资源（默认 1MB 栈），不理解线程池 → 解决：单采集线程 + 轮询点表队列，或 `Task`/`ThreadPool` 承载短任务（见 `taskrun-与-taskdelay`）

> [!best] 最佳实践
> - **UI 更新统一走一个"刷新入口"**：后台线程只 `Enqueue` 数据到 `ConcurrentQueue<T>`，UI 侧用一个 `DispatcherTimer` 批量取队列刷新，天然限流且避免频繁 `Invoke`
> - **用 `BeginInvoke` 代替 `Invoke`**：除非必须等 UI 处理完，否则同步 `Invoke` 会让采集线程等 UI，得不偿失
> - **后台线程 `IsBackground = true`**：保证主窗口关闭后进程能正常退出，不会因残留前台线程挂死
> - **采集循环里加异常保护**：`try/catch` 包住每次采集，设备异常只记录日志，不要让异常杀死整个采集线程
> - **线程命名**：`Name = "采集线程"` 等，崩溃 dump 和调试器里一眼认出是哪个线程在干什么

> [!practice] 上手练习
> **Lv.1 运行改参数**：运行示例启动后台采集，疯狂点"UI 响应测试"按钮——界面始终流畅，证明 UI 没被采集阻塞；把 `Thread.Sleep(200)` 改成 20ms 观察日志刷屏
> **Lv.2 加属性**：在 `AcquireLoop` 里故意直接写 `ValueText.Text = ...`（不走 Dispatcher），运行后点击启动，观察抛出的异常信息——亲眼见到违反线程模型的代价
> **Lv.3 改造**：把采集循环从 `Thread` 换成 `Task.Run(() => AcquireLoop())`，并把 `Dispatcher.Invoke` 换成 `BeginInvoke`，对比行为差异；再加一个"限流"：后台线程每 50ms 采一次，但 UI 最多每秒刷 5 次
> **Lv.4 挑战**：实现"单采集线程 + 多点位轮询"：后台线程遍历一个 `ConcurrentQueue<string>` 点位队列（如"设备1.温度""设备1.压力""设备2.液位"），逐个模拟读取并回填结果——体会为什么不用每设备一个线程
