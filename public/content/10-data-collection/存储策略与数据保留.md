# 存储策略与数据保留

> [!plain] 白话理解
> 把存储策略比作**档案室的"入档与销毁规则"**。档案室不可能无限大：最常用的文件放**前台抽屉**（内存），最近一段时间的放**近档区**（本地文件/数据库），过了期的**打包送仓库或销毁**（归档/清理）。如果什么文件都永远留着，三年后档案室就放不下了——服务器磁盘被历史数据写爆就是这么来的。
>
> 工控上位机的数据像流水一样不停产生，必须有**明确的存多少、存多久、超了怎么办**：
> - **容量上限**：实时缓冲只留最近 100 条（环形缓冲，新的顶掉旧的）
> - **时间保留**：原始数据留 30 天，过期自动删或归档
> - **降采样保留**：原始数据太占地方，保留"每分钟均值"（降采样）顶替原始数据
> - **分层存储**：内存→本地磁盘→企业数据库，越往后越"冷"
>
> 一句话：**存储策略 = 定好"什么数据留多久、超了是删还是压缩归档"，让磁盘永远不爆、历史永远够用**。

> [!def] 官方定义
> - **数据保留策略（Data Retention Policy）**：规定数据在系统中的**保存时长与处置方式**的规则，处置方式包括：过期删除、归档（转移到低成本介质）、降采样压缩（粗粒度替换细粒度）。
> - **环形缓冲（Ring/Circular Buffer）**：容量固定、写入指针循环覆盖的缓冲区，`System.Collections.Generic.Queue<T>` 满时 `Dequeue` 后再 `Enqueue` 即得 FIFO 环形语义；线程安全版本为 `System.Collections.Concurrent.ConcurrentQueue<T>`。
> - **TTL（Time To Live）**：以"数据年龄"为过期的依据（如 `TimeStamp < now - 30天` 则删），关系库用 `DELETE ... WHERE TimeStamp < @cutoff`，时序库内置 `RETENTION`。
> - **分层存储（Tiered Storage）**：热数据（内存/SSD）→ 温数据（本地磁盘）→ 冷数据（归档库/磁带/对象存储）的流转。
> - 📖 官方文档：[Queue<T> 类](https://learn.microsoft.com/zh-cn/dotnet/api/system.collections.generic.queue-1)、[ConcurrentQueue<T> 类](https://learn.microsoft.com/zh-cn/dotnet/api/system.collections.concurrent.concurrentqueue-1)

> [!origin] 由来背景
> 数据保留问题随"数据不再稀缺、存储成本开始心疼"而出现。早期硬盘小（几十 MB），工程师必须精打细算：环形缓冲思想可追溯到模拟磁带录音的循环走带（磁带录满自动覆盖）；计算机操作系统日志、网络抓包缓存都沿用了"固定容量 + 覆盖"的缓冲设计。
> 进入数字化车间后，上位机按毫秒级采集，**一台设备一年就能产生上亿条数据**：1 秒 5 点 × 8 小时 × 365 天 ≈ 1.05 亿条/年/设备。若全部原样保留，磁盘很快耗尽。于是"分层 + 保留 + 降采样"成为 SCADA/物联网平台的标配，也催生了时序数据库内置保留策略（见 `时序数据库简介`）。今天的规则很简单：**没配保留策略的系统，迟早被自己的数据撑死**。

> [!essentials] 核心要点
> - **容量上限优先用环形缓冲**：实时数据（最近 100 条/1000 条）用 `Queue<T>`/`ConcurrentQueue<T>`，满了丢最旧——简单、零额外成本
> - **时间保留用 TTL 清理**：定期执行 `DELETE WHERE TimeStamp < now - 保留期`；时序库直接配 `RETENTION` 自动过期
> - **降采样是"用粗换细"**：原始 1 秒 1 点留 7 天，7 天后只保留"每分钟均值"，体积缩 60 倍，趋势照样看（见 `时序数据库简介`）
> - **分层存储按"访问频率"分**：实时窗口（内存）→ 近期待查（本地库）→ 长期归档（企业库/文件），每层独立保留期
> - **保留策略要可配置**：不同点位保留期不同（报警记录留 2 年、趋势数据留 90 天、原始采样留 7 天），配置驱动而非写死
> - **清理与采集不能互相阻塞**：清理任务后台执行、错峰运行、`try/catch` 保护，别让"删旧数据"拖垮"采新数据"

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Collections.Generic;
> using System.Linq;
> using System.Windows;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         // 环形缓冲：容量固定，写入超过容量自动顶掉最旧数据
>         private readonly Queue<(DateTime Time, double Value)> _ring = new Queue<(DateTime, double)>();
>         private const int MaxCapacity = 10;
>         private readonly Random _rnd = new Random();
>
>         public MainWindow() => InitializeComponent();
>
>         // 写入 15 条数据，观察环形缓冲如何顶掉最旧的
>         private void OnFeedClick(object sender, RoutedEventArgs e)
>         {
>             for (int i = 0; i < 15; i++)
>             {
>                 _ring.Enqueue((DateTime.Now.AddSeconds(-i), _rnd.Next(20, 60)));
>                 if (_ring.Count > MaxCapacity) _ring.Dequeue();   // 超出容量：丢弃最旧一条
>             }
>             Refresh();
>         }
>
>         // TTL 清理：删除“年龄超过 60 秒”的数据(模拟保留期)
>         private void OnTtlClick(object sender, RoutedEventArgs e)
>         {
>             DateTime cutoff = DateTime.Now.AddSeconds(-60);
>             int before = _ring.Count;
>             var kept = _ring.Where(x => x.Time >= cutoff).ToList();
>             _ring.Clear();
>             foreach (var x in kept) _ring.Enqueue(x);
>             StatText.Text += $" | TTL清理：{before} → {_ring.Count} 条";
>             Refresh();
>         }
>
>         // 降采样：按分钟分组求均值，用“每分钟一个均值”代表一堆原始点
>         private void OnDownsampleClick(object sender, RoutedEventArgs e)
>         {
>             var groups = _ring.GroupBy(x => x.Time.ToString("mm"));
>             DataList.Items.Insert(0, $"降采样({groups.Count()} 组)：");
>             foreach (var g in groups)
>                 DataList.Items.Add($"  {g.First().Time:HH:mm} 均值 {g.Average(x => x.Value):F1}℃");
>         }
>
>         private void Refresh()
>         {
>             DataList.Items.Clear();
>             foreach (var x in _ring)
>                 DataList.Items.Add($"{x.Time:HH:mm:ss}  {x.Value:F1}℃");
>             StatText.Text = $"缓冲 {_ring.Count}/{MaxCapacity} 条（最新在前）";
>         }
>     }
> }
> ```

> [!scene] 适用场景
> ✅ **实时数据缓冲**：界面曲线/状态栏只需最近 N 条数据，用环形缓冲，天然防内存膨胀
> ✅ **历史数据滚动保留**：原始数据留 7 天、降采样留 90 天、月报表留 2 年——分层保留策略
> ✅ **磁盘有限/工控机长时间无人值守**：没有保留策略，半年后磁盘必满、程序必崩
> ✅ **上报后清空**：数据同步到 MES 后本地立即删除，本地只留"未同步"的部分
> ❌ **法规/审计要求长期保留**：报警记录、关键事件数据不能随便 TTL 删除，需归档到低成本介质并保留原始精度
> ❌ **数据量极小**：一天几十条，保留策略纯属多余，但也建议配一个兜底容量上限防意外

> [!pitfall] 常见踩坑
> 坑 1：**不配保留策略，磁盘被写爆** → 现象：程序运行几个月后磁盘 100%，采集中断、系统崩溃 → 原因：数据只进不出 → 解决：上线前就配好"容量上限 + TTL + 降采样"，并监控磁盘剩余空间（< 5GB 报警）
>
> 坑 2：**TTL 清理误删报警/审计数据** → 现象：出事故要查历史报警，发现 30 天前的报警记录没了 → 原因：所有表共用同一保留期，一刀切 → 解决：保留期**按数据类别配置**：报警/审计 2 年、趋势 90 天、原始采样 7 天；删除前先备份/导出归档
>
> 坑 3：**环形缓冲与"重要数据优先"冲突** → 现象：报警发生时正好被新数据顶掉，关键数据丢失 → 原因：纯 FIFO 不区分数据优先级 → 解决：报警/事件数据**绕过环形缓冲**直接落库（见 `报警系统`），缓冲只放趋势数据
>
> 坑 4：**清理任务与采集并发冲突** → 现象：采集线程卡顿、数据库锁冲突 → 原因：删除大表在采集高峰期执行 → 解决：清理任务错峰（凌晨/交接班）、分批删除（`DELETE ... LIMIT 1000` 循环）、`try/catch` 隔离失败

> [!best] 最佳实践
> - **三档策略起步**：实时（环形缓冲 N 条）→ 近期（本地库 TTL 30 天）→ 归档（降采样 90 天/备份文件），覆盖 90% 场景
> - **保留期做成配置项**：配置文件里 `Retention.Days=30`，现场按客户要求调，不用改代码
> - **清理动作记日志**：`[清理] 删除 12000 条(早于 2026-07-18)，剩余 35000 条`——审计可追溯
> - **删除前先导出**：TTL 删除前把待删数据导出为 CSV/文件归档（见 `导出-csv`），花一点磁盘换"永远有后路"
> - **与存储后端联动**：SQLite/关系库用 TTL SQL、时序库用 `RETENTION`、文件用滚动命名（`data_YYYYMMDD.bin`），各自的最佳实践不同（见 `轻量级数据库-sqlite`、`时序数据库简介`）

> [!practice] 上手练习
> **Lv.1 运行改参数**：运行示例连点"连续写入数据(环形缓冲)"，观察缓冲永远停在 10 条、最旧的被顶掉；把 `MaxCapacity` 改成 5 再观察
> **Lv.2 加属性**：给 `OnTtlClick` 加"按条数清理"模式（超出 N 条删最旧），与按时间 TTL 对比——理解"容量上限"与"时间过期"两种维度
> **Lv.3 改造**：把 `Queue` 换成 `ConcurrentQueue<T>`，在后台采集线程写入、UI 线程查询刷新——验证线程安全下的保留策略（配合 `采集线程模型设计`）
> **Lv.4 挑战**：实现"三层存储流转"：内存环形缓冲（最近 100 条）→ SQLite（`轻量级数据库-sqlite`，最近 1000 条，启动时加载）→ 超过 1000 条时自动归档成 `archive_YYYYMMDD.json` 文件并清库——三层数据自动流转，就是一个小型 SCADA 存储引擎
