# 采集系统总体设计

> [!plain] 白话理解
> 想象一条**饮料灌装产线**：传感器（料位、温度）是车间里的"眼"，PLC 是控制柜，而你的上位机软件要做的不是"一个人包办所有事"，而是搭一条分工明确的流水线——**采集员**（采集层）只管从设备读数据放进筐里，**分拣员**（处理层）只管从筐里取数据做校验、换算，**档案员**（存储层）只管把处理好的数据归档，**看板员**（展示层）只管把最新数据显示到大屏上。
>
> 筐（缓冲队列）是关键：采集员放得快、分拣员干得慢时，数据先在筐里排队，谁也不会被堵死。如果不分层，把"读设备、算工程值、存数据库、刷界面"全写在一个循环里，就像让一个人同时跑四个工位——设备一多、数据一快，界面卡、丢数据、改一处崩三处，全都来了。
>
> 一句话：**采集系统总体设计 = 给数据流动画好"谁负责哪一段"的分工图，用队列把各段解耦**。

> [!def] 官方定义
> - **采集系统总体设计**不是一个微软 API，而是上位机软件的一种**系统架构规划方法**：把"设备数据从产生到应用"的完整链路划分为**采集层（Acquisition）→ 缓冲层（Buffer）→ 处理层（Processing）→ 存储层（Storage）→ 展示层（Presentation）**，各层通过队列/接口解耦，形成可独立演进的数据流水线（Pipeline）。
> - 关键 API 归属：缓冲层常用 `System.Collections.Concurrent.ConcurrentQueue<T>`（线程安全队列）；采集定时常用 `System.Windows.Threading.DispatcherTimer`（UI 线程）或 `System.Threading.Timer`（后台线程）；后台采集任务用 `System.Threading.Tasks.Task` / `System.Threading.Thread`。
> - 这与经典**生产者-消费者模式**（Producer-Consumer）一脉相承：采集线程是生产者，处理/展示线程是消费者。
> - 📖 官方文档：[ConcurrentQueue<T> 类](https://learn.microsoft.com/zh-cn/dotnet/api/system.collections.concurrent.concurrentqueue-1)、[生产者/消费者模式（.NET Channel）](https://learn.microsoft.com/zh-cn/dotnet/core/extensions/channels)、[Windows 应用中的数据绑定与后台任务](https://learn.microsoft.com/zh-cn/dotnet/desktop/wpf/)

> [!origin] 由来背景
> 早期上位机软件多为"单机直连"：一台 PC 用串口连一台 PLC，所有逻辑（读寄存器、算数值、画曲线）写在一个 `while(true)` 循环里，简单直接。但到了 2000 年代，产线走向网络化——一台 PC 要同时采集几十台 PLC、MES 又要拿走同一份数据，单循环立刻崩溃：读设备的慢 IO 拖住了界面刷新，数据一积压就丢。
>
> 这时软件界已有的分层思想（MVC、三层架构）被引入工控：把"数据从设备到屏幕"拆成职责单一的几段，段与段之间用**队列**或**接口**衔接。OPC（OLE for Process Control，1996 年由微软与工控厂商联合推出，后演进为 OPC UA）进一步推动"采集能力标准化"，让采集层可以统一面对不同厂商设备。分层 + 标准化的结果，就是今天上位机普遍采用的"采集—处理—存储—展示"流水线模型。

> [!essentials] 核心要点
> - **五层职责必须清晰**：采集层只读设备，处理层只算数，存储层只落盘，展示层只渲染——任何一层跨职责都会让系统退化
> - **缓冲队列是解耦的命脉**：采集快、消费慢时队列兜底；用 `ConcurrentQueue<T>` 保证线程安全，并监控积压量（积压持续增长 = 消费端瓶颈）
> - **节拍要分层独立**：采集周期（如 200ms）、处理周期（如 500ms）、存储批量（如 1s 一批）各自可配，互不拖累
> - **数据模型要统一**：所有设备的数据最终统一成"点位模型"（设备号 + 点位名 + 值 + 时间戳 + 质量戳），处理/存储/展示只认这一种结构
> - **可扩展性靠接口**：新增一种设备 = 新增一个采集适配器，不动处理层；靠 `IAcquisitionSource` 这类接口隔离
> - **可靠性要有兜底**：断线重连、采集失败重试、缓冲溢出策略（丢旧保新或停止采集），都要在设计时定好

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Collections.Concurrent;
> using System.Windows;
> using System.Windows.Media;
> using System.Windows.Threading;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         // 缓冲队列：采集层与处理层解耦的中间地带
>         private readonly ConcurrentQueue<string> _buffer = new ConcurrentQueue<string>();
>         private readonly DispatcherTimer _acqTimer;   // 采集层定时器(模拟设备采集)
>         private readonly DispatcherTimer _procTimer;  // 处理层定时器(模拟数据处理)
>         private readonly Random _rnd = new Random();
>         private int _total;                           // 总采集条数
>
>         public MainWindow()
>         {
>             InitializeComponent();
>
>             // 采集层：每 200ms 向队列写入一条模拟数据
>             _acqTimer = new DispatcherTimer { Interval = TimeSpan.FromMilliseconds(200) };
>             _acqTimer.Tick += (s, e) =>
>             {
>                 _buffer.Enqueue($"[采集层] {DateTime.Now:HH:mm:ss.fff} 设备1 温度={_rnd.Next(20, 60)}℃");
>                 _total++;
>                 UpdateStat();
>             };
>
>             // 处理层：每 500ms 从队列取出一条数据显示(生产快于消费，可观察队列积压)
>             _procTimer = new DispatcherTimer { Interval = TimeSpan.FromMilliseconds(500) };
>             _procTimer.Tick += (s, e) =>
>             {
>                 if (_buffer.TryDequeue(out string item))
>                     DataList.Items.Add(item);
>                 UpdateStat();
>             };
>         }
>
>         private void OnStartClick(object sender, RoutedEventArgs e)
>         {
>             _acqTimer.Start();
>             _procTimer.Start();
>             StartBtn.IsEnabled = false;
>             StopBtn.IsEnabled = true;
>             StatusText.Text = "采集链路：运行中(采集 200ms/次，处理 500ms/次)";
>             StatusText.Foreground = Brushes.LimeGreen;
>         }
>
>         private void OnStopClick(object sender, RoutedEventArgs e)
>         {
>             _acqTimer.Stop();
>             _procTimer.Stop();
>             StartBtn.IsEnabled = true;
>             StopBtn.IsEnabled = false;
>             StatusText.Text = "采集链路：已停止";
>             StatusText.Foreground = Brushes.OrangeRed;
>         }
>
>         // 统计层：实时刷新采集量与队列积压量
>         private void UpdateStat()
>             => StatText.Text = $"已采集 {_total} 条 | 队列积压 {_buffer.Count} 条";
>     }
> }
> ```

> [!scene] 适用场景
> ✅ **多设备长期运行的监控平台**：几十台 PLC/仪表要同时采集、按不同周期分层处理，平台要能持续加设备
> ✅ **数据既要展示又要存储又要上报的项目**：同一份数据要进界面、进历史库、进 MES，分层后各取所需
> ✅ **多人协作的模块化开发**：采集、存储、界面分给不同人做，靠接口与队列约定边界
> ❌ **单设备单功能的小工具**：一台仪表读个数显示一下，分层反而增加无用复杂度
> ❌ **硬实时控制回路**：ms 级联锁/运动控制必须在 PLC 或专用控制器内完成，上位机分层架构扛不住这种确定性要求

> [!pitfall] 常见踩坑
> 坑 1：**采集和处理写在一个 Timer 里，处理变慢拖垮采集** → 现象：数据积压越来越严重，最终界面假死 → 原因：单线程串行，慢步骤阻塞了快步骤 → 解决：生产者（采集）与消费者（处理）用独立定时器/线程 + `ConcurrentQueue` 解耦
>
> 坑 2：**后台采集线程直接操作 UI 控件** → 现象：程序运行时抛出 `InvalidOperationException`（调用线程无法访问此对象）→ 原因：WPF 控件只能由创建它的 UI 线程访问 → 解决：后台线程更新数据，再 `Dispatcher.Invoke` 封送刷新界面（见 `采集线程模型设计`）
>
> 坑 3：**每个设备定义一套数据结构，处理层到处 if-else** → 现象：新增一种设备要改处理、存储、界面三处代码 → 原因：缺少统一点位模型 → 解决：把所有设备的数据归一为"设备号+点位名+值+时间戳"结构，适配器负责转换

> [!best] 最佳实践
> - **先画数据流图再写代码**：明确每个设备数据"从哪进、经过哪几层、最后到哪"，再动手分层
> - **缓冲用 `ConcurrentQueue<T>` 起步**：数据量大（每秒上万点）再升级为 .NET `Channel` 或环形缓冲，别一开始就自己写锁
> - **给队列加积压监控**：界面显示积压量（如示例的 `StatText`），积压持续上涨说明消费端是瓶颈，第一时间能发现
> - **接口只暴露业务语义**：`IAcquisitionSource.ReadPoint(string name)`，内部是串口还是 Modbus 对上层透明
> - **分层配置独立化**：采集周期、处理周期、存储批量放进配置文件，现场调试不用改代码

> [!practice] 上手练习
> **Lv.1 运行改参数**：运行示例启动采集，观察"已采集"与"队列积压"两个数字的差距；把采集间隔从 200ms 改成 100ms、处理间隔改成 1000ms，观察积压如何暴涨
> **Lv.2 加属性**：在界面加一个 `TextBlock` 显示"队列积压率"（积压量/采集总量），超过 50% 时用红色高亮——这就是最简单的容量告警
> **Lv.3 改造**：把采集层从 `DispatcherTimer` 换成后台 `Thread` + `Thread.Sleep` 循环（模拟真实采集 IO），处理层改用 `Task.Run` 消费队列，验证线程安全
> **Lv.4 挑战**：定义 `IAcquisitionSource` 接口和统一 `PointData` 模型，分别实现"模拟温度源"和"模拟串口源"两个采集适配器，处理层只认接口——体会新增设备时为什么不用改处理层
