# 时序数据库简介

> [!plain] 白话理解
> 把时序数据库比作**给"温度记录仪"这种设备专门盖的档案馆**。普通档案馆（关系库）按"文件夹-文件"归档（表-行），适合查"哪台设备温度是多少"；但工业数据是**一条永不停止的时间轴**——每秒几千个"时间戳+数值"往上涨，查询也永远按时间切（"昨天 14 点到 15 点"），这种数据的形状和关系库完全不一样。
>
> 时序库的杀手锏：
> - **写快**：海量小数据追加写入，吞吐是关系库的数倍
> - **存省**：时间戳和数值按列压缩，同设备同类型数据高度相似，压缩比可达 10~100 倍
> - **查爽**：按时间范围查询、降采样聚合（把 1 小时 3600 个点聚合成 60 个点）是内置一等公民，一条 SQL 就出
>
> 一句话：**数据是"时间戳+数值"为主、按时间写、按时间查、只追加不改——这种数据的专用数据库就是时序数据库（TSDB）**。

> [!def] 官方定义
> - **时序数据库（TSDB，Time Series Database）**：专为**带时间戳的、按时间顺序追加的、高频写入**的数据设计的数据库。核心数据模型为 **measurement（表/度量）+ tag（标签，如设备号）+ field（数值字段）+ timestamp（时间戳）**。
> - 代表产品：**InfluxDB**（2013 年发布，时序库的标杆，.NET 客户端 `InfluxData.Client`）、**TimescaleDB**（PostgreSQL 扩展，关系库与时序能力的混合体）、**TDengine**（国产开源，涛思数据 2017 年发布，专为物联网/工控设计）。
> - 关键能力：高吞吐写入、时间分区存储、列式压缩、**降采样（Downsampling）**、**保留策略（Retention Policy，数据按时间自动过期）**、连续查询。
> - 📖 官方文档：[InfluxDB 文档](https://docs.influxdata.com/influxdb/)、[TDengine 文档](https://docs.taosdata.com/)、[TimescaleDB](https://www.timescale.com/)

> [!origin] 由来背景
> 2010 年前后，物联网与监控告警（如云监控、智能家居）爆发，产生了和传统业务完全不同的数据压力：**千万级设备、每秒海量写入、数据只追加不改、查询永远带时间范围**。用关系库存时序数据有两个致命伤：行存储 + 每行带一堆索引，写入慢、膨胀快；数据按时间自然过期，却要靠 DBA 手工删。2013 年，Paul Dix 创立 InfluxDB，专攻"监控度量与事件数据"，定义了 TSDB 的现代形态；随后 TimescaleDB 让 PostgreSQL 也能跑时序，TDengine（涛思数据）则把"数据库+缓存+流式计算"融合，主打工业物联网。
> 对上位机来说，当单机历史数据从"几十万条"涨到"每天上亿点"时，SQLite 会先撑不住，于是 TSDB 成为 SCADA/物联网平台存储层的标准答案。

> [!essentials] 核心要点
> - **数据模型四要素**：`measurement`（表）+ `tag`（索引标签，如 `device=水泵1`，用于过滤与分组）+ `field`（数值，如 `temp=45.6`）+ `timestamp`（时间戳）
> - **写入要批量**：时序库最擅长"一批几千条"的追加写入，逐条写浪费吞吐；客户端库都支持 `WritePoints(batch)`
> - **tag 与 field 分工要正确**：`tag` 是**低频变化**的维度（设备名、点位名），`field` 是**高频变化**的数值；把高频变化的值塞进 tag 会让索引爆炸
> - **查询三件套**：按时间范围过滤 → 按 tag 分组 → 聚合函数（`mean`/`max`/`min`/`sum`）降采样
> - **保留策略必须配**：TSDB 默认无限存，不配 retention 磁盘会被写爆（对应 `存储策略与数据保留` 的时序版）
> - **时间戳精度统一**：写入用 `DateTime.UtcNow` 或指定精度（秒/毫秒/微秒），混用不同精度会导致数据错位

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Collections.Generic;
> using System.Linq;
> using System.Windows;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         // 内存中的“时序数据表”：每条记录 = 时间戳 + 数值
>         private readonly List<(DateTime Time, double Value)> _ts = new List<(DateTime, double)>();
>         private readonly Random _rnd = new Random();
>
>         public MainWindow() => InitializeComponent();
>
>         // 写入：批量追加带时间戳的数据，并按时间排序(时序库的基本操作)
>         private void OnWriteClick(object sender, RoutedEventArgs e)
>         {
>             DateTime now = DateTime.Now;
>             for (int i = 0; i < 120; i++)
>                 _ts.Add((now.AddSeconds(-i * 2), _rnd.Next(20, 60)));   // 每 2 秒一条
>             _ts.Sort((a, b) => a.Time.CompareTo(b.Time));
>             StatText.Text = $"已写入 {_ts.Count} 条";
>             ResultList.Items.Insert(0, $"写入 {_ts.Count} 条，最新值 {_ts[_ts.Count - 1].Value}℃");
>         }
>
>         // 查询：按时间范围过滤(时序查询最常见形态)
>         private void OnQueryClick(object sender, RoutedEventArgs e)
>         {
>             DateTime since = DateTime.Now.AddMinutes(-1);
>             var rows = _ts.Where(t => t.Time >= since).ToList();
>             ResultList.Items.Insert(0,
>                 $"时间范围查询(最近1分钟)命中 {rows.Count} 条，平均 {rows.Average(t => t.Value):F1}℃");
>         }
>
>         // 降采样：按 10 秒窗口聚合出平均值(压缩数据量，长周期趋势分析常用)
>         private void OnAggregateClick(object sender, RoutedEventArgs e)
>         {
>             var groups = _ts.GroupBy(t => t.Time.Ticks / TimeSpan.FromSeconds(10).Ticks);
>             ResultList.Items.Insert(0, $"降采样聚合(10秒窗口)得到 {groups.Count()} 个点：");
>             foreach (var g in groups.Take(5))
>                 ResultList.Items.Add($"  {new DateTime(g.Key * TimeSpan.FromSeconds(10).Ticks):HH:mm:ss}" +
>                                      $"  平均 {g.Average(t => t.Value):F1}℃");
>         }
>     }
> }
> ```

> [!scene] 适用场景
> ✅ **海量高频采集**：每秒几百到几万点、长期（月/年级）不删的采集数据——TSDB 的压缩与写吞吐是唯一不心疼的方案
> ✅ **监控告警平台**：设备指标、性能监控、趋势异常检测，天然就是"时间+值"数据
> ✅ **多设备海量点位**：几百台设备 × 几十个点位，按设备 tag 过滤查询是 TSDB 的看家本领
> ❌ **单机少量历史数据**：几万条/天的数据 SQLite 完全够，上 TSDB 是过度设计（见 `轻量级数据库-sqlite`）
> ❌ **强事务与复杂关联**：库存扣减、订单联动这类业务事务和表关联，用关系库（见 `关系型数据库sql-servermysql`）

> [!pitfall] 常见踩坑
> 坑 1：**把高频变化值放进了 tag** → 现象：库膨胀快、写入越来越慢 → 原因：`tag` 被当作索引存储，值变化一次就多一个索引项；`temp=45.6` 这种每秒都变的值放 tag 是灾难 → 解决：tag 只放低频维度（设备名、点位名），数值一律放 field
>
> 坑 2：**时间戳精度混用** → 现象：查询按分钟分组时数据对不齐、曲线错位 → 原因：有的点用毫秒、有的用秒或默认精度 → 解决：写入时统一 `DateTime.UtcNow`，并显式声明精度；读取时用同一基准转换
>
> 坑 3：**逐条写入而非批量** → 现象：实测吞吐只有理论值的 1/10 → 原因：时序库高频接口按"批"优化（batch write），逐条写等于每个点一次网络往返 → 解决：攒一批（如 1000 点）再 `WritePoints`，采集端用队列攒批（见 `采集线程模型设计`）
>
> 坑 4：**没配保留策略** → 现象：磁盘被历史数据写爆，服务器宕机 → 原因：TSDB 默认无限保留 → 解决：创建数据库时即配置 `RETENTION`/保留策略（如 90 天自动过期），与 `存储策略与数据保留` 联动

> [!best] 最佳实践
> - **先建模再建库**：写数据前设计好 `measurement / tag / field` 结构（设备号 tag、数值 field），改模型比改数据容易
> - **写入走"批量攒批"通道**：采集线程只入队，后台定时器每 1 秒把队列攒批写入，兼顾实时性与吞吐
> - **查询优先降采样**：画月趋势图时用降采样查询（聚合 5 分钟窗口），别把千万原始点拉回界面（配合 `实时曲线livecharts2`）
> - **保留策略分层**：原始数据留 30 天，降采样后留 1 年，冷数据归档文件——兼顾精度与磁盘
> - **备选型别迷信**：单机小数据用 SQLite、企业共享用 SQL Server、海量高频才上 TSDB——选型看量级，看 `存储策略与数据保留` 的分层思路

> [!practice] 上手练习
> **Lv.1 运行改参数**：运行示例执行"写入→查询→聚合"三步，把窗口从 10 秒改成 30 秒，观察聚合点数量变化
> **Lv.2 加属性**：在"按 10 秒聚合"里增加 `Max`/`Min` 聚合结果展示（一窗三值），理解降采样的信息压缩
> **Lv.3 改造**：接入真实 InfluxDB：用 `InfluxData.Client` 的 `WritePoint` 批量写入（tag=`device`、field=`temp`），再用 `QueryAsync` 的 Flux 查询实现按时间过滤与 `mean()` 降采样
> **Lv.4 挑战**：实现"采集→TSDB→曲线"全链路：后台模拟 100 个点位 × 每秒 1 次写入 InfluxDB，界面上用 `实时曲线livecharts2` 按时间范围查询并画出最近 5 分钟曲线，配 30 天保留策略——这就是一个微型 SCADA 数据链
