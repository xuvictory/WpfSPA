# 串口数据接收最佳实践

> [!plain] 白话理解
> 串口数据是"流"不是"包"——设备发来一帧数据，DataReceived 可能分多次触发，也可能一次带来好几帧。所以正确姿势是：每次事件把字节追加到缓冲区，再按协议从缓冲区里"拆"出完整帧。本文示例演示了"帧头+长度+数据+校验和"协议从缓冲拼接、丢垃圾字节到校验通过的完整解析流程，这是 Modbus 等所有串口协议的上位机通用套路。

> [!def] 官方定义
> 串口接收最佳实践指一套工程约定：不把单次 DataReceived 当完整报文，而是使用累积缓冲（List<byte> 或环形队列）暂存字节流，再按帧协议（通常含帧头、长度域、数据域、校验域）切割出完整帧并校验。核心步骤：①事件中按 BytesToRead 一次性读尽缓冲；②追加到累积缓冲；③循环从缓冲头部剥离完整帧；④校验失败或数据残缺时保持缓冲等待下一事件。目标是解决粘包（多帧合并）、半包（一帧被拆开）两大串口经典问题。

> [!origin] 由来背景
> 串口是字节流协议，UART 本身不知道"帧"的概念。早期开发者直接在 DataReceived 里 ReadString 当一条报文处理，遇到设备响应慢、线缆噪声、系统调度抖动，经常出现一帧变两条或两条变一条，导致解析错乱。工程实践中逐渐形成"缓冲拼接 + 帧头长度剥离"的统一做法，Modbus、自定帧协议都基于此，于是沉淀为上位机串口开发的必备最佳实践。

> [!essentials] 核心要点
> - **不把单次事件当完整报文**：DataReceived 可能半包、可能粘包，必须以缓冲为准
> - **一次性读尽**：事件里按 BytesToRead 读取全部字节再入缓冲，不要一次只读一个字节（性能差）
> - **缓冲追加加锁**：后台线程写缓冲、解析线程/UI 读缓冲时，用 lock 保护 List<byte> 避免并发竞争
> - **按帧头剥离**：找帧头→读长度域→凑齐整帧→取出并消费，循环处理缓冲中可能存在的多帧
> - **垃圾字节丢弃**：帧头不匹配时逐字节丢弃（RemoveAt(0)）并重新找帧头，防止数据错位后死循环
> - **校验必须做**：校验和/CRC 失败要明确记录并丢弃该帧，不要"拿脏数据当有效数据"
> - **解析结果切线程**：帧解析可放后台，但更新界面控件仍要 Dispatcher.Invoke

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Collections.Generic;
> using System.IO.Ports;
> using System.Linq;
> using System.Windows;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         private SerialPort _port;
>         private readonly List<byte> _buffer = new List<byte>(); // 跨事件累积的接收缓冲
>
>         public MainWindow()
>         {
>             InitializeComponent();
>             foreach (string name in SerialPort.GetPortNames())
>                 PortCombo.Items.Add(name);
>             if (PortCombo.Items.Count > 0) PortCombo.SelectedIndex = 0;
>         }
>
>         private void OnOpenClick(object sender, RoutedEventArgs e)
>         {
>             try
>             {
>                 _port = new SerialPort(PortCombo.SelectedItem as string, 115200);
>                 _port.DataReceived += OnDataReceived;
>                 _port.Open();
>                 _buffer.Clear();
>                 StatusText.Text = "已打开，等待接收数据";
>                 StatusText.Foreground = System.Windows.Media.Brushes.LimeGreen;
>             }
>             catch (Exception ex)
>             {
>                 StatusText.Text = "打开失败：" + ex.Message;
>                 StatusText.Foreground = System.Windows.Media.Brushes.OrangeRed;
>             }
>         }
>
>         private void OnCloseClick(object sender, RoutedEventArgs e)
>         {
>             _port?.Close();
>             StatusText.Text = "已关闭";
>             StatusText.Foreground = System.Windows.Media.Brushes.Gray;
>         }
>
>         // 核心：收到的数据先入缓冲，再尝试从中剥离完整帧
>         private void OnDataReceived(object sender, SerialDataReceivedEventArgs e)
>         {
>             int len = _port.BytesToRead;
>             byte[] data = new byte[len];
>             _port.Read(data, 0, len); // 一次性读出全部
>             lock (_buffer) _buffer.AddRange(data);
>             Dispatcher.Invoke(() => RawBox.AppendText(BitConverter.ToString(data) + " "));
>             ParseFrames(); // 立即尝试解析
>         }
>
>         // 帧协议：AA 长度 数据... 校验和（长度 = 数据字节数）
>         private void ParseFrames()
>         {
>             lock (_buffer)
>             {
>                 while (_buffer.Count >= 4)
>                 {
>                     if (_buffer[0] != 0xAA) { _buffer.RemoveAt(0); continue; } // 丢掉垃圾字节
>                     int dataLen = _buffer[1];
>                     int frameLen = dataLen + 3; // 头+长度+数据+校验
>                     if (_buffer.Count < frameLen) return; // 未收齐，等待下一次事件
>                     byte[] frame = _buffer.Take(frameLen).ToArray();
>                     _buffer.RemoveRange(0, frameLen);
>                     // 校验和：数据字节求和，低 8 位为 0
>                     byte sum = 0;
>                     for (int i = 2; i < frameLen - 1; i++) sum += frame[i];
>                     bool ok = sum == frame[frameLen - 1];
>                     Dispatcher.Invoke(() => FrameList.Items.Add(
>                         $"{BitConverter.ToString(frame)}  校验{(ok ? "通过" : "失败")}"));
>                 }
>             }
>         }
>     }
> }
> ```
> 

> [!scene] 适用场景
> ✅ 任何需要按协议解析设备数据的串口应用（Modbus、自定帧协议）
> ✅ 设备主动上报不定长数据、数据帧随时可能被拆散/合并的场景
> ✅ 需要从噪声中恢复的现场环境（丢垃圾字节、重新找帧头）
> ✅ 多设备共用一路总线的轮询应答（一主多从，帧边界必须可靠）
> ❌ 纯文本调试、人眼可读即可的简易通信（帧解析收益不大）
> ❌ 数据量极大且无帧协议（先用协议规范解决，而非靠解析硬扛）

> [!pitfall] 常见踩坑
> 坑 1：**直接把 ReadExisting() 结果当一条报文解析** → 串口是字节流，一帧可能被拆成多次事件到达；必须缓冲拼接后再按帧解析
>
> 坑 2：**帧头错位后死循环** → 找不到帧头时逐字节丢弃并继续找，不能 break；找到帧头但长度域非法时要清空缓冲防止无限等待
>
> 坑 3：**缓冲不加锁，后台线程与 UI 线程同时访问 List** → 解析线程和接收线程共用缓冲时必须 lock，否则可能抛 ArgumentException 或丢数据
>
> 坑 4：**数据量大的场景用 Dispatcher.Invoke 每帧切线程，界面卡死** → 高频接收应批量累积后定时刷新，或用 BeginInvoke 异步投递避免阻塞接收线程

> [!best] 最佳实践
> - **帧协议尽量带长度域**：有长度域才能可靠拆帧，靠"帧间超时"拆帧在重负载下易误判
> - **解析与界面分离**：帧解析放独立类（FrameParser），输入 byte[]、输出帧对象，便于单元测试
> - **环形队列替代 List 高频场景**：数据量大时用环形缓冲减少扩容与拷贝开销
> - **校验失败单独计数**：不只在日志里打印，还要累加错误计数供告警，判断线路是否劣化
> - **超时兜底**：约定帧间超时（如 50ms），半包迟迟不齐时清空缓冲，防止内存无限增长

> [!practice] 上手练习
> **Lv.1 照猫画虎**：用模拟设备程序（每次只发半个帧，延迟后再发另一半）验证缓冲拼接逻辑能正确组出完整帧
> **Lv.2 小试牛刀**：改造帧协议为"帧头 0xAA + 0x55 双字节"，并在解析时加入超时清缓冲（半包超 100ms 丢弃）
> **Lv.3 融会贯通**：把帧解析抽成独立 FrameParser 类（输入 byte[]，输出解析后的帧对象），并写单元测试覆盖粘包、半包、垃圾字节三种用例
