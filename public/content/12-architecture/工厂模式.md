# 工厂模式

> [!plain] 白话理解
> 工厂模式是**把"造谁"的决定收拢到一个柜台**：调用方只说"给我一台 PLC"，不用管 PLC 类怎么 new、构造参数怎么配，工厂按"设备类型"（字符串/枚举）返回对应的 `IDevice`。加一台变频器只改工厂一处，调用方和界面零改动——这就是上位机里"加设备不炸主程序"的底气。

> [!def] 官方定义
> 工厂模式（Factory Pattern）是 GoF 创建型设计模式家族：**用工厂方法/抽象工厂把对象创建逻辑集中封装，调用方依赖产品接口而非具体类**。常见形态：简单工厂（一个方法 switch 返回具体产品）、工厂方法（子类重写工厂方法生产产品）、抽象工厂（一族相关产品的创建）。它属软件设计模式而非微软 API；.NET 中 `System.Data.Common.DbProviderFactories`（ADO.NET 的数据库工厂）就是官方提供的工厂模式实例：https://learn.microsoft.com/zh-cn/dotnet/api/system.data.common.dbproviderfactories 。

> [!origin] 由来背景
> 工厂思想源自制造业"流水线 + 规格书"——调用方不关心零件从哪来，只要规格符合。软件上，1987 年 Erich Gamma 在博士论文中提出创建型模式，1994 年 GoF《设计模式》正式收录"工厂方法"与"抽象工厂"。其核心动机是消除 `new` 的硬编码耦合：早期代码里 `new PlcDevice()` 散落各处，换型号要全局搜索替换；工厂把"根据什么创建什么"集中，调用方只认接口，契合开闭原则（见 `solid-设计原则`）。ADO.NET 的工厂模式让程序能在 SQL Server/Oracle 间切换而不改业务代码，是 .NET 生态最早的工厂范例。

> [!essentials] 核心要点
> - **角色**：产品接口（`IDevice`）、具体产品（`PlcDevice`…）、工厂（`DeviceFactory.Create`）
> - **创建依据**：类型字符串/枚举/配置项 → 返回对应产品；未知类型抛 `NotSupportedException`
> - **简单工厂 vs 工厂方法 vs 抽象工厂**：按"变化维度"选——单产品族用简单工厂，多产品族用抽象工厂
> - **配合 DI**：工厂负责"按名称创建"，DI 容器负责"全局装配"，可叠加使用（见第 7 章 `常用-di-容器`）
> - **实战位置**：协议插件创建（见 `上位机插件化场景`）、设备驱动创建、报表导出器创建（`工厂模式` 示例的 `IReportExporter`）

> [!example] 完整示例
> **设备工厂演示：通过 DeviceFactory 按类型创建 PLC / 变频器 / 温控仪表，调用方只依赖 IDevice 接口，新增设备类型时只需扩展工厂：**
>
> **MainWindow.xaml：**
> ```xml
> <Window x:Class="HmiDemo.MainWindow"
>         xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
>         xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
>         Title="设备工厂 - 工厂模式" Height="300" Width="420"
>         WindowStartupLocation="CenterScreen" Background="#0D1117">
>     <StackPanel Margin="15">
>         <TextBlock Text="设备创建工厂" Foreground="#58A6FF" FontWeight="Bold"/>
>         <ComboBox x:Name="DeviceTypeBox" Margin="0,12,0,0" Padding="4"
>                   Background="#161B22" Foreground="#8B949E">
>             <ComboBoxItem Content="PLC" IsSelected="True"/>
>             <ComboBoxItem Content="变频器"/>
>             <ComboBoxItem Content="温控仪表"/>
>         </ComboBox>
>         <Button Content="创建设备" Click="OnCreate" Margin="0,10,0,0" Padding="8"
>                 Background="#21262D" Foreground="White"/>
>         <TextBlock x:Name="OutputText" Margin="0,12,0,0" Foreground="#8B949E" TextWrapping="Wrap"/>
>     </StackPanel>
> </Window>
> ```
>
> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System.Windows;
> using System.Windows.Media;
>
> namespace HmiDemo
> {
>     // 产品接口：所有设备都支持启动
>     public interface IDevice
>     {
>         string Start();
>     }
>
>     public class PlcDevice : IDevice
>     {
>         public string Start() => "PLC 已启动：开始扫描 IO 与执行梯形图";
>     }
>
>     public class VfdDevice : IDevice
>     {
>         public string Start() => "变频器已启动：输出 50Hz 运行";
>     }
>
>     public class MeterDevice : IDevice
>     {
>         public string Start() => "温控仪表已启动：采集温度并调节输出";
>     }
>
>     // 工厂：集中管理"根据类型创建对象"的逻辑，屏蔽具体类
>     public static class DeviceFactory
>     {
>         public static IDevice Create(string type)
>         {
>             switch (type)
>             {
>                 case "PLC": return new PlcDevice();
>                 case "变频器": return new VfdDevice();
>                 case "温控仪表": return new MeterDevice();
>                 default: throw new NotSupportedException($"不支持的设备类型：{type}");
>             }
>         }
>     }
>
>     public partial class MainWindow : Window
>     {
>         public MainWindow() => InitializeComponent();
>
>         private void OnCreate(object sender, RoutedEventArgs e)
>         {
>             // 调用方只依赖 IDevice 接口，不关心具体类是哪个
>             IDevice device = DeviceFactory.Create(DeviceTypeBox.Text);
>             OutputText.Text = device.Start();
>             OutputText.Foreground = new SolidColorBrush(Color.FromRgb(0x23, 0x86, 0x36));
>         }
>     }
> }
> ```
> 

> [!scene] 适用场景
> ✅ 按设备类型创建驱动：PLC/变频器/仪表下拉选择即创建（示例场景）
> ✅ 协议解析器创建：按配置选 Modbus/S7/私有协议（见 `上位机插件化场景`）
> ✅ 报表/导出格式工厂：CSV/Excel/PDF 按需返回导出器
> ✅ 创建过程复杂（需配参数、建连接）时：集中管理构造细节
> ❌ 只有一种实现、永远不扩展：直接 `new` 更简单，工厂是多余抽象
> ❌ 创建逻辑与类型映射频繁变动的场景：工厂 switch 也要维护，考虑配置文件 + 反射

> [!pitfall] 常见踩坑
> 坑 1：**工厂里堆满 `if/switch` 且无默认处理** → 现象：传入未登记类型时静默返回 null，界面报"对象引用未设置" → 原因：缺少兜底分支 → 解决：`default: throw new NotSupportedException(...)`，把错误尽早暴露（示例已演示）
> 
> 坑 2：**产品接口设计过粗** → 现象：`IDevice` 只有 `Start()`，实际需要 `ReadData()`/`SetParam()`，工厂创建后还要类型判断 → 原因：接口没按调用方需求设计 → 解决：先写调用方代码，从"界面/业务需要什么"倒推接口（见 `solid-设计原则` 接口隔离）
>
> 坑 3：**创建逻辑里混入业务判断** → 现象：工厂方法里加"如果温度>80 就创建报警设备" → 原因：把策略/规则塞进工厂 → 解决：工厂只负责"按参数创建对象"，规则判断放业务层（见 `策略模式`）

> [!best] 最佳实践
> - 工厂返回接口类型：`IDevice device = DeviceFactory.Create(...)`，调用方永不 `using` 具体类
> - 类型标识用 `const string` 或枚举：避免魔法字符串拼错（示例中 ComboBox 值与 case 保持一致）
> - 工厂方法保持"纯创建"：无副作用、不读写界面，便于单元测试（见 12.8 `单元测试xunitmoq`）
> - 创建参数多时定义参数对象（如 `DeviceOptions`），比一长串参数更清晰
> - 与 DI 结合：简单类型交给 DI 容器，只有"运行时按名选择"的场景才用工厂

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例代码，在下拉框分别选 PLC/变频器/温控仪表，观察输出对应启动文案
> **Lv.2 小试牛刀**：新增 `HmiDevice`（人机界面）实现 `IDevice`，在 `DeviceFactory.Create` 与下拉框各加一项
> **Lv.3 融会贯通**：把工厂改为"配置驱动"：从配置文件读设备类型列表（见 12.5 `appsettingsjson推荐方案`），动态生成下拉项并创建
> **Lv.4 拆层挑战**：实现"抽象工厂"：`DeviceFactory` 接口含 `CreatePlc()`/`CreateVfd()`，`DomesticFactory` 与 `ImportedFactory` 各返回不同型号产品，界面切换工厂观察差异
