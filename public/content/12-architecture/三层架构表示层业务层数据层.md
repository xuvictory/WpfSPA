# 三层架构（表示层、业务层、数据层）

> [!plain] 白话理解
> 三层架构把程序按"干什么"切成三间房：**表示层**只负责摆控件、收输入（前台），**业务层**负责算账、做判断（调度室），**数据层**负责读写设备/数据库（仓库）。规矩是"只能往下传话"：前台找调度室，调度室找仓库，仓库不跟前台说话。示例里点一下"登录并查询产量"：界面层只拿输入，BLL 校验权限、DAL 查产量——你改数据库字段时界面一行不用动。

> [!def] 官方定义
> 三层架构（Three-Tier / Layered Architecture）是一种软件架构风格：将系统按职责划分为**表示层（UI/PL）**、**业务逻辑层（BLL）**与**数据访问层（DAL）**，上层依赖下层、下层不依赖上层，层间通过接口与数据传输对象（DTO）通信。它是分层架构（Layered Architecture）最常见的三切分形态，微软官方在「.NET 应用程序架构指南」中有系统阐述：https://learn.microsoft.com/zh-cn/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures#layers ，在桌面/上位机领域常与 MVVM（见第 7 章 `什么是-mvvm`）结合使用——MVVM 管表示层内部，三层管整个系统边界。

> [!origin] 由来背景
> 分层思想源于 1970 年代操作系统分层设计（Dijkstra 的 THE 系统按层划分功能）与 ISO/OSI 七层网络模型。1990 年代，随着客户端/服务器（C/S）应用兴起，两层结构暴露出"界面里塞满 SQL、改一处崩一片"的痛点，业界逐渐把业务逻辑从界面和数据库访问中独立出来，形成三层结构；Martin Fowler 在《企业应用架构模式》（2003）中将其归纳为 Layer/Service Layer 等模式。微软 .NET 时代将其固化为官方推荐结构，至今仍是上位机、Web、桌面应用最普及的基础架构。

> [!essentials] 核心要点
> - **表示层（UI）**：XAML 界面 + ViewModel，只收集输入、展示输出，不写业务判断（对应 MVVM 的 View/ViewModel）
> - **业务层（BLL）**：权限校验、流程编排、报警判断，是系统的大脑，不依赖具体控件
> - **数据层（DAL）**：SQL/设备读写/文件存储，向上只暴露"取数/存数"方法，隐藏实现细节
> - **依赖方向**：UI→BLL→DAL 单向传递；反向解耦靠接口 + 依赖注入（见第 7 章 `什么是依赖注入`）
> - **数据载体**：层间传 DTO/实体对象，别让 DataTable、控件对象跨层乱飞（见第 7 章 `dto-vs-entity`）

> [!example] 完整示例
> **三层架构演示：表示层（UI）、业务层（BLL）、数据层（DAL）三个类各自独立，点击按钮触发"登录校验 → 查询产量"完整流程，体现职责分离：**
>
> **MainWindow.xaml：**
> ```xml
> <Window x:Class="HmiDemo.MainWindow"
>         xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
>         xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
>         Title="三层架构演示" Height="340" Width="420"
>         WindowStartupLocation="CenterScreen" Background="#0D1117">
>     <StackPanel Margin="15">
>         <TextBlock Text="表示层 / 业务层 / 数据层" Foreground="#58A6FF" FontWeight="Bold"/>
>         <TextBox x:Name="UserBox" Margin="0,12,0,0" Padding="4"
>                  Background="#161B22" Foreground="#8B949E" Text="operator"/>
>         <Button Content="登录并查询当日产量" Click="OnLogin" Margin="0,10,0,0" Padding="8"
>                 Background="#21262D" Foreground="White"/>
>         <TextBlock x:Name="OutputText" Margin="0,12,0,0" Foreground="#8B949E" TextWrapping="Wrap"/>
>     </StackPanel>
> </Window>
> ```
>
> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System.Windows;
> using System.Windows.Media;
>
> namespace HmiDemo
> {
>     // 数据访问层 DAL：只做数据库/设备读写
>     public class Dal
>     {
>         public int GetTodayOutput() => 1280; // 模拟查询数据库
>     }
>
>     // 业务逻辑层 BLL：校验规则、业务判断，组合 DAL
>     public class Bll
>     {
>         private readonly Dal _dal = new Dal();
>         public string LoginAndOutput(string user)
>         {
>             if (string.IsNullOrWhiteSpace(user)) return "用户名不能为空";
>             if (user != "operator" && user != "admin") return "无权限用户";
>             return $"登录成功（{user}），今日产量：{_dal.GetTodayOutput()} 件";
>         }
>     }
>
>     // 表示层 UI：只收集输入、展示输出，不写业务逻辑
>     public partial class MainWindow : Window
>     {
>         private readonly Bll _bll = new Bll();
>         public MainWindow() => InitializeComponent();
>
>         private void OnLogin(object sender, RoutedEventArgs e)
>         {
>             OutputText.Text = _bll.LoginAndOutput(UserBox.Text);
>             OutputText.Foreground = new SolidColorBrush(Color.FromRgb(0x8B, 0x94, 0x9E));
>         }
>     }
> }
> ```
> 

> [!scene] 适用场景
> ✅ 单设备上位机从几百行写到几万行：三层是最经济的"防乱"结构
> ✅ 界面、业务、数据任一侧会独立演进：数据库换型、界面重做都不影响另两层
> ✅ 多人分工开发：UI 同学只碰表示层，协议同学只碰数据层
> ✅ 需要同时支撑"界面操作 + 后台服务"的系统：业务层可被多个入口复用
> ❌ 只有两三个界面的小工具：直接两层甚至单层更快
> ❌ 纯实时采集转发（无业务逻辑）的中间层：分层只会增加延迟与复杂度

> [!pitfall] 常见踩坑
> 坑 1：**界面层写了业务判断** → 现象：按钮 Click 里直接算超温、拼 SQL、写文件 → 原因：图省事，把层当摆设 → 解决：界面只调 `ProcessBiz` 方法，所有判断下沉业务层
> 
> 坑 2：**DAL 层泄露实现细节** → 现象：业务层出现 `SqlConnection`、`DataTable`、设备寄存器地址 → 原因：DAL 返回值不够抽象 → 解决：DAL 只返回 DTO/实体，把"读哪些寄存器、怎么解析"封装在 DAL 内部（见第 10 章 `数据解析字节序类型转换`）
>
> 坑 3：**层与层循环引用** → 现象：BLL using UI、UI using BLL，编译期就要破解 → 原因：依赖方向失控 → 解决：依赖只从上往下；反向需求用接口 + DI（见第 7 章 `什么是依赖注入`）打破

> [!best] 最佳实践
> - 三层 + MVVM 各司其职：MVVM 管"表示层内部"（View/ViewModel），三层管"系统级"（UI/BLL/DAL），别混为一谈（见第 7 章 `什么是-mvvm`）
> - 每层一个项目（程序集）：`Hmi.UI`、`Hmi.Business`、`Hmi.Data`，引用关系在项目层面就锁死
> - 层间传 DTO/实体，不传控件和 `DataTable`：换数据库不影响上层（见第 7 章 `dto-vs-entity`）
> - 耗时操作异步化：BLL/DAL 方法返回 `Task`，界面 `await`，避免阻塞 UI（见第 8 章）
> - 先定义"接口/返回模型"再写实现：层与层之间先约定契约，各自并行开发

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例代码，把 DAL 的 `ReadTemperature` 改成读"湿度"，观察业务层和界面层需要改什么、不用改什么
> **Lv.2 小试牛刀**：新增一个"数据层存历史记录"方法（模拟写入 SQLite），业务层每次读取后调用，界面显示"已存 N 条"
> **Lv.3 融会贯通**：把示例改造成三个独立目录（或项目）：`UI/BLL/DAL` 各一，UI 只引用 BLL，BLL 只引用 DAL
> **Lv.4 拆层挑战**：给 BLL 加接口层 `IProcessBiz`，UI 构造函数注入接口，用第 7 章 `常用-di-容器` 注册实现，实现"UI 不认识具体业务类"
