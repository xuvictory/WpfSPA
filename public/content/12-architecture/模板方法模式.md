# 模板方法模式

> [!plain] 白话理解
> 模板方法模式是**把"工序流程"写死、把"每道工序怎么做"留给子类**：所有设备采集都走"连接→校验→采集→断开"四步，顺序不能乱；但 Modbus 设备怎么连接、串口怎么连接，各自实现。基类把流程钉死（`Collect()` 是模板方法），子类只填差异步骤——流程复用、细节隔离，改流程顺序只动一处。

> [!def] 官方定义
> 模板方法模式（Template Method Pattern）是 GoF 行为型设计模式：**在抽象类中定义一个操作算法的骨架（模板方法），将某些步骤延迟到子类中实现**。骨架方法通常标记 `sealed`/`final` 禁止重写，需要子类定制的步骤声明为 `abstract`（必须实现）或 `virtual`（钩子方法，可选覆写）。它是软件设计模式；.NET 框架中大量使用：`System.IO.Stream` 的 `Read/Write` 骨架、ASP.NET 生命周期方法、WPF 的 `OnRender` 等虚方法回调都是模板方法思想的体现：https://learn.microsoft.com/zh-cn/dotnet/api/system.io.stream 。

> [!origin] 由来背景
> 模板方法模式可追溯到 1980 年代"框架设计"实践（Hollywood 原则："别打给我们，我们会打给你"），1994 年 GoF 正式收录。其动机是消除"流程代码重复"：不同采集器都写一遍"连接→读取→断开"，一旦流程要加"日志"就要改所有实现。模板方法把不变的部分（骨架）提升到基类，变化的部分（步骤实现）下沉到子类——这正是"控制反转"在类层面的雏形，也为后来的依赖注入（见第 7 章 `什么是依赖注入`）埋下伏笔。.NET `Stream` 的同步/异步骨架、上位机采集/登录/初始化流程都是经典用法。

> [!essentials] 核心要点
> - **模板方法**：基类 `Collect()` 定义骨架，流程顺序固定；通常 `public` 且不可重写
> - **抽象步骤**：`abstract` 方法（如 `Connect`/`ReadData`）由子类强制实现
> - **钩子方法**：`virtual` 方法（如 `Verify`）提供默认实现，子类可覆写增强
> - **好莱坞原则**：基类调用子类方法（流程控制反转），子类不决定流程顺序
> - **适用场景**：采集流程、启动/关闭流程、数据校验流程、报表生成流程等"同骨架异细节"

> [!example] 完整示例
> **设备采集流程演示：抽象基类把"连接→校验→采集→断开"定义成固定模板，子类只实现各自不同的步骤，流程顺序不允许被改动：**

> **MainWindow.xaml：**

> <Window x:Class="HmiDemo.MainWindow"

>                 Background="#21262D" Foreground="White"/>
>         <TextBlock x:Name="FlowText" Margin="0,12,0,0" Foreground="#8B949E" TextWrapping="Wrap"/>
>     </StackPanel>
> </Window>
> ```

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System.Windows;
> using System.Windows.Media;
>
> namespace HmiDemo
> {
>     // 抽象基类：模板方法 Collect 固定了算法骨架
>     public abstract class DataCollectorBase
>     {
>         public string Flow = "";
>
>         // 模板方法：定义流程顺序，子类不能重写此方法
>         public void Collect()
>         {
>             Connect();                       // 1. 连接设备
>             Verify();                        // 2. 校验（钩子，可选覆写）
>             ReadData();                      // 3. 采集数据
>             Disconnect();                    // 4. 断开连接
>         }
>
>         protected abstract void Connect();    // 子类各自实现
>         protected abstract void ReadData();
>         protected virtual void Verify() => Flow += "  [通用校验] 参数范围正常\n"; // 钩子：默认实现
>         protected abstract void Disconnect();
>     }
>
>     // 子类 A：Modbus TCP 设备的采集步骤
>     public class ModbusCollector : DataCollectorBase
>     {
>         protected override void Connect()    => Flow += "  连接 Modbus TCP (192.168.1.10:502)\n";
>         protected override void ReadData()   => Flow += "  读取保持寄存器 40001~40010\n";
>         protected override void Disconnect() => Flow += "  关闭 Modbus 连接\n";
>     }
>
>     // 子类 B：串口设备的采集步骤，并覆写校验钩子
>     public class SerialCollector : DataCollectorBase
>     {
>         protected override void Connect()    => Flow += "  打开串口 COM3 (9600,8,N,1)\n";
>         protected override void ReadData()   => Flow += "  读取 20 字节采集帧\n";
>         protected override void Disconnect() => Flow += "  关闭串口\n";
>         protected override void Verify()     => Flow += "  [串口校验] CRC 校验通过\n";
>     }
>
>     public partial class MainWindow : Window
>     {
>         public MainWindow() => InitializeComponent();
>
>         private void OnCollect(object sender, RoutedEventArgs e)
>         {
>             // 选择不同子类，流程顺序完全一致，只有步骤实现不同
>             DataCollectorBase collector = DeviceBox.SelectedIndex == 0
>                 ? new ModbusCollector()
>                 : new SerialCollector();
>             collector.Flow = $"采集流程（{DeviceBox.Text}）：\n";
>             collector.Collect(); // 调用模板方法
>             FlowText.Text = collector.Flow;
>             FlowText.Foreground = new SolidColorBrush(Color.FromRgb(0x8B, 0x94, 0x9E));
>         }
>     }
> }
> ```

> [!scene] 适用场景
> ✅ 设备采集流程：连接→校验→采集→断开，多设备同骨架异细节（示例场景）
> ✅ 启动/关闭流程：多子系统统一"初始化→自检→就绪"骨架
> ✅ 数据校验流程：不同产品线共用"读取→校验→入库"骨架
> ✅ 报表生成：统一"取数→加工→导出"骨架，格式各异
> ❌ 步骤数量/顺序各不相同的场景：骨架约束反而碍事
> ❌ 没有公共流程、纯平行实现：模板方法没有可复用的骨架

> [!pitfall] 常见踩坑
> 坑 1：**模板方法被 `virtual` 后被子类改流程** → 现象：子类覆写 `Collect()` 自己另写一套流程 → 原因：骨架没锁死 → 解决：模板方法保持 `sealed`（示例 `public void Collect()` 不标 virtual），子类只能覆写步骤
> 
> 坑 2：**钩子方法太多导致理解困难** → 现象：基类五六个 `virtual` 钩子，子类不知道该覆写哪个 → 原因：抽象设计过度 → 解决：钩子方法给明确默认实现与注释，必要时分"必须实现"（abstract）与"可选增强"（virtual）两组
>
> 坑 3：**子类通过覆写偷偷改变流程语义** → 现象：`Disconnect()` 里做清理时提前退出流程 → 原因：步骤实现里控制流程 → 解决：步骤方法只管本步骤，流程控制只在模板方法内；需要变体时新增模板方法而非在步骤里 hack

> [!best] 最佳实践
> - 模板方法命名用"动词+流程"：`Collect()`、`Initialize()`、`GenerateReport()`，语义即流程
> - 明确分层注释：`// 1. 连接 2. 校验(钩子) 3. 采集 4. 断开`，子类实现者对号入座
> - 钩子方法给"有意义的默认实现"：`Verify()` 默认做范围校验，子类想加强再覆写
> - 流程中的公共逻辑（日志、计时）放模板方法内，一次写好到处生效
> - 结合日志记录流程执行情况：每步成功/失败记入日志（见 12.6 `serilog-结构化日志`）

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例代码，分别选 Modbus/串口设备执行采集，观察流程四步顺序一致、步骤文案不同
> **Lv.2 小试牛刀**：新增 `OpcCollector` 子类（OPC UA 采集），只实现四个抽象步骤，流程复用
> **Lv.3 融会贯通**：给模板方法 `Collect()` 加"记录耗时"：开头记 `Stopwatch.Start()`、结尾输出耗时，观察所有子类自动获得该能力
> **Lv.4 拆层挑战**：把流程改成"采集 N 次"版本：基类加 `CollectMany(int count)` 模板方法循环调用步骤，子类零改动复用
