# 架构设计重要性与类型

> [!plain] 白话理解
> 软件架构就是**盖厂房先画图纸**：先定好哪些区域放车间（界面）、哪些放仓库（数据）、哪些放调度台（业务），再动工。上位机代码从几百行长到几万行时，没有图纸硬盖，改一处牵扯一片。架构类型就是几张不同的"图纸模板"——单体、分层、插件化、微服务，按项目多大、需求多稳来选择。本篇解决"为什么必须先想架构，以及有哪些流派可选"。

> [!def] 官方定义
> 软件架构（Software Architecture）指软件系统的高层结构：一组**构件**（components）、它们之间的**关系**，以及与外部环境的交互约定，用于指导系统的设计与演化（对应 ISO/IEC/IEEE 42010 / IEEE 1471 标准中"系统的基本组织、其构件、构件间与环境间的关系"的定义）。微软官方提供 .NET 应用的架构指导（分层、模块化、依赖方向等），见「.NET 应用程序架构指南」：https://learn.microsoft.com/zh-cn/dotnet/architecture/ 。上位机常见的架构类型包括**单体架构、分层架构、插件化架构**与面向大型产线的**分布式/微服务架构**。

> [!origin] 由来背景
> "架构"概念来自建筑学。1960 年代软件危机（软件规模失控、成本超支）促使人们把建筑蓝图思想引入软件开发：1970 年代结构化编程提出模块化与层次化；1990 年代 David Parnas、Grady Booch 等确立组件与架构描述语言；2003 年 Martin Fowler 出版《企业应用架构模式》（Patterns of Enterprise Application Architecture），系统化总结分层、领域模型等模式，成为 .NET 分层架构的重要源头。微软《.NET 应用程序架构指南》随后把这套思想固化为官方建议。上位机从单机采集程序走向产线级系统，正是这些模式落地的典型场景。

> [!essentials] 核心要点
> - **架构的价值**：控制复杂度、隔离变化、支撑扩展——先有结构再写代码，而不是代码堆完再补结构
> - **架构组成**：构件（类/模块/程序集）+ 连接件（接口/事件/依赖关系）+ 约束（依赖方向、分层规则）
> - **主要类型**：单体、分层（三层/N 层）、插件化、事件驱动、微服务——按项目规模与团队选择
> - **依赖规则**：上层依赖下层、抽象不依赖细节（详见 `solid-设计原则` 的 DIP）
> - **架构即权衡**：没有银弹，任何架构都要为"易改 vs 简单 vs 性能"做取舍

> [!example] 完整示例
> **分层架构最小演示：用"界面层 + 业务层 + 数据层"三层的类结构展示架构的重要性——界面只负责显示，业务层管逻辑，数据层管采集，点击按钮模拟一次完整的取数流程：**
>
> **MainWindow.xaml：**
> ```xml
> <Window x:Class="HmiDemo.MainWindow"
>         xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
>         xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
>         Title="分层架构 - 架构设计" Height="300" Width="420"
>         WindowStartupLocation="CenterScreen" Background="#0D1117">
>     <StackPanel Margin="15">
>         <TextBlock Text="三层架构职责演示" Foreground="#58A6FF" FontWeight="Bold"/>
>         <Button Content="读取一次温度" Click="OnRead" Margin="0,12,0,0" Padding="8"
>                 Background="#21262D" Foreground="White"/>
>         <TextBlock x:Name="OutputText" Margin="0,12,0,0" Foreground="#8B949E" TextWrapping="Wrap"/>
>     </StackPanel>
> </Window>
> ```
>
> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Windows;
> using System.Windows.Media;
>
> namespace HmiDemo
> {
>     // 数据层：只负责读写数据，不关心界面
>     public class SensorDataLayer
>     {
>         public double ReadTemperature() => 78.5 + new Random().Next(-10, 10) / 10.0;
>     }
>
>     // 业务层：负责加工数据、判断逻辑，不直接碰控件
>     public class ProcessBiz
>     {
>         private readonly SensorDataLayer _data = new SensorDataLayer();
>         public string GetTemperatureReport()
>         {
>             double t = _data.ReadTemperature();
>             string alarm = t > 85 ? "⚠ 超温报警" : "温度正常";
>             return $"采集值：{t:F1}℃\n业务判断：{alarm}";
>         }
>     }
>
>     // 界面层：只做显示与用户交互，逻辑全部交给业务层
>     public partial class MainWindow : Window
>     {
>         private readonly ProcessBiz _biz = new ProcessBiz();
>         public MainWindow() => InitializeComponent();
>
>         private void OnRead(object sender, RoutedEventArgs e)
>         {
>             OutputText.Text = _biz.GetTemperatureReport();
>             OutputText.Foreground = new SolidColorBrush(Color.FromRgb(0x8B, 0x94, 0x9E));
>         }
>     }
> }
> ```
> 

> [!scene] 适用场景
> ✅ 新项目立项：动手前先决定"单体/分层/插件化"，避免代码野蛮生长
> ✅ 上位机从单机程序往产线级系统演进：需要分层、模块化支撑多人协作
> ✅ 设备种类多、协议多的工控项目：插件化 + 分层组合最稳
> ✅ 需要长期维护、频繁加需求的产线软件：架构决定了改动成本
> ❌ 一次性验证程序/脚本：几十行代码，直接写更快
> ❌ 资源极受限的屏端程序：分层抽象开销不划算，保持简单

> [!pitfall] 常见踩坑
> 坑 1：**不设计架构就堆代码** → 现象：几万行代码散落各处，加需求牵一发动全身 → 原因：没有层次边界，职责混在一起 → 解决：第 1 天就划好"界面/业务/数据"目录与依赖方向，只往格子里填代码
> 
> 坑 2：**过度设计** → 现象：为"将来可能用"建了一堆抽象，简单功能十几个类 → 原因：给不存在的需求买单（YAGNI） → 解决：按当前需求设计，预留扩展点即可，架构跟着需求演进
>
> 坑 3：**层间越权调用** → 现象：界面里直接连数据库、业务层写 SQL → 原因：图省事绕开分层 → 解决：约定依赖只能自上而下，用依赖注入（见第 7 章 `什么是依赖注入`）强制约束

> [!best] 最佳实践
> - 先画"架构图 + 依赖方向"再写代码：哪怕一张手绘分层图，也比没图强
> - 目录结构即架构：`Views/`、`Services/`、`Repositories/`、`Models/` 分层摆放，一看就懂
> - 依赖方向单一：界面→业务→数据；反向依赖用接口 + DI 容器解耦
> - 架构决策写进文档（ADR）："为什么选三层而不是插件化"记下来，避免后人推翻重来
> - 架构随项目演进：先分层、规模扩大再拆模块/插件，不必一步到位

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例代码，观察"界面→业务→数据"的调用链；把超温阈值 85 改成 80，验证改动只发生在业务层
> **Lv.2 小试牛刀**：给示例加一个"数据层读历史均值"的方法（模拟从数据库取数），业务层汇总后界面显示"当前值/均值"
> **Lv.3 融会贯通**：把你之前写的任一上位机小功能（如温度采集）按三层拆分，确保界面代码不出现任何采集/判断逻辑
> **Lv.4 拆层挑战**：给三层加"服务接口层"，界面只依赖接口，再用第 7 章 `常用-di-容器` 的容器注册实现，完成依赖倒置
