# 上位机插件化场景

> [!plain] 白话理解
> 上位机是插件化架构最典型的"买家"：**协议千变万化、界面功能层出不穷**。一条产线上可能同时有 Modbus 设备、西门子 PLC、自定义协议板卡，今天还要加个 MES 上传——如果每种协议都写死进主程序，加一台设备就要改主程序、重新发布。插件化把**通信协议、业务功能**做成插件：主程序只认 `IProtocolPlugin`，换协议就像换"驱动卡"。示例里 Modbus/S7/私有协议三个插件任选切换，主程序一行协议代码都没有。

> [!def] 官方定义
> 上位机插件化场景指把**设备通信协议、采集驱动、业务功能**等按"契约接口 + 独立程序集"组织为插件（Plug-in），由宿主运行时加载装配的架构实践。它是插件化架构（见 `什么是插件化架构`）在工控软件中的具体落地：宿主依赖统一接口（如 `IProtocolPlugin`），具体协议实现以插件形式提供，可独立开发、独立升级、动态挂载。上位机中可用 MEF（`mef-与-prism-modules`）、Prism Modules 或自研反射加载器实现。该实践无单一"官方定义"，属微软 .NET 架构指南推荐的可扩展设计：https://learn.microsoft.com/zh-cn/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures#plugin-architecture 。

> [!origin] 由来背景
> 上位机行业天然是"多协议混战"：不同厂商 PLC、仪表、板卡各自为政，Modbus、S7、OPC UA、EtherCAT、私有帧协议并存。早期上位机把协议解析写死在各窗口的代码里，新设备上线就要改源码重编译、停机更新，交付现场苦不堪言。借鉴操作系统"设备驱动"与工业组态软件（如 WinCC、组态王）"驱动扩展"机制，上位机开发者把协议层抽象成插件接口，宿主通过工厂/目录加载，实现了"主程序万年不动、插件按需插拔"，成为中大型上位机与组态软件的标准做法。

> [!essentials] 核心要点
> - **协议插件契约**：`Connect()`/`ReadRegisters()` 等统一接口，屏蔽 Modbus/S7/私有协议的差异
> - **工厂创建**：`ProtocolPluginFactory.Create(name)` 按配置/选项返回对应插件实例（工厂模式，见 `工厂模式`）
> - **配置驱动**：插件选择读自配置文件/下拉框，运行时切换协议无需改代码
> - **可扩展边界**：新增协议 = 新增插件类，宿主与既有插件零修改（开闭原则落地）
> - **范围把控**：不是所有功能都适合插件化——只对"会变"的边界（协议/报表/导入导出）做插件，核心流程保持稳定

> [!example] 完整示例
> **上位机插件场景演示：通信协议以插件形式提供，主程序只认识 IProtocolPlugin，选择不同协议插件就像更换"驱动卡"一样简单：**

>                   Background="#161B22" Foreground="#8B949E">
>             <ComboBoxItem Content="Modbus TCP 插件" IsSelected="True"/>
>             <ComboBoxItem Content="西门子 S7 插件"/>
>             <ComboBoxItem Content="私有协议插件"/>
>         </ComboBox>
>         <Button Content="连接设备并读取 3 个寄存器" Click="OnRead" Margin="0,10,0,0" Padding="8"
>                 Background="#21262D" Foreground="White"/>
>         <TextBlock x:Name="OutputText" Margin="0,12,0,0" Foreground="#8B949E" TextWrapping="Wrap"/>
>     </StackPanel>
> </Window>

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System.Windows;
> using System.Windows.Media;
>
> namespace HmiDemo
> {
>     // 协议插件契约：连接 + 读寄存器
>     public interface IProtocolPlugin
>     {
>         string Name { get; }
>         string Connect();
>         string ReadRegisters(int count);
>     }
>
>     public class ModbusPlugin : IProtocolPlugin
>     {
>         public string Name => "Modbus TCP 插件";
>         public string Connect() => "Modbus 已连接 192.168.1.10:502";
>         public string ReadRegisters(int count) => "寄存器: 0x0123 0x0456 0x0789";
>     }
>
>     public class S7Plugin : IProtocolPlugin
>     {
>         public string Name => "西门子 S7 插件";
>         public string Connect() => "S7 已连接 192.168.1.20";
>         public string ReadRegisters(int count) => "DB1.DBW0=100 DB1.DBW2=200 DB1.DBW4=300";
>     }
>
>     public class PrivatePlugin : IProtocolPlugin
>     {
>         public string Name => "私有协议插件";
>         public string Connect() => "私有协议已连接 COM3";
>         public string ReadRegisters(int count) => "帧解析成功: 温度78.5 压力0.85 流量12.3";
>     }
>
>     // 插件工厂：按名称返回协议插件实例
>     public static class ProtocolPluginFactory
>     {
>         public static IProtocolPlugin Create(string name)
>         {
>             if (name.Contains("Modbus")) return new ModbusPlugin();
>             if (name.Contains("S7")) return new S7Plugin();
>             return new PrivatePlugin();
>         }
>     }
>
>     public partial class MainWindow : Window
>     {
>         public MainWindow() => InitializeComponent();
>
>         private void OnRead(object sender, RoutedEventArgs e)
>         {
>             IProtocolPlugin plugin = ProtocolPluginFactory.Create(ProtocolBox.Text);
>             OutputText.Text = $"当前插件：{plugin.Name}\n{plugin.Connect()}\n读取：{plugin.ReadRegisters(3)}";
>             OutputText.Foreground = new SolidColorBrush(Color.FromRgb(0x23, 0x86, 0x36));
>         }
>     }
> }
> ```
> 

> [!scene] 适用场景
> ✅ 产线多设备混接：一台上位机同时跑 Modbus、S7、私有协议，协议做成插件
> ✅ 现场设备升级换代：换新 PLC 型号只换插件，主程序与界面零改动
> ✅ 组态软件/通用采集平台：客户自己选驱动，平台按需加载插件
> ✅ 项目复制多产线：同一套上位机 + 不同协议插件组合，快速交付
> ❌ 固定单协议的专用设备：插件化徒增复杂度，写死协议更简单
> ❌ 协议解析极依赖硬件/实时性：性能敏感的解析放插件层要考虑开销

> [!pitfall] 常见踩坑
> 坑 1：**协议插件"假解耦"** → 现象：`IProtocolPlugin` 接口里全是 `string`，各协议实现各写各的，宿主里还是要 `if (plugin is ModbusPlugin)` → 原因：契约太弱、出现类型判断 → 解决：契约按业务能力设计（`ReadFloat/WriteFloat/Scan`），宿主只认接口，禁止 `is` 分支（见 `solid-设计原则`）
> 
> 坑 2：**插件实例生命周期混乱** → 现象：每次读数据都 `new` 一个插件，连接状态丢失、资源泄漏 → 原因：没有明确"插件何时创建、何时释放" → 解决：协议插件做成"每连接一实例"，由工厂创建、宿主统一释放（见 `工厂模式`、12.6 全局异常里处理连接异常）
>
> 坑 3：**现场升级插件不兼容** → 现象：新协议插件引用了新库，现场旧主机运行崩溃 → 原因：契约/依赖版本不匹配 → 解决：插件元数据登记依赖版本（`[Plugin("Modbus", "2.0", TargetFramework=...)]`），升级前校验（见 12.7 `增量更新与版本管理`）

> [!best] 最佳实践
> - 协议接口按"能力"而非"厂商"设计：`ReadRegisters/WriteCoils/ReadFloats`，Modbus/S7/私有协议都能实现
> - 插件 + 工厂 + 配置三段式：配置写 `Protocol = Modbus`，工厂按名创建，宿主不认识任何具体类
> - 插件连接状态独立管理：每个插件自带 `Connect/Disconnect`，界面切换协议时先释放旧连接
> - 插件目录与版本登记：`Plugins/` 下插件 dll + `plugin.json` 元数据，加载前校验，失败给明确提示
> - 与日志/异常体系打通：插件所有异常冒泡到宿主统一处理并记录（见 12.6 `全局异常捕获与记录`）

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例代码，在 `ProtocolBox` 下拉框里切换三种协议，观察宿主代码完全不涉及协议细节
> **Lv.2 小试牛刀**：新增一个 `TcpIpPlugin` 实现 `IProtocolPlugin`（模拟 TCP 收发），在工厂 `Create` 里注册并能在界面切换
> **Lv.3 融会贯通**：把协议插件的选择改成从配置文件读取（见 12.5 `appsettingsjson推荐方案`），启动时按配置加载
> **Lv.4 拆层挑战**：加入"连接状态"概念：接口加 `IsConnected`，插件内部维护 TCP/串口状态，界面用状态指示灯（见第 10 章 `状态指示灯`）显示
