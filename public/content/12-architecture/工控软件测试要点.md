# 工控软件测试要点

> [!plain] 白话理解
> 普通软件测"功能对不对"，工控软件还得多测三样：**可靠性**（连续跑 72 小时不崩）、**异常容错**（断网、断电、设备失联不把现场搞乱）、**时序并发**（采集线程、界面线程抢数据不打架）。上位机出故障代价是产线停线，所以"测不完的边界"比"测不完的功能"更要命。本篇就是把工控软件的测试要点（尤其上位机）给你列全。

> [!def] 官方定义
> 工控软件测试要点指面向工业控制系统软件（SCADA/上位机/组态）的测试方法集合，核心是**可靠性测试（Reliability）**与**异常场景测试（Negative/Error-path）**：验证长时间连续运行（老化/7×24 稳定性）、异常输入/断线/断电恢复、多线程并发安全、时序一致性等。它无单一官方标准，参考 IEEE 610.12 软件工程术语、ISO/IEC 25010 质量模型（可靠性/可维护性），以及工控行业惯例（WinCC/组态王厂验）。相关规范：IEC 61508（功能安全）与 IEC 62443（工业网络安全）对软件验证提出系统性要求：https://www.iec.ch/functional-safety ；.NET 侧配合单元测试（`单元测试xunitmoq`）与 UI 自动化（`ui-自动化测试flaui`）落地。

> [!origin] 由来背景
> 工控软件测试的特殊性来自行业教训：1970-80 年代工业事故（如化工厂控制软件故障）催生了**功能安全（Functional Safety）**学科，IEC 61508（1998）把"软件必须在规定工况下可靠运行"上升为行业标准；同时工业软件长期依赖"现场试运行+人工回归"，效率低、漏测多。进入 .NET/PC 时代，上位机测试逐步引入软件工程方法：单元测试保证逻辑、UI 自动化保证主流程、**长时间老化测试 + 异常注入（拔线/断电模拟）**保证可靠性。自动化测试框架成熟后，"测试自动化金字塔"（单元→集成→UI）成为工控软件团队的标准打法。

> [!essentials] 核心要点
> - **可靠性优先**：长时间连续运行（72h+）测试、内存泄漏监控、日志无异常堆积
> - **异常容错**：断网/断设备/断电恢复——程序不崩、现场状态不丢、恢复后自动重连
> - **并发与时序**：采集线程、界面线程共享数据安全（见第 8 章）；高并发下数据不错乱
> - **测试金字塔**：单元测试（逻辑）→ 集成测试（模块协作）→ UI 测试（主流程）按比例分配（见 `单元测试xunitmoq`、`ui-自动化测试flaui`）
> - **真实环境验证**：出厂前用真实/模拟设备跑全流程 + 现场试运行跟踪，日志是验证依据（见 `上位机日志场景`）

> [!example] 完整示例
> **工控测试要点演示：模拟"上位机对设备心跳超时的处理"，展示边界值测试思路（恰好等于超时阈值 / 超过阈值 / 未超过），并内置一个自检清单界面：**
>
> **MainWindow.xaml：**
> ```xml
> <Window x:Class="HmiDemo.MainWindow"
>         xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
>         xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
>         Title="工控测试要点" Height="400" Width="460"
>         WindowStartupLocation="CenterScreen" Background="#0D1117">
>     <StackPanel Margin="15">
>         <TextBlock Text="心跳超时边界测试（阈值 3000ms）" Foreground="#58A6FF" FontWeight="Bold"/>
>         <ComboBox x:Name="CaseBox" Margin="0,12,0,0" Padding="4"
>                   Background="#161B22" Foreground="#8B949E">
>             <ComboBoxItem Content="用例1：2999ms（未超时）" IsSelected="True"/>
>             <ComboBoxItem Content="用例2：3000ms（边界值）"/>
>             <ComboBoxItem Content="用例3：3001ms（已超时）"/>
>         </ComboBox>
>         <Button Content="执行测试用例" Click="OnRun" Margin="0,10,0,0" Padding="8"
>                 Background="#21262D" Foreground="White"/>
>         <TextBlock x:Name="OutputText" Margin="0,12,0,0" Foreground="#8B949E" TextWrapping="Wrap"/>
>     </StackPanel>
> </Window>
> ```
>
> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System.Windows;
> using System.Windows.Media;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         private const int TimeoutMs = 3000; // 心跳超时阈值
>
>         public MainWindow() => InitializeComponent();
>
>         // 被测函数：根据距上次心跳的间隔判断设备是否离线
>         private static string CheckHeartbeat(int intervalMs)
>             => intervalMs >= TimeoutMs ? "设备离线，触发报警" : "设备在线，心跳正常";
>
>         private void OnRun(object sender, RoutedEventArgs e)
>         {
>             int interval = CaseBox.SelectedIndex switch
>             {
>                 1 => 3000, // 边界值：等于阈值应判离线
>                 2 => 3001,
>                 _ => 2999,
>             };
>
>             string expected = CaseBox.SelectedIndex == 2 ? "设备离线，触发报警" : "设备在线，心跳正常";
>             string actual = CheckHeartbeat(interval);
>             bool pass = expected == actual;
>
>             OutputText.Text =
>                 $"间隔 {interval}ms → 结果：{actual}\n期望：{expected}\n" +
>                 (pass ? "✅ 用例通过" : "❌ 用例失败（边界值判断有误）");
>             OutputText.Foreground = new SolidColorBrush(Color.FromRgb(
>                 pass ? 0x23 : 0xDA, pass ? 0x86 : 0x36, pass ? 0x36 : 0x33));
>         }
>     }
> }
> ```
> 

> [!scene] 适用场景
> ✅ 上位机出厂前：全功能 + 7×24 老化测试，交付有底
> ✅ 产线现场试运行：真实设备/网络环境验证，日志持续跟踪
> ✅ 每次发版回归：单元 + UI 自动化把主流程快速回归一遍
> ✅ 重大改造后：并发、断线、异常场景重点回归
> ❌ 一次性演示程序：测试投入不划算
> ❌ 纯算法库（无 IO/UI）：常规单元测试即可，不需要工控级场景测试

> [!pitfall] 常见踩坑
> 坑 1：**只测"正常路径"** → 现象：断网、设备掉线、断电恢复这些"必出事"场景从没测过 → 原因：正常路径好测、异常路径费事 → 解决：把异常注入列入测试计划（拔网线/模拟设备断开），每个异常场景写测试用例
> 
> 坑 2：**老化测试不监控资源** → 现象：跑了 72 小时看似正常，内存/句柄泄漏已在积累 → 原因：只看"没崩"没看指标 → 解决：老化期间监控内存/CPU/句柄/日志异常数，结束后出报告
>
> 坑 3：**测试环境与现场环境差异大** → 现象：开发机一切正常，现场网速/干扰/时钟漂移全暴露 → 原因：环境不一致 → 解决：测试环境尽量仿真（车间网络、真机/仿真器、配置一致），并在现场试运行期重点观察

> [!best] 最佳实践
> - 测试金字塔落地：单元测试（逻辑 60%）+ 集成测试（模块协作 30%）+ UI/端到端（主流程 10%）
> - 异常场景清单化：断网、设备失联、断电重启、数据越界、非法输入——逐条造测例
> - 可靠性指标化：连续运行 N 小时无崩溃、内存增长 < X、日志无 Error 堆积
> - 测试数据与日志闭环：测试过程全程日志，失败用例可回放（见 `上位机日志场景`）
> - 发布前 Checklist：功能回归 + 老化 + 异常注入 + 更新/回滚测试都过，才允许发版（见 `自动更新检测与下载`）

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例代码，观察"连接失败/数据越界/数值超限"三类异常的模拟与提示，理解异常场景测试的写法
> **Lv.2 小试牛刀**：给示例加"断线重连"模拟：模拟器数据源 5 秒断开再恢复，断言程序自动重连且不崩
> **Lv.3 融会贯通**：做一个"异常注入清单"：列出示例的 5 个异常场景，逐个手测/自动测并记录结果到日志
> **Lv.4 拆层挑战**：搭建最小测试体系：单元测试（阈值逻辑）+ FlaUI 主流程（见 `ui-自动化测试flaui`）+ 老化脚本（循环跑 1 小时采集观察内存），三件套齐全
