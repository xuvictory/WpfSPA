# 为什么要用日志？

> [!plain] 白话理解
> 日志是上位机的**"黑匣子"**：设备运行中半夜出故障、客户说"昨天下午 3 点温度异常"，你不在现场——靠什么还原？靠日志。没有日志的程序出了问题只能"复现-打断点"，而现场设备往往无法复现。把关键事件、数据、异常按时间记下来，排查问题就从"猜"变成"查"。

> [!def] 官方定义
> 日志（Logging）指程序在运行过程中记录时间、事件、数据、异常等信息到持久化介质（文件/数据库/远程服务）的机制。.NET 官方提供 `Microsoft.Extensions.Logging` 抽象（`ILogger<T>`、`LogInformation/LogError/LogWarning` 等方法），与具体日志实现（Serilog、NLog 等）解耦：https://learn.microsoft.com/zh-cn/dotnet/core/extensions/logging 。上位机日志的独特要求：高可靠性（现场断电不丢）、时间精确、可追溯、能按级别过滤，常配合日志框架实现滚动文件、按天归档。

> [!origin] 由来背景
> 日志思想来自航空"黑匣子"（飞行记录仪，1950 年代）与大型主机系统的"运行审计"。软件开发早期用 `Console.WriteLine` 打点，但正式环境没有控制台，便有了"写文件日志"的朴素实践。1990 年代 Apache Log4j（2001）/log4net（2004）等框架把日志系统化——级别（TRACE→FATAL）、Appender（输出目标）、Layout（格式）成为标准；微软在 .NET Core 中统一为 `Microsoft.Extensions.Logging` 抽象。上位机行业尤其依赖日志：工控现场不可调试、故障代价高，"先查日志"是行业铁律。

> [!essentials] 核心要点
> - **日志级别**：`Trace < Debug < Information < Warning < Error < Critical`，按级别过滤噪音（生产环境通常 Info 起步）
> - **记录内容**：时间戳、级别、来源（类/模块）、事件描述、关键数据（值/状态）、异常堆栈
> - **日志抽象**：`ILogger<T>` 注入使用，实现可替换（Serilog/NLog/控制台），测试时可注入假实现
> - **可靠性**：写文件用异步/缓冲，避免日志本身拖垮采集；断电场景考虑即时落盘
> - **与用户反馈结合**：日志 + 界面提示（`MessageBox`/状态栏）双通道，现场操作员看界面、开发看日志

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Collections.Generic;
> using System.Windows;
> using System.Windows.Controls;
> using System.Windows.Media;
>
> namespace HmiDemo
> {
>     // 极简日志器：带时间戳与级别，生产环境应替换为 NLog/Serilog
>     public class SimpleLogger
>     {
>         private readonly TextBlock _view;
>         public SimpleLogger(TextBlock view) => _view = view;
>
>         public void Info(string msg) => Write("INFO", msg, 0x8B, 0x94, 0x9E);
>         public void Error(string msg) => Write("ERROR", msg, 0xDA, 0x36, 0x33);
>         public void Success(string msg) => Write("OK", msg, 0x23, 0x86, 0x36);
>
>         private void Write(string level, string msg, byte r, byte g, byte b)
>         {
>             _view.Text = $"[{DateTime.Now:HH:mm:ss}] [{level}] {msg}\n" + _view.Text;
>             _view.Foreground = new SolidColorBrush(Color.FromRgb(r, g, b));
>         }
>     }
>
>     public partial class MainWindow : Window
>     {
>         private SimpleLogger _log;
>
>         public MainWindow()
>         {
>             InitializeComponent();
>             _log = new SimpleLogger(LogText);
>             _log.Info("程序启动完成");
>         }
>
>         private void OnStart(object sender, RoutedEventArgs e) => _log.Success("设备启动成功，开始扫描 IO");
>         private void OnAlarm(object sender, RoutedEventArgs e) => _log.Error("超温报警：温度 92.1℃ > 上限 85℃");
>         private void OnStop(object sender, RoutedEventArgs e) => _log.Info("设备正常停机");
>     }
> }
> ```

> [!scene] 适用场景
> ✅ 现场设备故障排查：没有日志只能"等复现"，有日志直接查时间线
> ✅ 数据采集异常定位：哪一秒哪台设备通信失败，日志一清二楚
> ✅ 多线程/后台任务调试：后台异常不可见，必须靠日志（见第 8 章）
> ✅ 操作审计：谁在何时改了什么参数，合规追溯（见 `上位机日志场景`）
> ❌ 一次性调试脚本：`Console.WriteLine` 够了
> ❌ 高频核心循环的过度打点：日志本身拖慢采集，用节流/级别过滤

> [!pitfall] 常见踩坑
> 坑 1：**只打异常不记上下文** → 现象：日志里只有"连接失败"，不知道是哪个设备、哪个环节 → 原因：异常信息不完整 → 解决：记录时带上设备 ID、功能模块、当时的参数值（见 `serilog-结构化日志` 的模板字段）
> 
> 坑 2：**日志写入阻塞业务** → 现象：采集线程写日志时卡顿，数据采集丢帧 → 原因：同步写文件阻塞 → 解决：用异步日志（Serilog 默认异步队列）或独立日志线程；高频日志降级为 `Debug` 级
>
> 坑 3：**日志文件无限膨胀** → 现象：运行一个月日志几个 GB，打开都卡 → 原因：没做滚动/清理 → 解决：按天滚动 + 保留 N 天（见 `serilog-结构化日志` 的 `rollingInterval`），操作日志单独长期保留

> [!best] 最佳实践
> - 日志级别分级：Info 记关键流程（启动/连接/停止），Debug 记细节（协议帧），Error 记异常——生产用 Info 起步
> - 每条日志回答"5W"：何时（时间）、何地（模块）、谁（设备/用户）、发生了什么、结果如何
> - 统一通过 `ILogger<T>`/日志单例：禁止到处 `File.AppendAllText` 裸写
> - 异常日志带完整堆栈 + 内部异常：`ex.ToString()` 而非只 `ex.Message`
> - 关键业务动作（启动、停止、改参、报警）必须留痕：这是现场追溯的第一现场

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例代码，点击按钮触发"连接/读取/异常"三类日志，查看控制台与日志文件的输出
> **Lv.2 小试牛刀**：在读取方法里加一行 `Debug` 级日志记录读取值，把日志级别调到 Debug 观察出现、调回 Info 观察消失
> **Lv.3 融会贯通**：给示例的日志加"异常堆栈"：`catch (Exception ex) { log.Error(ex, "读取设备失败 Device={Id}", id); }`，观察堆栈完整记录
> **Lv.4 拆层挑战**：把示例的日志抽象成 `ILogService` 注入到 ViewModel（见第 7 章 `什么是依赖注入`），测试时注入假实现验证调用
