# 上位机日志场景

> [!plain] 白话理解
> 上位机的日志**不是记给自己看的，是记给"一年后的现场"看的**：产线故障、客户投诉、设备追溯都要靠它。所以上位机日志要按"人"分层次：操作员看"操作日志"（谁在几点改了参数）、维护看"设备日志"（哪台设备何时断开）、开发看"调试日志"（协议帧、堆栈）。本篇教你把这三大类日志拆清楚、记对地方。

> [!def] 官方定义
> 上位机日志场景指工控软件特有的日志分类与落地规范，业界（组态软件/SCADA）通行的三类：**操作日志（Operator/User Audit）**——记录操作员行为（登录、改参数、启停），用于审计追溯；**设备/运行日志（Runtime）**——记录设备通信、采集、报警、流程状态；**调试/诊断日志（Diagnostic）**——记录协议帧、异常堆栈，供研发排障。三者可共用日志框架（Serilog/NLog，见 `serilog-结构化日志`），通过 Logger 名称（如 `Log.ForContext("Category", "Op")`）或独立 Sink 分流。该规范无单一官方标准，参考工业软件最佳实践与 ISO 审计要求（如 FDA 21 CFR Part 11 对电子记录的要求：https://www.fda.gov/regulatory-information/search-fda-guidance-documents/part-11-electronic-records-electronic-signatures-scope-and-application ）。

> [!origin] 由来背景
> 上位机日志分类来自工控与合规的双重压力：一方面现场故障要快速定位，把"操作/设备/调试"混在一个日志文件里，一天几万行根本没法查；另一方面制药、汽车等受监管行业要求"谁在何时做了什么"有据可查（21 CFR Part 11、IATF 16949 追溯要求）。于是组态软件（WinCC、组态王等）普遍按"操作记录 + 报警记录 + 运行记录"分文件存储。现代 .NET 日志框架让分类更容易：结构化字段打标、按目录/Sink 分流、按天滚动归档，上位机日志从此"条理分明"。

> [!essentials] 核心要点
> - **三类日志**：操作日志（审计）、设备/运行日志（故障定位）、调试日志（研发排障）——分开记录
> - **按天/按大小滚动**：日志文件按天归档（`rollingInterval: Day`），避免单文件无限膨胀
> - **保留策略**：调试日志保留数天即可，操作日志按客户要求长期保留（审计需要）
> - **统一时间与来源**：时间戳精确到毫秒 + 设备 ID + 功能模块，多线程环境下不乱序（见第 8 章）
> - **可检索性**：结构化字段（`{DeviceId}`、`{Category}`）让日志能按条件过滤查询（见 `serilog-结构化日志`）

> ```csharp
> using System;
> using System.IO;
> using System.Windows;
> using System.Windows.Controls;
> using System.Windows.Media;

> namespace HmiDemo

>     public partial class MainWindow : Window

>                 LogText.Foreground = new SolidColorBrush(Color.FromRgb(0xDA, 0x36, 0x33));
>             }
>         }
>     }
> }

> [!scene] 适用场景
> ✅ 产线追溯：客户问"昨天这批料哪台设备测的、结果如何"——操作/设备日志作答（示例场景）
> ✅ 操作审计：谁在几点改了什么参数、启停了什么设备，合规留痕
> ✅ 现场远程排障：只拿日志文件就能定位"设备断开/超时/报警"原因
> ✅ 多设备多工位：每设备一分类标签，日志可独立过滤
> ❌ 玩具演示程序：日志分类是过度设计，统一记一份即可
> ❌ 无持久化需求的临时工具：控制台日志足够

> [!pitfall] 常见踩坑
> 坑 1：**三类日志混在一个文件** → 现象：一天几万行，操作员动作淹没在协议调试信息里 → 原因：没分类 → 解决：按 `Category` 字段/独立 Logger 分流：操作日志、运行日志、调试日志各写各的文件（见 `serilog-结构化日志`）
> 
> 坑 2：**时间戳不可信** → 现象：日志时间与实际不一致，多台机器对不上 → 原因：设备时钟漂移/时区不一致 → 解决：统一时区（本地/UTC 明确标注），必要时启动时从服务器校时；采集日志用高精度时间戳
>
> 坑 3：**操作日志与运行日志级别混乱** → 现象：操作员改参数记成 `Debug`，正式环境被过滤掉 → 原因：级别规划不清 → 解决：操作日志固定 `Information` 以上（不可过滤），调试细节才用 `Debug`；用独立 Logger 不依赖级别路由

> [!best] 最佳实践
> - 三类日志独立 Logger/文件：`Op`、`Runtime`、`Debug` 各一，互不干扰、按需保留
> - 操作日志必须"可审计"：时间、用户、动作、旧值→新值、结果，一条不落
> - 设备日志带设备标识：`{DeviceId}`、`{Station}` 字段，多设备可过滤（见 `serilog-结构化日志`）
> - 保留策略差异化：调试 3~7 天、运行 30~90 天、操作日志按合同/合规长期保存
> - 日志目录统一：`logs/{yyyyMMdd}/op.log`、`runtime.log`、`debug.log`，打包排障时整目录带走

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例代码，分别触发"操作（改参数）"“设备（连接/断开）”“调试（帧数据）”，观察三类日志写入不同文件
> **Lv.2 小试牛刀**：给操作日志加"用户 + 动作 + 旧值→新值"：点按钮改阈值时记录 `{User}=操作员, {Old}=85, {New}=80`
> **Lv.3 融会贯通**：为设备日志加 `DeviceId` 结构化字段并模拟两台设备，验证可按设备过滤日志
> **Lv.4 拆层挑战**：实现"日志查看窗口"：界面读操作日志文件展示表格（用户/时间/动作），把日志分类与 UI 打通（结合第 5 章数据绑定）
