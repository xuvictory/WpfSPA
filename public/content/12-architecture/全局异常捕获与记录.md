# 全局异常捕获与记录

> [!plain] 白话理解
> 全局异常捕获是上位机的**"最后一道安全网"**：代码总有漏网的异常——设备断开、解析越界、用户乱操作。不兜底，程序直接闪退，现场设备停摆、操作员懵圈。在 WPF 里挂三个全局钩子（UI 线程、非 UI 线程、AppDomain），任何漏网异常都"先记日志再决定"：能恢复的提示后继续，不能恢复的友好退出。程序"宁可不崩，不可白崩"。

> [!def] 官方定义
> 全局异常捕获指在应用级挂接未处理异常处理器，拦截未被代码 catch 的异常并统一处理。WPF/.NET 提供三个官方事件：**`AppDomain.CurrentDomain.UnhandledException`**（进程级未处理异常，包括非 UI 线程）、**`DispatcherUnhandledException`**（`System.Windows.Application`，WPF UI 线程，`e.Handled = true` 可阻止崩溃）、**`TaskScheduler.UnobservedTaskException`**（未观察的 Task 异常）：https://learn.microsoft.com/zh-cn/dotnet/desktop/wpf/advanced/dispatcherunhandledexception 。配合日志框架记录堆栈与上下文（见 `serilog-结构化日志`），实现"异常不丢、可追溯"。

> [!origin] 由来背景
> .NET Framework 1.0 时代"未处理异常 = 直接崩溃"，桌面程序一个空引用就闪退，用户数据与现场状态损失惨重。微软在 .NET 2.0 起引入 `AppDomain.UnhandledException` 钩子，WPF（2006）专门提供 `DispatcherUnhandledException` 让 UI 线程异常可"拦截并标记已处理"；Task 并行库（2010）又带来 `UnobservedTaskException`。业界随之形成"全局兜底 + 本地精准 catch"的异常治理实践：能预判的在方法内 catch，漏网的全局兜底，两者结合，配合日志/崩溃转储（WER）实现现场可追溯。

> [!essentials] 核心要点
> - **三个钩子**：`AppDomain.UnhandledException`（全兜底）、`DispatcherUnhandledException`（UI 线程，可 `e.Handled=true`）、`TaskScheduler.UnobservedTaskException`（后台 Task）
> - **注册位置**：`App.xaml.cs` 的 `OnStartup` 里注册，统一处理 + 写日志
> - **处理策略**：记录异常详情 → 决定"继续/退出"；`DispatcherUnhandledException` 建议 `e.Handled = true` 防闪退，但致命异常（`OutOfMemory` 等）应退出
> - **日志内容**：异常类型、消息、完整堆栈、时间、来源模块、当时的业务上下文（设备/工序）
> - **兜底≠不 catch**：可预判异常（`TimeoutException`、`IOException`）仍应在方法内精确处理，全局钩子只接漏网之鱼

> [!example] 完整示例
> **全局异常捕获演示：在 App.xaml.cs 中订阅 DispatcherUnhandledException 兜底捕获所有未处理异常，并记录到界面/日志，程序不会闪退：**
>
> **App.xaml.cs：**
> ```csharp
> using System;
> using System.Windows;
> using System.Windows.Threading;
>
> namespace HmiDemo
> {
>     public partial class App : Application
>     {
>         protected override void OnStartup(StartupEventArgs e)
>         {
>             // 全局兜底：任何未捕获异常都会走到这里
>             DispatcherUnhandledException += (s, args) =>
>             {
>                 MainWindow window = (MainWindow)MainWindow;
>                 window.ShowGlobalError($"全局捕获：{args.Exception.Message}");
>                 args.Handled = true; // 标记已处理，避免程序崩溃
>             };
>             base.OnStartup(e);
>         }
>     }
> }
> ```
>
> **MainWindow.xaml：**
> ```xml
> <Window x:Class="HmiDemo.MainWindow"
>         xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
>         xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
>         Title="全局异常捕获" Height="320" Width="440"
>         WindowStartupLocation="CenterScreen" Background="#0D1117">
>     <StackPanel Margin="15">
>         <TextBlock Text="全局异常捕获与记录" Foreground="#58A6FF" FontWeight="Bold"/>
>         <Button Content="触发一个未处理异常" Click="OnThrow" Margin="0,12,0,0" Padding="8"
>                 Background="#DA3633" Foreground="White"/>
>         <TextBlock x:Name="OutputText" Margin="0,12,0,0" Foreground="#8B949E" TextWrapping="Wrap"/>
>     </StackPanel>
> </Window>
> ```
>
> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Windows;
> using System.Windows.Media;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         public MainWindow() => InitializeComponent();
>
>         // 故意抛出异常，验证全局处理器能捕获而不闪退
>         private void OnThrow(object sender, RoutedEventArgs e)
>             => throw new InvalidOperationException("设备通信超时（模拟）");
>
>         public void ShowGlobalError(string message)
>         {
>             OutputText.Text = $"[{DateTime.Now:HH:mm:ss}] {message}\n（已在全局层记录日志，程序保持运行）";
>             OutputText.Foreground = new SolidColorBrush(Color.FromRgb(0xDA, 0x36, 0x33));
>         }
>     }
> }
> ```
> 

> [!scene] 适用场景
> ✅ 上位机 7×24 运行：漏网异常不能直接闪退，先记录再决定（示例场景）
> ✅ 后台采集线程异常：UI 线程看不到，必须全局兜底（见第 8 章）
> ✅ 第三方库/插件抛意外异常：SDK 不靠谱时全局钩子是最后防线
> ✅ 崩溃现场追溯：异常日志 + 堆栈是"案发现场"的第一证据
> ❌ 每个方法都能精确处理的异常：别依赖全局钩子，方法内 catch 更精准
> ❌ 致命异常（OOM、栈溢出）：全局钩子救不了，配置好 WER/崩溃转储

> [!pitfall] 常见踩坑
> 坑 1：**在 `DispatcherUnhandledException` 里 `e.Handled = true` 一律不退出** → 现象：程序连续出异常仍"强撑"运行，状态错乱越走越远 → 原因：把兜底当万能补丁 → 解决：`e.Handled = true` 只对"可恢复"异常；致命异常（`OutOfMemoryException`、`StackOverflowException`）记录后退出，重启程序
> 
> 坑 2：**后台线程异常没被 UI 钩子捕获** → 现象：`Task.Run` 里抛异常程序莫名退出 → 原因：`DispatcherUnhandledException` 只管 UI 线程 → 解决：补 `AppDomain.CurrentDomain.UnhandledException` 与 `TaskScheduler.UnobservedTaskException` 两个钩子
>
> 坑 3：**全局钩子里访问界面/卡死** → 现象：异常发生时在钩子里弹 MessageBox，现场无人点击程序挂死 → 原因：钩子处理太重 → 解决：钩子只做"记录日志 + 最小化提示"，UI 恢复走独立流程

> [!best] 最佳实践
> - 三钩子全挂：UI 线程（`DispatcherUnhandledException`）、非 UI（`AppDomain.UnhandledException`）、Task（`UnobservedTaskException`），一个都不能少
> - 钩子里只做三件事：写日志（含堆栈）、记录崩溃标记、最小化提示/退出
> - 异常日志尽量"瘦"：只记异常信息与关键上下文，别在钩子里做重操作（见 `serilog-结构化日志`）
> - 结合崩溃转储：配置 Windows 错误报告（WER）或 `dotnet-dump`，异常堆栈 + 内存快照双保险
> - 单元测试覆盖兜底逻辑：模拟抛出异常验证"日志记录 + 不闪退"（见 12.8 `单元测试xunitmoq`）

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例代码，点"触发异常"，观察全局钩子捕获、日志记录、界面提示（不闪退）
> **Lv.2 小试牛刀**：加一个后台线程异常：`Task.Run(() => throw new InvalidOperationException())`，观察 `UnobservedTaskException` 是否记录
> **Lv.3 融会贯通**：区分处理策略：`e.Handled = true` 继续运行 vs 致命异常记录后 `Environment.Exit`，模拟两种异常验证
> **Lv.4 拆层挑战**：把异常处理封装成 `IExceptionHandler` 服务（可注入），App 启动注册，测试时注入假实现验证"异常被记录"
