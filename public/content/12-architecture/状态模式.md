# 状态模式

> [!plain] 白话理解
> 状态模式是**把"不同状态下的不同行为"各自装进一个类**：设备在"待机/运行/报警"下，点"启动"的行为完全不同（待机→运行、运行→提示重复、报警→禁止）。与其写一堆 `if (state == 运行)`，不如让状态对象自己处理操作——每个状态类实现 `IDeviceState`，知道"自己在什么状态下该干什么、该切到哪个状态"。状态越多，这招越省心。

> [!def] 官方定义
> 状态模式（State Pattern）是 GoF 行为型设计模式：**允许对象在其内部状态改变时改变其行为，对象看起来好像修改了它的类**。核心结构：状态接口（State）+ 具体状态类（ConcreteState）+ 上下文（Context，持有当前状态并将请求转发给状态对象）。它与策略模式结构相似，但意图不同：状态模式用状态驱动转换（状态自己决定下一个状态），策略模式由外部选择算法。它是软件设计模式；.NET 中 `System.Threading.Tasks.Task` 的状态机实现（WaitingForActivation/RanToCompletion 等）就是状态化行为的典型：https://learn.microsoft.com/zh-cn/dotnet/api/system.threading.tasks.taskstatus 。

> [!origin] 由来背景
> 状态模式 1994 年 GoF 收录，但其思想源自更早的**有限状态机（FSM）**理论——计算理论中"状态+转移"模型，1960 年代起广泛用于编译器词法分析、协议解析、硬件控制。软件上的动机是"状态分支爆炸"：设备控制、协议解析等代码随状态增多，`if/switch` 嵌套到不可维护，改一个状态要动一大片。状态模式把"每个状态下所有操作的行为"内聚到状态类中，状态转换由状态对象协作完成——上位机设备状态机（待机/运行/报警/维护）、通信连接状态机（未连接/连接中/已连接/断开）都是它的最佳战场。

> [!essentials] 核心要点
> - **四角色**：状态接口 `IDeviceState`、具体状态类（`IdleState/RunState/AlarmState`）、上下文 `Context`（持有状态并转发请求）
> - **转换责任**：状态对象决定"下一个状态"，上下文只负责切换（示例 `ctx.State = new RunState()`）
> - **与策略模式的区分**：状态由内部转换驱动、行为依赖状态；策略由外部选择、行为不自动跳转
> - **状态一致性**：上下文的状态永远合法（禁止非法转移靠状态类自身约束）
> - **上位机应用**：设备状态机、通信连接状态、窗口页面状态（登录/配置/运行）

> [!example] 完整示例
> **设备状态机演示：设备在不同状态（待机/运行/报警）下"启动/停止/复位"行为不同，用状态对象替代大量 if-else 判断：**
>
> **MainWindow.xaml：**
> ```xml
> <Window x:Class="HmiDemo.MainWindow"
>         xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
>         xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
>         Title="状态机 - 状态模式" Height="320" Width="420"
>         WindowStartupLocation="CenterScreen" Background="#0D1117">
>     <StackPanel Margin="15">
>         <TextBlock x:Name="StateText" Text="当前状态：待机" Foreground="#58A6FF"
>                    FontSize="16" FontWeight="Bold"/>
>         <Button Content="启动" Click="OnStart" Margin="0,12,0,0" Padding="8"
>                 Background="#21262D" Foreground="White"/>
>         <Button Content="停止" Click="OnStop" Margin="0,8,0,0" Padding="8"
>                 Background="#21262D" Foreground="White"/>
>         <Button Content="触发报警 / 复位" Click="OnAlarmReset" Margin="0,8,0,0" Padding="8"
>                 Background="#21262D" Foreground="White"/>
>         <TextBlock x:Name="OutputText" Margin="0,12,0,0" Foreground="#8B949E" TextWrapping="Wrap"/>
>     </StackPanel>
> </Window>
> ```
>
> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System.Windows;
> using System.Windows.Media;
>
> namespace HmiDemo
> {
>     // 状态接口：不同状态对同一操作给出不同行为
>     public interface IDeviceState
>     {
>         string HandleStart(Context ctx);
>         string HandleStop(Context ctx);
>         string HandleAlarm(Context ctx);
>     }
>
>     // 状态 A：待机
>     public class IdleState : IDeviceState
>     {
>         public string HandleStart(Context ctx) { ctx.State = new RunState(); return "待机 → 运行：设备启动"; }
>         public string HandleStop(Context ctx) => "已在待机，无需停止";
>         public string HandleAlarm(Context ctx) { ctx.State = new AlarmState(); return "待机 → 报警：发生异常"; }
>     }
>
>     // 状态 B：运行
>     public class RunState : IDeviceState
>     {
>         public string HandleStart(Context ctx) => "已在运行，请勿重复启动";
>         public string HandleStop(Context ctx) { ctx.State = new IdleState(); return "运行 → 待机：设备停止"; }
>         public string HandleAlarm(Context ctx) { ctx.State = new AlarmState(); return "运行 → 报警：设备过温！"; }
>     }
>
>     // 状态 C：报警
>     public class AlarmState : IDeviceState
>     {
>         public string HandleStart(Context ctx) => "报警状态禁止启动，请先复位";
>         public string HandleStop(Context ctx) => "报警状态禁止停止，请先复位";
>         public string HandleAlarm(Context ctx) { ctx.State = new IdleState(); return "报警 → 待机：故障已复位"; }
>     }
>
>     // 上下文：持有当前状态，把操作转发给状态对象
>     public class Context
>     {
>         public IDeviceState State { get; set; } = new IdleState();
>         public string Name => State.GetType().Name.Replace("State", "");
>     }
>
>     public partial class MainWindow : Window
>     {
>         private readonly Context _ctx = new Context();
>
>         public MainWindow() => InitializeComponent();
>
>         private void OnStart(object sender, RoutedEventArgs e) => Do(() => _ctx.State.HandleStart(_ctx));
>         private void OnStop(object sender, RoutedEventArgs e) => Do(() => _ctx.State.HandleStop(_ctx));
>         private void OnAlarmReset(object sender, RoutedEventArgs e) => Do(() => _ctx.State.HandleAlarm(_ctx));
>
>         private void Do(Func<string> action)
>         {
>             OutputText.Text = action();
>             StateText.Text = $"当前状态：{_ctx.Name}";
>             OutputText.Foreground = new SolidColorBrush(Color.FromRgb(0x8B, 0x94, 0x9E));
>         }
>     }
> }
> ```
> 

> [!scene] 适用场景
> ✅ 设备状态机：待机/运行/报警/维护，不同状态下操作行为不同（示例场景）
> ✅ 通信连接状态：未连接/连接中/已连接/断开，重连策略随状态变化
> ✅ 流程状态：登录→配置→运行→停机，界面可操作项随状态切换
> ✅ 协议解析状态：帧头→长度→数据→校验，解析行为分阶段
> ❌ 只有两三个状态且行为简单：`if/else` 更直观，状态类是过度设计
> ❌ 状态转换复杂到需要显式状态图：先画状态转移图确认合法性再编码

> [!pitfall] 常见踩坑
> 坑 1：**非法状态转换未拦截** → 现象：报警状态还能被"停止"操作改变状态、数据错乱 → 原因：状态类没约束自己允许的转移 → 解决：状态方法内校验（示例 `AlarmState.HandleStop` 返回"禁止"），状态转换表集中维护
> 
> 坑 2：**上下文与状态互相持有导致循环引用** → 现象：`Context` 引用状态、状态又要操作上下文数据 → 原因：双向依赖 → 解决：状态方法接收 `Context` 参数（示例 `HandleStart(Context ctx)`），数据都在上下文里，状态类无状态可共享
>
> 坑 3：**状态对象每次转换都 `new`** → 现象：高频状态切换频繁创建对象、GC 压力大 → 原因：状态类可无状态却没复用 → 解决：状态类做成无状态单例（见 `单例模式`），转换时复用同一实例

> [!best] 最佳实践
> - 先画"状态转移图"再写代码：把每个状态"哪些操作合法、切到哪"画清楚，杜绝漏转移
> - 状态类保持无状态：状态行为所需数据通过 `Context` 传递，便于共享与测试
> - 状态转换集中收口：上下文提供 `TransitionTo(state)` 并记录日志（见 12.6 `serilog-结构化日志`）
> - 状态与界面联动：`StateText` 用 `INotifyPropertyChanged` 绑定（见第 7 章 `inotifypropertychanged-实现`），状态一变界面自动刷新
> - 与报警系统配合：进入 `AlarmState` 时通过观察者广播（见 `观察者模式`、第 10 章 `报警系统`）

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例代码，依次点"启动→触发报警/复位→启动"，观察状态流转与"禁止"提示
> **Lv.2 小试牛刀**：新增"维护"状态 `MaintainState`：`HandleStop` 从运行切到维护、维护下 `HandleStart` 回运行，把维护加进 `Context`
> **Lv.3 融会贯通**：把 `Context.State` 改为 `INotifyPropertyChanged` 属性，`StateText` 用 `{Binding}` 自动刷新（见第 7 章 `inotifypropertychanged-实现`）
> **Lv.4 拆层挑战**：把状态类改成共享单例（无状态设计），`Context` 增加 `TransitionLog` 记录每次转换（谁→谁、时间），界面显示完整转移历史
