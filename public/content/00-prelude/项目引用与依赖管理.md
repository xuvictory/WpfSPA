# 项目引用与依赖管理

> [!plain] 白话理解
> 项目引用就是「我需要你，所以我记下你的电话」——当你的 WPF 项目想要用另一个类库项目里的代码时，你得先在项目引用里「登记」它，编译器才知道去哪儿找那些类型。没了引用，就算两个项目在同一个解决方案文件夹里，编译器也当对方不存在。依赖管理的核心原则是「单向依赖」：上层依赖下层，界面依赖服务，服务依赖数据——像水流一样只能从上往下，绝不能反着来。

> [!def] 官方定义
> 项目引用（Project Reference）是在 .csproj 文件中通过 `<ProjectReference>` 元素声明的项目间编译依赖。它告诉 MSBuild：在编译当前项目之前，先编译被引用的项目，并将后者的输出 `.dll` 复制到当前项目的输出目录。依赖关系决定了编译顺序——MSBuild 通过拓扑排序自动解析依赖图，确保每个项目在被引用前已完成编译。

> [!origin] 由来背景
> 在 .NET 出现之前，C/C++ 项目的依赖管理是场噩梦——链接器配置（`.lib` 路径 + `.h` 路径 + 库搜索顺序）能让人抓狂，俗称 "DLL Hell"。.NET 程序集的版本管理和引用机制从根本上解决了这个问题：每个引用只声明程序集名称（或项目名），运行时根据清单自动加载，不需要注册表、不需要 PATH。更重要的是，MSBuild 在编译时自动检测编译顺序，开发者不需要手动排「A 先编译，B 再编译」——这在上位机多项目方案中省了大量的机械操作。

> [!essentials] 核心要点

> **三种引用方式对比**：

> | 引用方式 | 操作 | 用途 | 写在 .csproj |
> |----------|------|------|-------------|
> | **项目引用** | 右键「依赖项」→「添加项目引用」→ 勾选目标项目 | 引用同一解决方案中的其他项目 | `<ProjectReference>` |
> | **程序集引用** | 右键「依赖项」→「添加引用」→「浏览」→ 选 .dll 文件 | 引用外部的 .dll 文件 | `<Reference>` |
> | **NuGet 引用** | 右键「管理 NuGet 程序包」→ 搜索安装 | 引用第三方/官方发布的包 | `<PackageReference>` |

> **依赖管理的三大规则**：

> ```
> 规则 1：单向依赖（DAG，有向无环图）
>   ✅ App → Services → Models
>   ❌ Services → App（下层不能依赖上层）

> 规则 2：禁止循环引用
>   ✅ A → B → C
>   ❌ A → B → A（MSBuild 直接报错）

> 规则 3：最上层项目决定平台
>   ✅ App 目标 net8.0-windows，所有类库也用 net8.0
>   ❌ App 用 net8.0，Models 用 netstandard2.0（能兼容但增加认知负担）
> ```

> [!example] 完整示例
>
> **添加项目引用的三种方法**：
>
> 方法一：VS 图形界面
> ```
> 解决方案资源管理器 → 展开 WPF 项目 → 右键「依赖项」
> →「添加项目引用」→ 勾选目标类库项目 → 确定
> ```
>
> 方法二：直接编辑 .csproj
> ```xml
> <Project Sdk="Microsoft.NET.Sdk">
>   <ItemGroup>
>     <!-- 项目引用 -->
>     <ProjectReference Include="..\PlcMonitor.Models\PlcMonitor.Models.csproj" />
>     <ProjectReference Include="..\PlcMonitor.Services\PlcMonitor.Services.csproj" />
>     
>     <!-- 条件引用：只在 Debug 模式下引用的项目 -->
>     <ProjectReference Include="..\PlcMonitor.DebugTools\PlcMonitor.DebugTools.csproj"
>                       Condition="'$(Configuration)' == 'Debug'" />
>   </ItemGroup>
> </Project>
> ```
>
> 方法三：dotnet CLI
> ```bash
> dotnet add src/PlcMonitor.App reference src/PlcMonitor.Models
> dotnet add src/PlcMonitor.App reference src/PlcMonitor.Services
> ```
>
> **依赖关系可视化——用 dotnet 命令查看**：
> ```bash
> # 查看某个项目的直接依赖
> dotnet list src/PlcMonitor.App reference
> 
> # 输出：
> # 项目引用
> # ----------
> # ..\PlcMonitor.Models\PlcMonitor.Models.csproj
> # ..\PlcMonitor.Services\PlcMonitor.Services.csproj
> 
> # 查看 NuGet 包依赖
> dotnet list src/PlcMonitor.App package
> ```
>
> **编译顺序自动计算——你不需要手动排**：
> 假设你有以下依赖：
> ```
> App → Services → Models
> App → Protocols → Models
> ```
> MSBuild 会自动按这个顺序编译：`Models → Services & Protocols（并行）→ App`

> [!scene] 适用场景
> ✅ 多项目解决方案：每个用到的类库都要加项目引用
> ✅ 引入外部 DLL：第三方库只给了 .dll 没给源码时，用程序集引用
> ✅ 条件引用：Debug 模式引用调试工具库，Release 不引用
> ✅ 迁移 NuGet 到本地项目：团队决定自己维护某个包的修改版，删 NuGet 引用改为项目引用
> ❌ 用 NuGet 能满足的场景就用 NuGet——不要为了「控制源码」把所有依赖都本地化

> [!pitfall] 常见踩坑
> 坑 1：**添加了引用还是报「找不到类型」** → 三步检查：① 确认类是否为 `public`（不是 `internal` 或默认访问级别）；② 确认 .cs 文件顶部的 `using` 语句是否正确指向类库的命名空间；③ 确认类库项目的 TargetFramework 兼容（比如都用 `net8.0`，不要混用 `net6.0` 和 `net8.0`）。
>
> 坑 2：**引用了正确的项目，但运行时报 `FileNotFoundException`** → 编译通过不代表运行时能找到 DLL。检查：① 被引用的项目是否编译成功（解决方案是否勾选了编译该项目的配置）；② 输出目录中是否有对应的 `.dll` 文件；③ 是否在代码中用了反射动态加载但没有处理找不到的情况。
>
> 坑 3：**「依赖项」右键菜单没有「添加项目引用」** → 必须是 SDK 风格项目（.NET Core/5+）才有这个菜单。如果是老式 .NET Framework 项目，右键「引用」→「添加引用」。另一个常见原因：当前项目不是 SDK 风格，检查 .csproj 首行是否 `<Project Sdk="Microsoft.NET.Sdk">`。

> [!best] 最佳实践
> - 项目引用用相对路径：`..\OtherProject\OtherProject.csproj`，不要用绝对路径，否则换了电脑就崩
> - 最小依赖原则：App 只引用它直接需要的项目。如果 App → Services → Models，App 可以不直接引用 Models（除非 App 也直接使用 Models 中的类型）
> - 定期审查依赖：半年看一次，删掉多余的项目引用和 NuGet 包引用
> - 用「管理 NuGet 程序包」的「已安装」标签定期清理：攒了一堆版本过期的包会影响构建速度
> - 解决方案的「生成」配置检查：确保所有项目都勾选了对应的生成配置（Debug/Release），不然切换配置时某个项目不编译导致运行时找不到 DLL

> [!practice] 上手练习
> **Lv.1 照猫画虎**：创建一个 WPF 项目和一个类库项目。在类库中定义一个 `public class Calculator { public int Add(int a, int b) => a + b; }`。在 WPF 项目中添加对类库的项目引用，然后在按钮 Click 事件中调用 `new Calculator().Add(3, 5)` 并显示结果。
>
> **Lv.2 小试牛刀**：创建三个项目的依赖链：App → Services → Models。在 App 中只引用 Services，看能否直接使用 Models 中的类型（应该能，因为传递依赖）。然后故意制造一个循环依赖（Services 引用 App），观察 VS 报什么错。
>
> **Lv.3 融会贯通**：搭建一个 4 项目的上位机方案。App 引用 Services 和 Protocols。Services 引用 Models。Protocols 引用 Models。用 `dotnet list reference` 逐一确认依赖关系正确。手动改 .csproj 中的 `<ProjectReference>` 条件使其仅在 Debug 配置下引用 Protocols。
