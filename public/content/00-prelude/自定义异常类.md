# 自定义异常

> [!plain] 白话理解
> .NET 提供了 `ArgumentException`、`InvalidOperationException` 等通用异常，但有时候你需要更精准的表达——"Modbus CRC 校验失败"、"设备高温告警"、"协议帧格式错误"。这时候就该自定义异常了——继承 `Exception` 类，加上自己的属性和上下文信息，让 catch 代码一目了然地知道发生了什么。

> [!def] 官方定义
> 自定义异常是从 `System.Exception`（或其子类）派生的类，用于表示特定领域的错误。推荐：
> - 继承 `Exception` 或某个更具体的异常基类
> - 提供三个标准构造函数：无参、`string message`、`string message, Exception inner`
> - 标记 `[Serializable]`（如果可能跨域传输）
> - 添加领域特定属性携带上下文信息

> [!origin] 由来背景
> 早期 .NET 程序遇到领域错误（如"Modbus 从站返回错误码 0x02"）只能抛 `new Exception("Modbus错误")`——catch 后拿不到从站号、功能码、错误码，还得解析字符串，脆弱又啰嗦。社区的共识逐渐成型：把领域错误建模成类型。继承 `Exception` 自定义异常类，用属性携带结构化上下文，catch 时按类型精确匹配、按属性读取细节。如今自定义异常已成为大型上位机项目的标配，`ModbusException`、`DeviceOfflineException` 让错误一目了然。

> [!essentials] 核心要点
> - 继承 `System.Exception`，类名以 `Exception` 结尾
> - 必须提供三个标准构造函数：无参 / `(string message)` / `(string message, Exception inner)`——兼容序列化与旧调用方
> - 领域属性用只读（get-only），构造函数中赋值，保证异常对象不可变
> - 把完整消息拼好传给 `base(message)`，`ex.Message` 才有人可读的内容
> - 可分层继承：`ModbusException : Exception`，`CrcException : ModbusException`，catch 时可以分层捕获
> - 只存错误关键信息，不要持有整个设备对象

> [!example] 完整示例
> ```csharp
> public class ModbusException : Exception
> {
>     public byte SlaveId { get; }
>     public byte FunctionCode { get; }
>     public byte ErrorCode { get; }
    
>     public ModbusException(byte slaveId, byte funcCode, byte errorCode, string message)
>         : base($"从站{slaveId} 功能码0x{funcCode:X2}: {message} (错误码0x{errorCode:X2})")
>     {
>         SlaveId = slaveId;
>         FunctionCode = funcCode;
>         ErrorCode = errorCode;
>     }
    
>     public ModbusException() : base() { }
>     public ModbusException(string message) : base(message) { }
>     public ModbusException(string message, Exception inner) : base(message, inner) { }
> }

> // ====== 使用 ======
> try
> {
>     throw new ModbusException(0x01, 0x03, 0x02, "非法数据地址");
> }
> catch (ModbusException ex)
> {
>     Console.WriteLine($"Modbus错误: 从站{ex.SlaveId} 错误码{ex.ErrorCode}");
> }
> ```

> [!scene] 适用场景
> ✅ 领域特定的错误类型
> ✅ 需要携带错误上下文（设备ID、地址、错误码）给上层
> ❌ 可以复用内置异常 → 不自定义

> [!pitfall] 常见踩坑
> 坑 1：**消息没传给 `base(message)`** → 自定义异常里拼了 `Message` 属性但构造函数不调用 `base(...)`，`ex.Message` 会变成默认空内容，日志里什么都看不到。所有上下文都应经构造参数传给基类。
> 坑 2：**异常类里塞业务逻辑** → 自定义异常只该携带数据，别让它写日志、发通知、访问数据库，否则 catch 时会执行不可控的副作用，职责混乱。
> 坑 3：**丢弃 `innerException`** → 捕获底层 `IOException`/`TimeoutException` 后直接 `throw new DeviceException("...")`，根因链丢失。应 `throw new DeviceException("...", ex);` 保留原始异常。
> 坑 4：**忘记序列化构造** → 跨进程/跨 AppDomain 传递异常（如日志集中收集）时没有标准构造会序列化失败。

> [!best] 最佳实践
> - 命名以 `Exception` 结尾
> - 提供三个标准构造函数
> - 添加领域属性（方便 catch 后用）
> - 上位机中：`ModbusException`、`DeviceOfflineException`、`ProtocolMismatchException`
