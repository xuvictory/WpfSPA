# 单步执行（F10、F11）

> [!plain] 白话理解
> 单步执行就是在程序暂停后，像翻书一样「一行一行」往下走、观察每行代码执行的结果。F10 是「大步走」——把当前行当作一个整体执行完直接看结果，不钻进方法内部；F11 是「钻进去看」——如果当前行调用了你写的方法，它会跳进那个方法里逐行执行。上位机调试时，F10 帮你快速跳过系统方法（如 `SerialPort.Open()`），F11 帮你钻进自己的业务逻辑看每一步的数据变化。

> [!def] 官方定义
> 单步执行是 VS 调试器的核心交互模式。当程序在断点处暂停时：
> - **F10（逐过程 / Step Over）**：执行当前行，如果当前行包含方法调用，不进入该方法，直接执行完返回
> - **F11（逐语句 / Step Into）**：执行当前行，如果当前行包含方法调用，进入该方法的第一行继续调试
> - **Shift+F11（跳出 / Step Out）**：执行完当前方法的剩余代码，跳出到调用方
> - **F5（继续 / Continue）**：继续执行直到下一个断点或程序结束

> [!origin] 由来背景
> 单步调试（Single-step debugging）的概念可以追溯到 1970 年代的 UNIX `ptrace` 系统调用和 Intel 8086 处理器的 Trap Flag（TF 位）——CPU 执行一条指令后如果 TF=1 就触发 INT 1 中断。现代调试器（VS、GDB、LLDB）将这个底层机制封装成了用户体验很好的「黄色箭头 + F10/F11」。VS 的黄色箭头（当前执行行指示器）从 VS 2002 开始就是这个样子，20 年没变过，因为实在太直观了。

> [!essentials] 核心要点

> **单步执行三件套速查**：

> | 快捷键 | 名称 | 行为 | 上位机场景 |
> |--------|------|------|-----------|
> | `F10` | 逐过程 | 执行当前行，不进入方法 | 跳过 `SerialPort.Open()` 看连接结果 |
> | `F11` | 逐语句 | 进入方法内部逐行执行 | 钻进 `ParseRegisterData()` 看解析逻辑 |
> | `Shift+F11` | 跳出 | 执行完当前方法，回到调用者 | 方法里确认没问题，快速返回 |
> | `F5` | 继续 | 运行到下一个断点 | 跳过不关心的循环区域 |
> | `Ctrl+F10` | 运行到光标 | 执行到光标所在行后暂停 | 跳过一大段已知正确的代码 |

> **黄箭头能做什么**：

> | 操作 | 方法 | 效果 |
> |------|------|------|
> | 跳过代码 | 拖动黄箭头到下面几行 | 让程序「跳过」中间几行不执行 |
> | 回退执行 | 拖动黄箭头到上面几行 | 重新执行刚才的代码（回退不会撤销副作用！） |
> | 查看返回值 | 黄箭头停在 `return` 行 → 看自动窗口 | 看方法即将返回的值 |

> [!example] 完整示例
> ```csharp
> // 用单步执行调试一个上位机数据解析流程
> using System;
> using System.Collections.Generic;
> 
> namespace PlcMonitor
> {
>     public class DataDebug
>     {
>         public static void Main()
>         {
>             // 👈 F10 从这里开始
>             byte[] rawData = { 0x01, 0x03, 0x04, 0x00, 0x64, 0x00, 0xC8, 0xBA, 0xD4 };
> 
>             // 👈 F10 到大步，看到 rawData 已赋值
>             bool isValid = ValidateChecksum(rawData);
> 
>             // 👈 如果 isValid 为 false，F11 钻进去看哪里校验不通过
>             if (!isValid)
>             {
>                 Console.WriteLine("数据校验失败！");
>                 return;
>             }
> 
>             // 👈 F10 跳过，不关心 PrintHex 内部实现
>             PrintHex(rawData);
> 
>             // 👈 F11 钻进 ParseRegisterValues 看解析过程
>             var registers = ParseRegisterValues(rawData);
> 
>             foreach (var reg in registers)
>             {
>                 Console.WriteLine($"地址: {reg.Address}, 值: {reg.Value}");
>             }
>         }
> 
>         static bool ValidateChecksum(byte[] data)
>         {
>             // 👈 F11 钻进来后，逐行看 CRC 计算
>             if (data.Length < 3) return false;
> 
>             ushort crc = 0xFFFF;
>             for (int i = 0; i < data.Length - 2; i++)
>             {
>                 crc ^= data[i];
>                 for (int j = 0; j < 8; j++)
>                 {
>                     if ((crc & 1) != 0)
>                         crc = (ushort)((crc >> 1) ^ 0xA001);
>                     else
>                         crc >>= 1;
>                 }
>             }
> 
>             ushort receivedCrc = (ushort)(data[^2] | (data[^1] << 8));
>             return crc == receivedCrc; // 👈 看 crc 和 receivedCrc 是否相等
>         }
> 
>         static void PrintHex(byte[] data)
>         {
>             // 工具方法，F10 跳过不看
>             Console.WriteLine(BitConverter.ToString(data));
>         }
> 
>         static List<RegisterValue> ParseRegisterValues(byte[] response)
>         {
>             var result = new List<RegisterValue>();
>             int byteCount = response[2]; // 数据字节数
> 
>             for (int i = 3; i < 3 + byteCount; i += 2)
>             {
>                 ushort value = (ushort)((response[i] << 8) | response[i + 1]);
>                 // 👈 逐次看每个寄存器的值是否正确
>                 result.Add(new RegisterValue
>                 {
>                     Address = 100 + (i - 3) / 2,
>                     Value = value
>                 });
>             }
> 
>             return result; // 👈 Shift+F11 从这里跳出，回到 Main
>         }
>     }
> 
>     public class RegisterValue
>     {
>         public int Address { get; set; }
>         public ushort Value { get; set; }
>     }
> }
> ```
>
> **单步操作实战流**：
> ```
> 1. F9 在 Main 第一行设断点
> 2. F5 启动 → 停在断点
> 3. F10 × 3 → 跳过变量声明和校验调用
> 4. 发现 isValid = false → 重新 F5，这次在第 2 行 F11 钻进 ValidateChecksum
> 5. 在 CRC 计算中逐行 F10，发现一个位运算搞反了 → 心头雪亮
> 6. Shift+F11 跳出 → F5 继续完成
> ```

> [!scene] 适用场景
> ✅ 断点停住后的下一步：看数据经过每一步的变化
> ✅ 区分「哪一步把数据搞错了」：进方法前是对的，出方法后就错了，就在这个方法里
> ✅ 理解别人代码的执行流程：F11 钻进陌生方法看它到底干了什么
> ✅ 查 NullReferenceException：F10 逐行走，看哪一步对象变 null
> ❌ 大循环（1000+ 次）——F10 按到手抽筋，改用条件断点 + F5

> [!pitfall] 常见踩坑
> 坑 1：**F11 钻进了不想看的方法（如 `ToString()`、属性 getter）** → VS 默认会把所有代码当你的代码来调试。**解决方案**：「工具 → 选项 → 调试 → 常规」勾选「启用仅我的代码」，然后在调试 → 窗口 → 「仅我的代码」中会把系统/框架代码自动跳过。
>
> 坑 2：**F10 按太快，跳过了关键行** → 鼠标拖动黄箭头回到上一行可以重新执行。但注意：已经产生的副作用不会撤销（比如已经写入了文件、已经发送了网络请求）。对于纯计算逻辑可以放心回退，对于 I/O 操作要谨慎。
>
> 坑 3：**异步方法中 F10/F11 会「丢失」执行流** → `async` 方法被编译成状态机，单步进去后遇到 `await` 时执行流会跳出当前方法（交给 .NET 运行时调度）。当 `await` 完成后继续执行时，黄箭头可能跳到看似不相关的位置。**解决方案**：异步调试多用断点 + 跟踪点，少用单步；或者在 `await` 之后紧接着设一个断点。

> [!best] 最佳实践
> - F10 是默认选择，F11 只在你真的需要看内部实现时才用
> - 善用「运行到光标处」（`Ctrl+F10`）：把光标放在下面第 20 行 → Ctrl+F10 → 省掉 19 次 F10
> - 属性/运算符重载的 getter 会自动被 F10 执行但不进入——如果你怀疑属性 get 有问题，在那个属性的 get 里直接设断点，不要用 F11 撞大运
> - 配合「自动窗口」和「局部变量」窗口：F10 走一步，看一眼变量变化
> - 异步代码的调试策略：设断点 > 单步执行，因为异步状态机的跳转会让单步体验很差

> [!practice] 上手练习
> **Lv.1 照猫画虎**：写一个简单的计算器方法 `int Calculate(int a, int b)`，里面包含加、乘两个子方法的调用。在调用处设断点，用 F10 跳过子方法看结果，用 F11 钻进子方法看内部计算。体会 F10 和 F11 的区别。
>
> **Lv.2 小试牛刀**：写一个包含 3 层方法调用的流程：`Process() → Validate() → Checksum()`。在 `Process()` 中设断点，用 F11 一层层钻到底，再用 Shift+F11 一层层跳出来。用 Ctrl+F10 一次性跳到 `Process()` 的最后一行。
>
> **Lv.3 融会贯通**：写一个模拟 Modbus 响应解析的流程：生成响应字节 → CRC 校验 → 提取数据 → 转换为浮点数。在每一步设断点，用 F10/F11/Shift+F11 组合调试整个流程。在字节转换处故意写一个错误（如大小端搞反），用单步执行发现计算结果和预期不一致的具体位置。
