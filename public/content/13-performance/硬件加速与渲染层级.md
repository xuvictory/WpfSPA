# 硬件加速与渲染层级

> [!plain] 白话理解
> 把"把界面画到屏幕上"这件事外包给显卡（GPU）干，就是**硬件加速**——GPU 天生擅长画图形，又快又省 CPU；显卡不给力（老驱动、虚拟机、远程桌面）时，WPF 只能退回让 CPU 自己画，这就是**软件渲染**。**渲染层级（Tier）**就是 WPF 给显卡发的一张"评级卡"：0 级"完全不行"、1 级"部分行"、2 级"完全行"。示例用 `RenderCapability.Tier` 读出这张评级卡，再用 `RenderOptions.ProcessRenderMode` 在"软件渲染 / 硬件加速"之间一键切换——这正是现场工控机花屏、黑屏时售后最常用的兜底手段。

> [!def] 官方定义
> 渲染层级（Render Tier）是 WPF 依据显卡能力把硬件加速划分为的三个等级：**Tier 0**（无硬件加速，全部由 CPU 软件绘制）、**Tier 1**（部分加速，仅支持基本图形与文本）、**Tier 2**（完全加速，支持所有渲染特性）。层级值通过静态属性 `RenderCapability.Tier`（`System.Windows.Media` 命名空间）读取，返回值的高 16 位即层级数（示例的 `Tier >> 16`）。`RenderOptions.ProcessRenderMode`（`RenderMode.Default` / `RenderMode.SoftwareOnly`）用于**进程级**强制切换渲染模式，必须在 UI 线程（STA）设置，通常用于远程桌面、虚拟机、显卡驱动异常导致的花屏/黑屏兜底。详见官方文档：[WPF 图形渲染层级](https://learn.microsoft.com/zh-cn/dotnet/desktop/wpf/advanced/graphics-rendering-tiers)、[RenderCapability.Tier](https://learn.microsoft.com/zh-cn/dotnet/api/system.windows.media.rendercapability.tier)、[RenderOptions.ProcessRenderMode](https://learn.microsoft.com/zh-cn/dotnet/api/system.windows.media.renderoptions.processrendermode)。

> [!origin] 由来背景
> WPF 1.0（2006 年）首次把矢量界面全面托付给 DirectX 渲染，这在当时非常激进——彼时大量办公机、工控机还是集成显卡甚至无显卡环境，驱动对 DirectX 9 的支持参差不齐，强行硬件渲染必然大面积花屏。微软因此引入"渲染层级"机制：启动时检测显卡能力，能到哪一级就开哪一级的硬件加速，画不出就自动退回软件渲染。后来远程桌面、虚拟机场景又暴露出"驱动被虚拟化导致画面错乱"的新问题，WPF 4.0 起提供 `RenderOptions.ProcessRenderMode` 让开发者/运维可以强制软件渲染。对上位机而言，**现场工控机配置参差、还常被远程操控**，这套"自动降级 + 手动兜底"的机制至今仍是排查渲染问题的第一招。

> [!essentials] 核心要点
> - **Tier 读数**：`RenderCapability.Tier >> 16` 得到 0/1/2 三级，启动时检测一次即可，不要按整值直接比较
> - **进程级开关**：`ProcessRenderMode = RenderMode.SoftwareOnly` 强制全进程软件渲染，恢复用 `RenderMode.Default`
> - **自动降级**：硬件不可用（如远程桌面）时 WPF 会自动降级，但显式设置可让行为可控、可复现
> - **代价对比**：软件渲染全部走 CPU，叠加动画、模糊特效后性能差距可达数倍，是典型的"保稳定舍性能"
> - **调用约束**：`ProcessRenderMode` 只能在 UI 线程设置，工作线程调用无效或抛异常

> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System.Windows;
> using System.Windows.Interop;
> using System.Windows.Media;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         public MainWindow()
>         {
>             InitializeComponent();
>             CheckTier();
>             RefreshMode();
>         }
>
>         // 渲染层级：0 = 无硬件加速，1 = 部分，2 = 完全硬件加速
>         private void CheckTier()
>         {
>             int tier = RenderCapability.Tier >> 16;
>             string desc = tier switch
>             {
>                 0 => "纯软件渲染（CPU 绘制）",
>                 1 => "部分硬件加速",
>                 2 => "完全硬件加速（GPU 绘制）",
>                 _ => "未知"
>             };
>             TierText.Text = $"渲染层级 Tier：{tier} —— {desc}";
>         }
>
>         private void RefreshMode()
>         {
>             bool software = RenderOptions.ProcessRenderMode == RenderMode.SoftwareOnly;
>             ModeText.Text = software
>                 ? "当前：软件渲染模式（GPU 驱动异常时用于兜底）"
>                 : "当前：硬件加速模式（默认，性能最优）";
>         }
>
>         // 强制软件渲染：排查远程桌面、旧显卡等导致的渲染花屏/黑屏
>         private void OnToSoftware(object sender, RoutedEventArgs e)
>         {
>             RenderOptions.ProcessRenderMode = RenderMode.SoftwareOnly;
>             RefreshMode();
>         }
>
>         private void OnToHardware(object sender, RoutedEventArgs e)
>         {
>             RenderOptions.ProcessRenderMode = RenderMode.Default;
>             RefreshMode();
>         }
>     }
> }
> ```

> [!scene] 适用场景
> ✅ 现场工控机花屏/黑屏排查：远程桌面、虚拟机或旧显卡驱动异常，先 `SoftwareOnly` 验证是否渲染问题（一分钟定位）
> ✅ 项目启动自检：检测 `Tier`，低于 2 时在启动日志记录"渲染能力受限"，提示用户可能影响大屏动画
> ✅ 可视化大屏 / 多屏投屏：Tier 2 才启用高斯模糊等重特效，否则自动降级避免 CPU 满载
> ✅ 运维兜底开关：把渲染模式做成启动参数（`--soft-render`）或设置项，现场出问题可自助切换
> ❌ 显卡正常的开发机/办公机（默认硬件加速即可，无需干预）
> ❌ GPU 高性能计算类需求（WPF 渲染不承担计算任务，应走 CUDA/OpenCL 等专用方案）

> [!pitfall] 常见踩坑
> 坑 1：**直接拿 Tier 整值比较** → 现象：判断 `Tier == 2` 永远不成立，逻辑错乱 → 原因：`RenderCapability.Tier` 是一个 32 位值，层级编码在高 16 位（低 16 位是渐变支持标志位）→ 解决：先 `Tier >> 16` 取层级（示例写法），再与 0/1/2 比较
> 
> 坑 2：**在工作线程设置 ProcessRenderMode** → 现象：调用后不生效，甚至抛"调用线程必须为 STA"异常 → 原因：该 API 只能在 UI 线程（主窗口所属线程）调用 → 解决：用 `Dispatcher.Invoke` 包一层，确认在 UI 线程执行
>
> 坑 3：**软件渲染下还开着大量特效** → 现象：切换后 CPU 占用飙到 90% 以上，界面更卡 → 原因：软件渲染把所有特效、模糊、半透明都丢给 CPU 逐像素算 → 解决：软件模式下自动降低特效数量（见 `过度使用-effect-特效`），或提示用户恢复硬件加速

> [!best] 最佳实践
> - 启动时把 `Tier`、渲染模式写入日志（示例的 `CheckTier` 结果），售后远程排查时第一眼就知道渲染环境
> - "软件/硬件切换"做成设置项或命令行参数，现场问题运维可自助处理，不依赖开发人员到场
> - 软件渲染模式下自动裁剪重特效与大面积半透明，把有限 CPU 预算留给业务渲染
> - 切换前先读当前 `ProcessRenderMode` 判断是否已处于目标模式，避免重复设置引起不必要的重绘
> - 远程桌面场景优先考虑软件渲染：RDP 会禁用大部分 GPU 加速，强制硬件反而可能黑屏

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例，点击两个切换按钮，观察 `ModeText` 变化与图形渲染是否受影响，试试在远程桌面里跑一遍
> **Lv.2 小试牛刀**：新增"自动检测"逻辑：启动时 `Tier < 2` 就弹出提示框，询问是否切换软件渲染，点击后执行切换
> **Lv.3 融会贯通**：把渲染模式做成启动参数 `--soft-render`，程序启动时解析并设置，同时把 `Tier` 和最终模式写入日志文件，模拟现场排查流程
