# 布局循环

> [!plain] 白话理解
> 布局循环是 WPF 里的"永动机灾难"：你在 `SizeChanged` 事件里改了元素的宽度，改宽度又触发一次 `SizeChanged`，再触发一次修改……循环往复，`Measure`/`Arrange` 没完没了地跑，界面直接卡死。好比一个人站在体重秤上，看到自己胖了 1 斤就再吃 1 斤，称一次重一点、重一点再吃——永远循环下去。示例用计数器 + 25 次上限保护模拟了这个过程：勾选"启用布局循环模拟"，你能亲眼看到宽度一路暴涨直到被阈值拦停，真实场景里没有这个护栏，就是"界面假死 + CPU 100%"的现场事故。

> [!def] 官方定义
> 布局循环（Layout Loop）指 WPF 中因**布局属性在布局回调（`LayoutUpdated`、`SizeChanged`、`MeasureOverride`/`ArrangeOverride` 等）中被再次修改**，导致 Measure/Arrange 反复重入、无法收敛的死循环。WPF 布局系统本身没有循环检测与中断机制，一旦出现该模式，UI 线程会被无限布局占用，表现为 CPU 100%、界面完全无响应。常见触发：`SizeChanged` 里改 `Width`/`Height`/`Margin`、`LayoutUpdated` 里改布局属性、自定义 `MeasureOverride` 返回的期望尺寸随输入尺寸变化。诊断：`LayoutUpdated` 事件计数（示例 `_layoutCount`）持续增长即疑似循环；修复：从回调中移除布局属性修改，用标志位/定时器延迟修改，或用渲染层变换（`TranslateTransform`）代替布局属性变化。详见官方文档：[布局系统](https://learn.microsoft.com/zh-cn/dotnet/desktop/wpf/advanced/layout)、[FrameworkElement.LayoutUpdated](https://learn.microsoft.com/zh-cn/dotnet/api/system.windows.frameworkelement.layoutupdated)、[SizeChangedEventArgs](https://learn.microsoft.com/zh-cn/dotnet/api/system.windows.sizechangedeventargs)。

> [!origin] 由来背景
> WPF 的布局采用"级联测量-排列"模型：父元素尺寸变了会重新测量子元素，子元素尺寸变了也会向上冒泡影响父元素。这套模型本身是稳定的，但**回调里改布局属性**打破了稳定性——开发者常在图省事时写出"在 `SizeChanged` 里自适应改 `Width`"的代码，WPF 不像 Web 浏览器那样对循环有防护（如"仅触发一次"），于是循环变成死循环。官方文档反复强调"不要在布局回调中修改布局属性"，并把 `LayoutUpdated` 标注为"每次布局完成后触发"以提醒频率。上位机里"窗口缩放自适应""控件随数据变宽"这类需求最容易踩中这个坑，工程上统一用"标志位 + 延迟修改"或渲染层变换来规避。

> [!essentials] 核心要点
> - **循环公式**：布局回调（`SizeChanged`/`LayoutUpdated`/`MeasureOverride`）里改布局属性（`Width`/`Height`/`Margin`/`Dock`）→ 再次触发回调 → 死循环
> - **没有内置护栏**：WPF 不检测布局循环，只有"上限保护"式的代码逻辑能救命（示例 `_loopStep > 25` 终止）
> - **症状识别**：界面突然卡死 + CPU 100% + `LayoutUpdated` 计数疯狂增长（示例 `CountText` 就是计数器）
> - **修复三板斧**：①回调里不修改布局属性；②确需修改用标志位/`Dispatcher.BeginInvoke` 延迟；③位移类变化用 `TranslateTransform`（渲染层）
> - **自绘控件注意**：`MeasureOverride` 返回值依赖入参时也要防止振荡，加容差与上限

> [!example] 完整示例
> **布局循环演示与防护：在 SizeChanged 中修改尺寸形成自激，用上限保护避免界面卡死：**
>
> **MainWindow.xaml：**
> ```xml
> <Window x:Class="HmiDemo.MainWindow"
>         xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
>         xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
>         Title="布局循环检测与避免" Height="360" Width="520"
>         WindowStartupLocation="CenterScreen" Background="#0D1117">
>     <StackPanel Margin="15" Background="#161B22" Padding="15">
>         <TextBlock Text="布局循环（Layout Loop）演示与防护"
>                    Foreground="#58A6FF" FontSize="16" FontWeight="Bold"/>
>         <TextBlock x:Name="InfoText" Foreground="#8B949E" Margin="0,12,0,0" TextWrapping="Wrap"/>
>         <Border x:Name="TargetBox" Background="#21262D" Height="60" Margin="0,12,0,0"
>                 HorizontalAlignment="Left" SizeChanged="OnTargetSizeChanged">
>             <TextBlock Text="目标元素" Foreground="#8B949E" Margin="8" VerticalAlignment="Center"/>
>         </Border>
>         <CheckBox x:Name="LoopCheck" Content="启用布局循环模拟（改尺寸触发再次布局）"
>                   Checked="OnLoopChanged" Unchecked="OnLoopChanged"
>                   Margin="0,12,0,0" Foreground="#8B949E"/>
>         <TextBlock x:Name="CountText" Foreground="#DA3633" Margin="0,8,0,0" TextWrapping="Wrap"/>
>     </StackPanel>
> </Window>
> ```
>
> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Windows;
> using System.Windows.Controls;
> using System.Windows.Threading;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         private int _layoutCount;   // 布局触发计数
>         private int _loopStep;      // 循环模拟步数
>         private bool _inLoop;       // 是否处于模拟循环中
>
>         public MainWindow()
>         {
>             InitializeComponent();
>             // LayoutUpdated 每次布局完成后触发，用于监控布局频率
>             LayoutUpdated += (s, e) =>
>                 CountText.Text = $"布局次数：{++_layoutCount}";
>         }
>
>         private void OnLoopChanged(object sender, RoutedEventArgs e)
>         {
>             if (LoopCheck.IsChecked == true)
>             {
>                 // 第一次改宽度，触发 SizeChanged → 再次改宽度 → 形成布局循环
>                 _inLoop = true;
>                 _loopStep = 0;
>                 TargetBox.Width += 20;
>             }
>             else
>             {
>                 _inLoop = false;
>                 InfoText.Text = "已停止模拟，布局恢复正常。";
>             }
>         }
>
>         // 尺寸变化时再次修改宽度：这就是布局循环（Measure/Arrange 反复执行）
>         private void OnTargetSizeChanged(object sender, SizeChangedEventArgs e)
>         {
>             if (!_inLoop) return;
>             _loopStep++;
>             if (_loopStep > 25)
>             {
>                 // 防护：达到阈值自动终止，避免界面卡死
>                 _inLoop = false;
>                 LoopCheck.IsChecked = false;
>                 InfoText.Text = "已自动终止：真实布局循环会让界面卡死，应避免在 SizeChanged 中修改布局属性。";
>                 return;
>             }
>             InfoText.Text = $"布局循环进行中…第 {_loopStep} 次，目标元素宽度 {TargetBox.ActualWidth:F0}";
>             // 延后一步再改宽度，给布局执行留出时间（真实循环会无限递归）
>             Dispatcher.BeginInvoke(new Action(() =>
>             {
>                 if (_inLoop) TargetBox.Width += 20;
>             }), DispatcherPriority.Background);
>         }
>     }
> }
> ```

> [!scene] 适用场景
> ✅ 窗口缩放自适应：窗口 `SizeChanged` 里想"按比例改控件宽度"，最典型的循环雷区
> ✅ 控件随内容变宽：数据变化时想让按钮/文本块"自适应宽度"却写进 `SizeChanged`
> ✅ 自定义控件 MeasureOverride：自绘控件测量逻辑未收敛（返回值随输入振荡）
> ✅ 布局频率监控：任何页面可用 `LayoutUpdated` 计数器判断是否有异常布局风暴（示例 `CountText`）
> ✅ 列表容器尺寸联动：列表宽高互相影响导致反复重排
> ❌ 一次性布局调整（仅在初始化或数据变更时改尺寸，不依赖布局回调），无循环风险
> ❌ 渲染层变换能解决的位移/缩放（用 `TranslateTransform`/`ScaleTransform`，走渲染不走布局）

> [!pitfall] 常见踩坑
> 坑 1：**在 SizeChanged 里改宽度** → 现象：改一次宽度就引发连环重排，界面卡死、CPU 100% → 原因：改宽度触发 `SizeChanged`，事件里又改宽度，自激循环 → 解决：先量变差是否超过阈值（如 1px 内就返回），确需修改用标志位防重入（示例 `_inLoop`）或 `Dispatcher.BeginInvoke` 延迟
> 
> 坑 2：**LayoutUpdated 里做布局修改** → 现象：`LayoutUpdated` 里改了属性，布局完成后又触发 `LayoutUpdated`，循环不断 → 原因：`LayoutUpdated` 每次布局完成后都触发，改动属性会立刻开启新一轮布局 → 解决：`LayoutUpdated` 只做"观察计数"（示例 `CountText`）和轻量逻辑，绝不在里面修改布局属性
>
> 坑 3：**自定义控件测量不收敛** → 现象：自绘控件把布局"弹来弹去"，尺寸来回震荡 → 原因：`MeasureOverride` 期望尺寸随 `availableSize` 变化而没有收敛条件 → 解决：测量结果加容差判断（变化小于 0.5px 返回缓存值），必要时加最大迭代上限，防止振荡

> [!best] 最佳实践
> - 铁律：**布局回调里不修改布局属性**；`SizeChanged` 只读、`LayoutUpdated` 只观察
> - 确需响应尺寸变化：用标志位 + `Dispatcher.BeginInvoke` 延迟到下一轮再改（示例做法），并加阈值判断
> - 位移/缩放/旋转类变化一律 `RenderTransform`（渲染层），不碰 `Margin`/`Width`（见 `rendertransform-vs-layouttransform`）
> - 页面常驻一个 `LayoutUpdated` 计数器（示例 `CountText`），一旦发现布局次数异常暴涨立即排查
> - 发布前用 `wpf-performance-suite` 或探查器跑一遍交互流程，布局风暴在开发期就暴露

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例，勾选"启用布局循环模拟"，观察宽度自动涨、`布局次数`计数飙升、25 步后自动终止；去掉示例中的上限保护再试（改代码前先备份），体会卡死的严重性
> **Lv.2 小试牛刀**：把示例改成"阈值防抖版"：`SizeChanged` 里只有宽度变化超过 50px 才更新（记录上次宽度，小于 50 直接 return），验证正常缩放不再引发循环
> **Lv.3 融会贯通**：给真实项目做"布局风暴"体检：所有页面挂 `LayoutUpdated` 计数监控，跑一遍完整交互流程；找到 `LayoutUpdated`/`SizeChanged` 里改布局属性的代码，逐个用"阈值 + 延迟 + RenderTransform"方案修复，修复后用计数验证布局次数回归正常
