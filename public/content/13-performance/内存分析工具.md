# 内存分析工具

> [!plain] 白话理解
> 内存分析就是给程序装"水表 + 仓库清点器"：`GC.GetTotalMemory` 看的是"仓库里托管堆摆了多少货"，`WorkingSet64` 看的是"整个进程从系统领走了多少内存"（包括仓库和杂物间）。示例模拟了两种状况：分配 100 MB 临时数组——这是"正常进货，清完仓（GC）就能腾出来"；把 100 MB 塞进静态字段——这是"货架永久占位"，GC 来了也腾不出，等于泄漏。配合 VS 诊断工具抓"内存快照"，就能把泄漏的"货"一件件翻出来，看清是哪个对象、哪条引用链拽着不放。

> [!def] 官方定义
> 内存分析是定位内存泄漏与内存增长的软件调试活动。.NET 提供的基础观测 API：`GC.GetTotalMemory(bool forceFullCollection)`（`System`）返回托管堆当前分配的总字节数；`System.Diagnostics.Process.WorkingSet64` 返回进程工作集（物理内存中当前驻留的字节数）；`GC.CollectionCount(gen)` 返回第 n 代 GC 发生的次数。更高阶工具：Visual Studio 诊断工具（内存快照、托管堆对象图、引用路径）、`dotnet-dump`（`dotnet-dump analyze` 抓进程转储）、`dotnet-counters`（实时性能计数）、PerfView。定位泄漏的标准流程：抓基线快照 → 执行可疑操作 → 再抓快照 → 对比两次快照中"增多的对象"→ 查看引用路径找"根"。详见官方文档：[GC.GetTotalMemory](https://learn.microsoft.com/zh-cn/dotnet/api/system.gc.gettotalmemory)、[Visual Studio 内存诊断](https://learn.microsoft.com/zh-cn/visualstudio/profiling/memory-usage)、[dotnet-dump](https://learn.microsoft.com/zh-cn/dotnet/core/diagnostics/dotnet-dump)。

> [!origin] 由来背景
> WPF 上位机"内存越跑越大"的问题由来已久。早期排查只能靠任务管理器看进程内存，"知道涨了，不知道谁涨的"。微软随 .NET 提供 `GC.GetTotalMemory` 等基础 API，但只能看到"总量"，看不到"对象构成"。Visual Studio 2015+ 内置诊断工具补上了"内存快照 + 引用路径"能力：开发者可以像文件系统一样浏览托管堆里的对象、顺着引用链找到"到底是谁在持有泄漏对象"。配合 `dotnet-dump`/`dotnet-counters`（.NET Core 3.0+），还能在生产现场的工控机上离线抓转储、回开发机分析——这正是工业环境最需要的远程诊断能力。现在，"抓两个快照比对象差异"已经是内存排查的标准动作。

> [!essentials] 核心要点
> - **两个基本读数**：`GC.GetTotalMemory` 看托管堆总量；`WorkingSet64` 看进程工作集（含原生内存、GC 未回收部分）
> - **快照对比法**：基线快照 → 操作 → 对比快照，多出的对象就是可疑泄漏对象（VS 诊断工具核心用法）
> - **引用路径是关键**：找到增长对象后，顺"引用路径"看是谁持有它（静态字段？事件？集合？）
> - **GC 代际线索**：`GC.CollectionCount` 不断增长说明有大量对象进出，配合代际数判断压力来源
> - **现场转储**：工控机出问题用 `dotnet-dump collect` 抓转储，回开发机分析，无需现场断服务

> [!example] 完整示例
> **内存观测与泄漏模拟：GC.GetTotalMemory + 进程工作集读数，配合 VS 诊断工具定位泄漏：**
>
> **MainWindow.xaml：**
> ```xml
> <Window x:Class="HmiDemo.MainWindow"
>         xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
>         xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
>         Title="内存分析工具" Height="360" Width="640"
>         WindowStartupLocation="CenterScreen" Background="#0D1117">
>     <StackPanel Margin="15" Background="#161B22" Padding="15">
>         <TextBlock Text="内存观测与泄漏模拟（配合 VS 诊断工具 / 内存分析器使用）"
>                    Foreground="#58A6FF" FontSize="16" FontWeight="Bold"/>
>         <TextBlock x:Name="MemoryText" Foreground="#8B949E" Margin="0,12,0,0" TextWrapping="Wrap"/>
>         <StackPanel Orientation="Horizontal" Margin="0,14,0,0">
>             <Button Content="分配 100MB 临时数组" Click="OnAllocateTemp" Padding="8"
>                     Background="#21262D" Foreground="White"/>
>             <Button Content="制造静态泄漏" Click="OnCreateLeak" Padding="8" Margin="8,0,0,0"
>                     Background="#DA3633" Foreground="White"/>
>             <Button Content="强制 GC" Click="OnCollect" Padding="8" Margin="8,0,0,0"
>                     Background="#21262D" Foreground="White"/>
>             <Button Content="刷新内存读数" Click="OnRefresh" Padding="8" Margin="8,0,0,0"
>                     Background="#21262D" Foreground="White"/>
>         </StackPanel>
>         <TextBlock x:Name="LogText" Foreground="#58A6FF" Margin="0,16,0,0" TextWrapping="Wrap"/>
>     </StackPanel>
> </Window>
> ```
>
> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Diagnostics;
> using System.Windows;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         private static byte[] _staticLeak;   // 静态字段持有 → 永不回收 → 模拟泄漏
>         private byte[] _temp;                // 普通字段 → GC 后可回收
>
>         public MainWindow() => InitializeComponent();
>
>         private void OnAllocateTemp(object sender, RoutedEventArgs e)
>         {
>             _temp = new byte[100 * 1024 * 1024];   // 分配 100 MB 临时数组
>             Log("已分配 100 MB 临时数组（普通字段持有，GC 后可回收）");
>         }
>
>         private void OnCreateLeak(object sender, RoutedEventArgs e)
>         {
>             _staticLeak = new byte[100 * 1024 * 1024];  // 静态引用 → 无法回收 → 泄漏
>             Log("已分配 100 MB 并存入静态字段（静态引用 → 永久泄漏）");
>         }
>
>         private void OnCollect(object sender, RoutedEventArgs e)
>         {
>             _temp = null;   // 断开临时引用
>             var sw = Stopwatch.StartNew();
>             GC.Collect();
>             GC.WaitForPendingFinalizers();
>             GC.Collect();
>             sw.Stop();
>             Log($"强制 GC 完成，耗时 {sw.ElapsedMilliseconds} ms（静态泄漏的内存仍无法回收）");
>             RefreshMemory();
>         }
>
>         private void OnRefresh(object sender, RoutedEventArgs e) => RefreshMemory();
>
>         // 内存读数：与分析工具观测同一进程，用于验证泄漏
>         private void RefreshMemory()
>         {
>             long managed = GC.GetTotalMemory(false);
>             long workingSet = Process.GetCurrentProcess().WorkingSet64;
>             MemoryText.Text = $"托管堆：{managed / 1024 / 1024} MB；进程工作集：{workingSet / 1024 / 1024} MB；" +
>                               $"已发生 {GC.CollectionCount(0)} 次第 0 代 GC";
>         }
>
>         private void Log(string msg) => LogText.Text = msg;
>     }
> }
> ```

> [!scene] 适用场景
> ✅ 上线前内存体检：长时间运行 4 小时后内存读数应趋于平稳，上涨趋势 = 潜在泄漏（示例读数就是体检工具）
> ✅ 页面泄漏定位：重复开关可疑页面，VS 诊断工具抓快照对比，找到"每次开关都多一批"的对象
> ✅ 现场远程诊断：工控机内存异常时 `dotnet-dump collect` 抓转储，回开发机 `dotnet-dump analyze` 分析
> ✅ 大对象排查：`GC.GetTotalMemory` 突增 + `WorkingSet64` 居高不下，排查 85KB 以上的大对象（LOH）
> ✅ 图片/缓存优化验证：优化位图解码（见 `图片优化与位图缓存`）前后用读数对比内存收益
> ❌ 只关心"是否卡顿"的普通功能开发（先用任务管理器粗看，卡了再上工具）
> ❌ 需要精确定位对象引用路径时（此时 VS 快照/转储分析才够用，裸 API 看不到对象图）

> [!pitfall] 常见踩坑
> 坑 1：**只看 WorkingSet64 下结论** → 现象：内存数字很高，误判"泄漏" → 原因：工作集包含 GC 未归还给 OS 的内存、原生内存、缓存，不代表泄漏 → 解决：以 `GC.GetTotalMemory` 托管堆为主，结合 `GC.CollectionCount`，配合快照对比下结论（示例同时展示两个读数）
> 
> 坑 2：**没抓基线就分析** → 现象：分析半天不知道哪些对象是"新增"的 → 原因：没有起始快照做对照 → 解决：固定流程——先抓基线快照，再执行一次可疑操作，再抓快照，只比较两次差异（VS 诊断工具的"对比"功能）
>
> 坑 3：**调试态与发布态混为一谈** → 现象：Debug 下内存高涨，Release 下正常 → 原因：Debug 下 GC 延迟（`gcAllowVeryLargeObjects` 等配置不同）、调试器持有对象引用 → 解决：内存评估一律在 Release + 无调试器（Ctrl+F5）下进行，`GC.Collect()` 手动回收后再读数

> [!best] 最佳实践
> - 三件套读数：`GC.GetTotalMemory` + `WorkingSet64` + `GC.CollectionCount(0)`，一起展示避免误判（示例 `RefreshMemory`）
> - 先用手动 `GC.Collect()` 排除"GC 没来得及收"的假象，再判断是不是真泄漏（示例 `OnCollect`）
> - 正式分析用 VS 诊断工具抓快照，对比前后差异 + 查引用路径，不要只靠总量猜
> - 泄漏观察要在 Release 无调试器下进行，内存基线记录到版本发版说明，长期跟踪
> - 生产现场优先 `dotnet-dump`/`dotnet-counters`：不影响运行，转储带回开发机分析

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例，点"分配 100MB 临时数组"→"强制 GC"，观察托管堆回落；再点"制造静态泄漏"→"强制 GC"，观察托管堆不再回落（泄漏特征）
> **Lv.2 小试牛刀**：在 VS 中用"诊断工具"附加示例程序：先抓内存快照，执行"制造静态泄漏"后再抓快照，对比两次快照中新增的 `Byte[]` 对象及其引用路径，找到 `_staticLeak` 字段
> **Lv.3 融会贯通**：为你的项目做一次完整内存体检：Release 运行 4 小时，记录三件套读数曲线；对"页面开关"类操作做快照对比，定位并修复 1 处真实泄漏；最后用 `dotnet-counters monitor` 在本地模拟现场观测流程
