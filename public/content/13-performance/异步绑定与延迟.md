# 异步绑定与延迟

> [!plain] 白话理解
> 把 UI 线程想成一台"单行道上的小轿车"，它既要开（响应鼠标、刷新界面），又要拉货（跑业务逻辑）。同步写法就是让司机"边开车边搬货"——一搬重货（比如查 10 万条数据、算 5 万次加密），车就停下来，方向盘（鼠标）怎么转都没反应，这就是"界面卡死"。`async/await` 的做法是：把重货丢给旁边的卡车（线程池）去拉，小轿车继续开，等货到了再用 `await` 把结果接回来——界面永远在动。示例里同步按钮一按界面冻结 3 秒，异步按钮点了立刻能拖动窗口，差别一眼可见。

> [!def] 官方定义
> 异步编程（Asynchronous Programming）指不阻塞调用线程的前提下执行耗时操作，由 `async`/`await`（.NET 4.5+）或 `Task` 实现。在 WPF 中，UI 线程（Dispatcher 线程）负责处理输入、布局、渲染，任何长时间运行于其上的代码都会冻结界面。`await` 会"暂停"当前方法并把控制权交还 UI 线程的消息循环，耗时操作在后台（线程池）执行，完成后通过 `SynchronizationContext` 自动回到 UI 线程继续——这就是"异步不卡界面"的原理。延迟（Delay）指 `Task.Delay` 等非阻塞等待，与 `Thread.Sleep` 阻塞式等待不同，`Task.Delay` 不占用线程。相关 API：`async`/`await`、`Task.Run`、`Task.Delay`、`CancellationToken`。详见官方文档：[使用 async 和 await 的异步编程](https://learn.microsoft.com/zh-cn/dotnet/csharp/asynchronous-programming/)、[Task.Run](https://learn.microsoft.com/zh-cn/dotnet/api/system.threading.tasks.task.run)、[Task.Delay](https://learn.microsoft.com/zh-cn/dotnet/api/system.threading.tasks.task.delay)。

> [!origin] 由来背景
> 桌面软件早年处理耗时操作只有两条路：`Thread` 手工开线程，或用 `BackgroundWorker`。前者容易踩跨线程访问控件的雷，后者 API 啰嗦。微软在 .NET 4.5（2012 年）引入 `async/await`，把"异步 + 回到原线程"的样板代码压缩成了两个关键字，编程体验脱胎换骨。但对上位机来说，最大的敌人不是语法而是习惯：很多人"能同步就同步"，直到发现"一查历史数据界面就死 3 秒"才回头改异步。`async/await` 让"耗时操作后台化"变成随手可写的默认选项，这也是现代上位机框架（包括 MVVM 里 `ICommand` 的异步实现）普遍采用它的原因。

> [!essentials] 核心要点
> - **await 不占线程**：`await` 期间 UI 线程恢复响应，后台任务在线程池执行，不阻塞不浪费
> - **自动回 UI 线程**：UI 线程发起的 `await` 完成后默认回到 UI 线程，可安全更新控件
> - **Task.Run 用于 CPU 密集**：计算/解析/序列化等用 `Task.Run` 丢后台；IO 密集（读文件、串口）用原生 `await` API 即可
> - **同步调用陷阱**：`async void` 的事件处理器可以，但业务方法应返回 `Task`；`Result`/`.Wait()` 在 UI 线程会导致死锁
> - **取消支持**：耗时循环配合 `CancellationToken`，关闭窗口/切换页面时可及时中断

>                     Background="#238636" Foreground="White"/>

>                      Background="#0D1117" Foreground="#8B949E" BorderThickness="0" Padding="8"
>                      TextWrapping="Wrap" AcceptsReturn="True"/>
>         </Border>
>     </Grid>

>
> **MainWindow.xaml.cs —— 后台代码：**
> ```csharp
> using System;
> using System.Diagnostics;
> using System.Linq;
> using System.Threading;
> using System.Threading.Tasks;
> using System.Windows;
>
> namespace HmiDemo
> {
>     public partial class MainWindow : Window
>     {
>         public MainWindow() => InitializeComponent();
>
>         // 同步加载：模拟耗时 3 秒，UI 线程被占死，窗口无法拖动、按钮无法点击
>         private void OnSyncLoad(object sender, RoutedEventArgs e)
>         {
>             Thread.Sleep(3000);   // 阻塞 UI 线程 3 秒
>             ResultText.Text = $"同步加载完成，共 {100000} 条记录";
>         }
>
>         // 异步加载：耗时操作放后台，UI 线程保持响应
>         private async void OnAsyncLoad(object sender, RoutedEventArgs e)
>         {
>             ResultText.Text = "异步加载中……界面可正常操作";
>             int count = await Task.Run(() =>
>             {
>                 // 模拟耗时 3 秒的批量查询与计算
>                 Thread.Sleep(3000);
>                 return Enumerable.Range(1, 100000).Count();
>             });
>             ResultText.Text = $"异步加载完成，共 {count} 条记录";
>         }
>     }
> }
> ```

> [!scene] 适用场景
> ✅ 历史数据查询：按时间段查 10 万条记录耗时 2~5 秒，异步查询期间界面可缩放、可翻其他页
> ✅ 串口/网络通信读取：设备应答慢（几百 ms 到数秒），异步等待不阻塞主界面
> ✅ 批量文件解析：导入 CSV/配方文件几十 MB，`await Task.Run` 后台解析后一次性刷新界面
> ✅ 报表生成/导出：Excel 导出几万行耗时数秒，异步期间弹出"正在导出"动画
> ✅ 延迟绑定刷新：`Task.Delay(100)` 节流合并高频数据更新（见 `频繁-ui-更新节流防抖`）
> ❌ 几毫秒的轻量计算（异步反而增加上下文切换与代码复杂度）
> ❌ 涉及 UI 控件的逻辑（UI 操作必须在 UI 线程，后台线程里的控件访问会抛异常）

> [!pitfall] 常见踩坑
> 坑 1：**用 Result 或 Wait 同步等待 Task** → 现象：点按钮后界面不仅卡死，还可能永远转圈 → 原因：UI 线程 `.Result` 阻塞等待任务，而任务完成回调又要回 UI 线程，形成死锁 → 解决：全程 `await`，不要 `.Result`/`.Wait()`（示例的异步分支是正确的 `await` 写法）
> 
> 坑 2：**async void 滥用** → 现象：异步方法里的异常没有捕获，程序直接崩 → 原因：`async void` 的异常无法被调用方捕获，会直接抛到 `SynchronizationContext` → 解决：事件处理器可以 `async void`（框架要求），但其他方法一律返回 `Task`，用 `try/catch` 捕获并展示
>
> 坑 3：**在后台线程碰控件** → 现象：`Task.Run` 里直接改 `TextBlock.Text`，抛跨线程异常 → 原因：`Task.Run` 的委托在线程池执行，不在 UI 线程 → 解决：后台只算数据，`await` 回到 UI 线程后再赋值（示例的 `ResultText.Text` 就在 await 之后）

> [!best] 最佳实践
> - 命令统一走异步：MVVM 中 `ICommand` 的 `ExecuteAsync` 模式（如 `AsyncRelayCommand`），从源头杜绝同步阻塞
> - `await Task.Run` 只包 CPU 密集段；IO/设备类用库自带的异步 API（`Stream.ReadAsync`、串口 `await` 包装）
> - 所有耗时循环加 `CancellationToken`，窗口 `Closed` 时 `Cancel()`，避免"关了窗口还在跑查询"
> - 更新 UI 只更新"最终结果"，不要在循环里逐条 `await`（会造成大量切换）；用节流合并批量刷新
> - 用 `Stopwatch` 记录真实耗时并输出日志，让"异步到底省了多久"有据可查

> [!practice] 上手练习
> **Lv.1 照猫画虎**：运行示例，先点"同步加载"立刻拖动窗口看是否卡死；再点"异步加载"，3 秒内在输入框打字验证界面响应
> **Lv.2 小试牛刀**：给异步加载加一个 `ProgressBar`：在 `Task.Run` 里循环输出进度，通过 `IProgress<double>` 报告进度并实时更新进度条
> **Lv.3 融会贯通**：把异步思想落地到真实数据采集：用 `await Task.Delay(100)` + `while` 循环模拟"每秒采集 1000 点"的异步采集器，界面显示实时计数并可随时"停止采集"（`CancellationTokenSource`），验证采集期间拖动窗口、点击按钮全部流畅
